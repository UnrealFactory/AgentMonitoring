`WORK-0005`, a work record in the relay project this app also tracked, described a receiving machine. It answered 503 for three hours, then 200, which meant it had recovered. On the page the 200 was gone. A "1." stood in its place, and one sentence had been broken into three. Nothing looked wrong, on the one screen whose job is to show a record exactly as written.

**The P2 comprehension critic got the number back only by luck.** That reviewer reads a record cold and says whether a newcomer could follow it. The phrase was written a second time, further down. That second copy is where it came back from.

**A sentence too long for one line had wrapped, and the next line began "200.".** Inside `src/lib/markdown.tsx`, the file that turns a stored record into a page, `parseBlocks` cuts that text into paragraphs and lists. It used one test for two questions. Does a numbered list start on this line? Does the paragraph I am in end here?

**The test was a single line-shape**, `^\s*([-*+]|\d+[.)])\s`. That means a line opening with a dash, a star, a plus, or a number and a dot. A line beginning "200." answers yes to the first question. It should almost never answer yes to the second.

It is like a form where anything on a numbered line gets renumbered, so your "200" comes back as "1".

**A public rulebook already said so.** CommonMark is the agreed standard for the marks writers put into plain text: stars, dashes, back-quotes. Its rule is that a numbered list may cut into a running paragraph only when it starts at 1. That rule exists for this reason.

**I moved the reading apart from the drawing.** The reading half now sits in `src/lib/markdown-parse.ts`, which runs without the page around it. A new test there, `interruptsParagraph`, decides whether a line really ends the paragraph. A dash may cut in. A number may cut in only at 1.

**Two nearby faults went with it.** A list the writer began at 3 keeps those numbers: it carries a `start`, taken from the writer's own first marker. And `parseInline`, the part that reads what sits inside a line, now reads bold all the way through. A name marked as code inside bold arrives as a name, not as quote marks.

**The check that would have caught this is `npm run smoke`.** It draws nine passages copied word for word out of real records, this sentence among them. Then it reads every record of both projects the app held then: twenty in one, ten in the other. It fails if a word of a stored record is missing from the drawn page. All 55 of its checks pass.

**I made it fail on purpose before trusting it.** Putting the old behaviour back failed two of the nine passages, and printed the drawn text with the 200 missing. Restoring the rule passed them again.

**Lists inside lists still come out flat.** No record uses one today; I searched `./vault`, the folder holding both projects' records then. Doing that properly is a bigger rebuild than this fix was.

The worst wrong page is the one that looks fine.
