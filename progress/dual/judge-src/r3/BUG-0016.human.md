`cargo test`, the command that runs this program's own automatic checks, reported 20 of 21 passed and one failed. Which one, nobody could say: the output had been trimmed to its last twelve lines, so the tally survived and the list of failures was thrown away. A suite that fails one run in sixteen teaches everybody to run it again — including the run that means something.

**It would not come back that day.** Four more full runs, six runs of that one file, and four of those at once to make them fight over the disk: green every time. It had failed straight after a browser check that loaded 413 pages, and finished in 0.40 seconds where an idle run takes 0.57. The obvious suspect was the one test that starts several writers at once; it went in as a suspect, not a finding.

**Two days later another agent caught it with the whole output kept.** Three of that test's writers had died on one file, `.agentmon.lock` — the marker a writer makes so the others wait their turn. It is like a key that must be hung back on its hook before the next person can take it, and for a moment it is neither on the hook nor in a hand.

**Windows gives an answer nobody was waiting for.** Ask for that marker while the previous holder is halfway through handing it back, and the reply is "permission denied", not "someone already has it". The waiting code only knew to wait on the second, so the writer gave up on the spot. A busy disk makes the hand-back and the next grab overlap more often.

**"Permission denied" now waits and tries again**, on the same clock as before. Three full runs of the suite are green, and five of the crowded test alone. By then it was no longer rare: once note-writing added traffic to that marker, the suite was failing about one run in five.

Never trim the output of a failing test.
