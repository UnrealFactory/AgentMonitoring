The list of bugs gave each one two lines and a dot coloured for how bad it was. You could narrow it by that dot or by a label, and by nothing else. A bug's own page gave the report, the conversation and the fix equal weight.

**The board is a triage screen now.** Three tabs run across the top — Open, Resolved, All — each carrying a count that already obeys your other choices, so it answers "how many will I see if I switch". You can also narrow by how bad a bug is, by label, by who owns it and who filed it, or by typing. Each bug is then one line, worst first.

**A bug's own page now has a moment.** One strip holds the three dates and they appear nowhere else: filed, claimed, fixed, with the real gaps between. The fix ends the page as a wide coloured banner: who fixed it, and how long it had been open.

**Three faults in shared code went first; both pages would have inherited them.** The code that draws a record read any line opening with a number and a full stop as the start of a numbered list, so a sentence wrapping onto "200. Without jitter…" lost the 200 and printed "1." — that is `BUG-0004`, filed and fixed here. A row too narrow for its contents used to sacrifice its title first, and sheds its tag chips first now. And a record listed only the records it points at; each now lists the ones pointing back.

It is like a typist who sees a figure at the top of a line and decides you meant to begin a list.

**I drove the finished board in a real browser, then read the screens it draws.** On the bugs it was reading, the tabs came back 2, 6 and 8; a nonsense search gave the designed empty page, whose button brought all eight back. Nothing errored.

Still wrong: the tabs over the work-log list count the whole project while the rows beneath them are filtered — `BUG-0005`, for another round.

A list you cannot narrow is a list somebody has to read from the top.
