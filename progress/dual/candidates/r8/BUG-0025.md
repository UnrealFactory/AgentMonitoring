You edit a screen file while the app is running for development. You save. The app shows the old version. A full reload of the page shows the old version too. Twice, in two different sessions, someone blamed a leftover old server squatting on port 5173 — the numbered door the app talks to while we build it — killed it, started fresh, and hit the same wall.

**A server seconds old, already stale.** That guess was wrong in a way that hid itself well. A brand-new server was stale too, for any file touched after it started. One thing made everything look healthy: a file created after the server was running got built correctly the first time it was asked for. The tool worked. It just never learned that anything had a second version. Asking the server outright for `src/App.tsx`, our main screen, handed back that screen without the day's edits in it.

**One line in vite.config.ts.** vite is the tool that rebuilds our screens as we edit them, and part of it sits and watches files for changes. Its settings file, vite.config.ts, told that watching part to ignore `**/AgentMonitoring/**` — any folder named AgentMonitoring, at any depth, and everything inside it. The reason was sound. Records get written into a folder of that name inside the project, and those writes should not shake the app. But the whole project lives at C:/Code/AgentMonitoring. Its own folder is named AgentMonitoring. So the pattern swallowed every file we write, and the watching stopped completely — including on vite.config.ts itself, which is why the rule could never notice its own change and reload.

It is like telling the cleaner to skip any room called the store room, in a building called The Store Room.

**One folder, spelled out.** The rule now names one exact folder by its full path — the AgentMonitoring folder at the top of the project — instead of a pattern that matches anywhere.

**The probe line.** Checked against the running desktop app: one throwaway line, `export const __watchProbe = 1`, was added to src/lib/useScrollRestoration.ts, a new file that remembers where you had scrolled to. It appeared in what the server handed out within 2 seconds. Deleted, it vanished again. Both directions, with nothing restarted. Cached-forever code cannot do that.

**What is different, and what nobody guards.** Edits show up in the running app again, which is what made this worth stopping for. The original intent survives: writing records into the data folder still does not disturb the development app, and the app still sees new records, because it goes and asks for them itself on a repeat. The proof here was a person watching, once, on one machine. No automatic check was written, so if that pattern widens again, nothing will say so.

A rule that skips folders by name will skip the one you are standing in.
