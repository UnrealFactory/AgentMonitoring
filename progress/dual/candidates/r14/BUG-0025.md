You edit a file in the app's code while the app runs for development. Nothing on screen changes. You reload the whole page and still get the old code.

**Twice we blamed a leftover server.** Two sessions read this as an older server from an earlier run, still going and still giving out old code. It was not that: a server seconds old is stale too, for anything you edit after it starts.

**One skip rule covered every file we write.** `vite.config.ts`, the settings file for the program that rebuilds the app as you work and feeds it to the screen, told it to skip `**/AgentMonitoring/**` — any folder named AgentMonitoring, at any depth, and everything inside it. That folder is where this app writes its own records, and those writes should not reload the app you are working in. But the folder holding this whole project has the same name, so every file of code sits inside one called AgentMonitoring.

It is like telling a house-sitter to skip any room called the office, in a house itself called The Office.

**You get the first copy, forever.** That program converts each file the first time something asks for it, then hands back the same copy ever after. It makes a fresh one only when it is told the file changed, and nothing was going to tell it. It could not see edits to its own settings file either, so it never restarted itself.

**The day's new file looked healthy.** `src/lib/useScrollRestoration.ts`, new code for putting you back where you had scrolled to, did nothing at all in the running app. Its first request converted it fine, and that is what hid the fault.

**The skip rule now names one exact folder.** It is spelled out from the top of the project, so it covers the data folder and nothing else.

**I watched one edit appear, then vanish.** On a live server started with `npm run tauri:dev`, the command that runs the desktop app for development, I added a marker line to that scroll file. Within two seconds the server was handing out the changed version. I deleted the line and it dropped away just as fast, with no restart. A copy cached at startup can do neither.

The old aim survives: writing a record still does not reload the server, and the app spots new records by asking again on its own. I checked that by hand, on one running server. Nothing announces this kind of failure: the server starts, the page loads, and the code is quietly old.

"Skip this folder anywhere" includes the folder you are standing in.
