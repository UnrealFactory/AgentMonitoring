Edits to the app's screens never reached the running app. You saved a file, reloaded the page, and the old version came back. Nobody could see their own changes.

**The wrong culprit.** Two sessions blamed a leftover program still using `5173`. That is the numbered channel where the development server answers. That server hands the app's files to the browser while you work. But a server started seconds ago was already out of date for any file edited afterwards.

**What the ignore rule said.** The server watches the project folder and re-sends any file you change. Its settings file, `vite.config.ts`, told it to skip anything matching `**/AgentMonitoring/**`. That means any folder with that name, anywhere, and all its contents. The rule was there so the app's own saved data would not trigger reloads.

The folder holding all of the app's code is itself named AgentMonitoring. So the pattern matched every file in the project, the settings file included. The watcher was ignoring everything.

Think of it as skipping every box labelled spare, in a garage that is itself labelled spare.

**What kept it hidden.** The server could not see its own settings change, so it never restarted itself. A brand-new file still arrived correctly on its first request. Only later edits to it went nowhere.

The ignore rule now names one exact folder: the data folder at the top of this project. Nothing outside it can match.

**How we know.** With the desktop app running, we added one line to a code file. It appeared in what the server handed out within two seconds. It left again when we deleted it. No restart. The record names no automated test guarding this.

Edits show up again, and the original intent holds. Data written into that one folder still causes no reloads. The app notices those writes by asking for updates on a schedule.

A rule that skips anything called X, anywhere, will one day skip the thing it lives in.
