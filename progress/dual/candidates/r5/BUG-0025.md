A development server builds the app's screens while we work and hands them to the window on screen. Editing any of those files changed nothing there. Even a full page reload brought back the old version, because the server keeps handing out the copy it prepared when that file was first asked for.

Two sessions blamed a leftover server from an earlier run and restarted it. That never helped: a server seconds old is already stale for any file edited after it started.

It surfaced during WORK-0039, whose new file remembers where a screen was scrolled to. That file did nothing against a server started minutes earlier, though it had been served correctly when new.

The settings file `vite.config.ts` told the file watcher, the part that notices saved files, to ignore `**/AgentMonitoring/**`. That rule was meant for the project's data folder, so writes there would not disturb the running app. But the repository folder is itself named AgentMonitoring, and the pattern matches that name at any depth, so it matched every source file we have.

Think of it as a do-not-disturb note meant for one room, pinned to the front door of the whole building.

The rule now names one exact place: the data folder directly under the repository root, with forward slashes because the watcher expects them.

We checked against the running desktop app. One throwaway line added to that scroll-position file showed up in what the server handed out within 2 seconds, and vanished when we removed it, with no restart.

Edits are seen again, and the old intent survives: writes into the data folder still do not disturb the running app, which notices them by asking for changes itself. Left out here: the settings file the old rule also hid from the watcher. The record does not say whether any other rule uses the same any-depth pattern.

A rule that names a folder by name alone will one day match a folder you did not mean.
