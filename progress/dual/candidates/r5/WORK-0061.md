Agents already write `[[note-name]]` in the prose of their records — a note's short name inside
double square brackets. Our app printed those rows as dead text. In ElmwoodOnline, a live project,
one note maps the others, and every row of it, `[[unrealnetcore-queue]]` among them, sat unclickable.

Think of it as an address written correctly on an envelope that the post office never reads.

**What it does now.** The renderer, the part of the app that turns written text into what you see,
knows that spelling. Double brackets around 2 to 64 letters, digits or hyphens, none at either edge —
the exact shape a note name may take — become a chip: the same clickable label a record number like
WORK-0061 already becomes.

**What fooled us.** We could not simply ask whether the text opens with two brackets. `[[label](url)`
is an ordinary link whose visible label happens to start with a bracket, and that crude test would
have swallowed it, so the whole shape has to match.

The second surprise came from the real notes. Elsewhere the app strips the markup back to plain
characters, and our first version dropped the brackets on the way. In those notes a Korean
grammatical ending is written hard against the closing brackets — `unrealnetcore-queue]]의` — so
dropping them eats part of a word.

**How we know.** The same checks, run over ElmwoodOnline's real folder, passed 106, three of which
had failed mid-work when the brackets went missing. The sample-file run passed 443 checks, a new set
among them for brackets in prose and in table cells. Two more ran, one a screenshot showing those
rows as chips.

**What is different.** Those rows link now; existing record links are untouched. Left out here: two
documents now state the rule, a bare hyphenated name still never links, and no stored file changed.
The record names nothing left broken.

If people are already writing the address, the least you can do is read it.
