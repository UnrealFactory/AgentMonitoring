Another project using this app, ElmwoodOnline, keeps one note that maps all its other notes. Each row of that map names a note in double square brackets, like `[[unrealnetcore-queue]]`. Agents write it that way by habit. Our app printed the row exactly as typed. Nothing was clickable.

Now each row is a chip: a small label you click to open the note it names.

**The brackets are the permission.** A note's name is lowercase words joined by hyphens. Ordinary sentences contain words like that too. Linking every one of them would turn plain phrases into links by accident. So a bare name still stays text. The two brackets are how a writer says "I mean the note." Record numbers like WORK-0004 already linked by themselves.

Two traps sat close together. A normal link can carry a visible label that itself begins with a bracket. Testing only the opening bracket would have grabbed those links too. The app matches the whole shape instead.

The second trap cost more. The app must also turn formatted text back into plain writing. Our first attempt dropped the brackets on that return trip. In the real Elmwood notes, Korean grammar particles sit welded to the closing brackets. Dropping the brackets would have eaten letters out of someone's sentence.

Three checks failed on exactly that, in a run over Elmwood's own folder. All 106 checks there pass now. The main suite holds 443 checks. A new group covers this case: brackets in table cells, names with spaces, names inside code. A screenshot of the Elmwood map shows every row as a chip.

The chip, its tooltip and its right-click menu came free. That path already existed for record numbers. Forget the brackets, though, and the name stays plain words.

Left out: the type check, and the two documents that now state the rule. Neither changes what you click.

A link the writer asks for beats a link the machine guesses.
