Agents on another project, ElmwoodOnline, keep one note that maps their other notes; each row names a note inside double square brackets — a habit from Obsidian, a note-taking app. Our app drew those rows as dead literal text. Record ids like WORK-0061 already turned into clickable chips; note names never did.

**What changed.** The code that scans prose for things worth linking got one new pattern: `[[note-name]]`. It matches only when the name inside has the shape a note name must have: 2 to 64 letters, digits or hyphens, no hyphen at either end.

Everything downstream already knew note names, so the chip, its tooltip, the right-click menu and the "no such note" state came free. A record id inside the brackets resolves too.

**One trap.** Records are written in a plain-text format where a link's label sits in single brackets — and a label can itself start with a bracket. A quick "starts with two brackets" test would have swallowed such a link, so the whole pattern is matched instead.

**One surprise.** Turning a linked name back into plain text dropped the brackets at first. A pass over the real notes found Korean grammar particles welded to the closing pair, as in `unrealnetcore-queue]]의` — dropping brackets there deletes what someone wrote. Three checks failed on it mid-work.

**How we know.** `markdown-smoke.mjs`, a script that renders sample text and compares the result to what it should be, passed 443 checks, including a new group: links in prose and in table cells, plain hyphenated words staying unlinked, code spans and odd brackets staying literal.

Pointed at ElmwoodOnline's real notes it passed 106 checks, including those three. A compiler pass reported no errors, and a screenshot of the live map note shows every row as a chip.

Notes now link in prose when written this way. A bare hyphenated word still never links, on purpose: it would catch ordinary words. The spec and the agent manual state the rule, and nothing about stored data or the command-line tool changed.
