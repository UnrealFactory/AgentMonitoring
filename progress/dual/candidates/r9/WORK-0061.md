In another project's notes — ElmwoodOnline's UnrealNetCore — one note is a map of all the others. Its rows read `[[unrealnetcore-mission-decisions]]`, `[[unrealnetcore-queue]]`: a note's name wrapped in double square brackets. On screen they appeared exactly like that, brackets and all, dead text nobody can click. In the same sentences a work id like `WORK-0004` already became a chip — a small badge you click to open that record.

**The double brackets as the signal.** The change sits in `src/lib/markdown-parse.ts`, the file that reads written text and decides which parts of it become links. It gained one new pattern: two brackets, a name, two brackets. The name must look like a note name — 2 to 64 letters, digits or hyphens, with no hyphen at either end. A match becomes the same kind of link a work id becomes. Everything downstream already knew what to do with a note's name: the chip, the hover title, the right-click menu, the message shown when no such note exists. None of it needed touching. `[[WORK-0004]]` resolves too.

It is like underlining a word on a form to mean "this is a name, go look it up". An underlined word gets looked up; a plain one stays a word.

**Two things fooled us.** First, `[[label](url)` is an ordinary link whose visible label happens to begin with a bracket. A quick test of "does this start with two brackets" would have swallowed it, so the full pattern does the matching instead. The second cost more. One part of the app turns a parsed line back into plain writing, and the first attempt dropped the brackets on the way. Real notes weld Korean grammar straight onto the closing brackets — `unrealnetcore-queue]]의`. Drop the brackets there and the writer's own words come back altered. Three checks over the real ElmwoodOnline notes failed on exactly that, mid-work.

**443 checks.** `node scripts/markdown-smoke.mjs` is the script that pushes prepared scraps of writing through that same reader and compares each result with the answer we wrote down. It passes all 443. The seventeenth group of checks is new, and is the one that would have caught this: a bracketed name in a sentence and inside a table cell, a bare hyphenated word staying plain, names with spaces and code samples staying literal, `[[label](url)` staying a link, and the trip back to plain writing keeping its brackets. Pointed at the real ElmwoodOnline notes folder, the same script passes 106 checks, the three earlier failures among them. A screenshot, `progress/shots-wikilink/note-detail-full.png`, shows that live map note: every bracketed row is a chip now, in prose and in table cells, work-id chips unchanged.

**What a bare name still does.** Nothing, on purpose. Write a note's name without the brackets and it stays plain text, because ordinary hyphenated words in a sentence would otherwise sprout links to nothing. The brackets are how a writer says they meant it. How notes are stored did not change, nor did the command-line tool — this is only what you see. The rule is now written into the project's specification and the manual agents read: ids link, `[[note-name]]` links, bare hyphenated words never do.

When people already write something a certain way, the work is to read their spelling, not to hand them a new one.
