You edit one of the app's files and save it. The app in front of you does not change. Reload the page and you still get the old code. This is the preview copy you start with `npm run dev` or `npm run tauri:dev`, the two commands that run the app while you work on it. For two working sessions, anyone judging their work by what the preview showed was judging old code.

**The leftover server on `5173`.** Twice we blamed an old preview server still sitting on `5173`, the numbered door on this machine where the preview answers. Kill it, start it again, and it would be fine. It was not. A server seconds old was already stale for every file edited after it started. What broke the story was asking the running server for its own copy of one source file, using `curl`, the command that fetches an address and prints back what it gets. The day's edits were not in there.

**A name that matched too much.** Behind the preview is `vite`, the tool that rebuilds the app each time you save. It spots your saves through `chokidar`, its file-watching part. Its settings live in `vite.config.ts`. One setting there listed what the watcher should ignore, and it read `**/AgentMonitoring/**` — meaning a folder called AgentMonitoring, at any depth, and everything inside it. The target was our data folder: writing a record there should not restart your preview. But this repository sits at `C:/Code/AgentMonitoring`. The repository is itself a folder called AgentMonitoring. So the pattern swallowed the whole codebase. The watcher saw nothing. Whatever a file looked like when it was first asked for, it looked like that forever after. Vite could not see edits to its own settings file either, so it never restarted itself.

It is like asking a guard to ignore any room in the building called Rosewood, in a building called Rosewood. He ignores the building.

**Pinning the rule to one folder.** The setting now names one exact folder — the AgentMonitoring data folder at the root of this repository, and only that one — instead of a name that could match anywhere. The original intent survives: writing a record still does not restart your preview. The app goes on noticing new records by asking for them itself, over and over.

**The probe line.** With a preview server running, I added one throwaway line to `src/lib/useScrollRestoration.ts`, the file `WORK-0039` had just added for restoring your scroll position. The line was `export const __watchProbe = 1`, which does nothing except be visible. It showed up in the server's copy of that file within two seconds. I deleted it, asked again, and it was gone. Nothing was restarted in between. A watcher still ignoring the codebase could not have shown either change.

**By hand, once.** Saving a file and seeing the app change works again. That proof was a live check I ran with my own hands; nothing runs on its own to catch this ignore rule going wrong a second time. If it does go wrong, it will look exactly as it did before — like a leftover server.

Before you tell a machine to ignore everything by a certain name, check that you are not standing in it.
