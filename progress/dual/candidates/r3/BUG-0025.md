Editing the app's screen code while it ran in development changed nothing on screen: no live update, and a full reload still served the old version. Two work sessions lost time to it before the cause surfaced.

**The rule that caused it.** The development server, which rebuilds the app as you work, reads a setup file, `vite.config.ts`. It told the file watcher, the part that notices when you save, to ignore anything inside a folder named AgentMonitoring, so the project's own record files would not jog it. The project's top folder is itself named AgentMonitoring.

Think of it as a note telling the cleaner to skip the Smith room, in a house that is the Smith house.

**So nothing was watched.** Every source file sits under that name, so nothing was ever marked as changed: the server kept serving the copy it made when each file was first requested — setup file included, so it never restarted itself.

Both sessions blamed a stale leftover server on port `5173`, and it kept looking right: a fresh server serves everything as it stands that second, so restarting appears to cure it — the freeze bites only the next edit. A new file misled us the same way: a scrolling helper from earlier work arrived correctly on first request, while edits to already-served files stayed frozen.

The setup file now names that one folder by its full path from the top of the project, in place of `**/AgentMonitoring/**`.

**How we know.** On a running desktop session we added a throwaway line to that scrolling helper: it reached the served app within two seconds and vanished when we removed it — both directions, no restart.

The rule still does its job: record files do not shake the running app, which spots them by checking on a timer. The checking is thinner — a probe run by hand, no automatic test in the record, so a future edit to that rule would fail just as quietly.

A pattern that matches by name matches every folder with that name, including the one you are standing in.
