For two work sessions, editing the app's screens changed nothing in the running app, and the cause was one line of setup that told the file-watcher to ignore the entire repository.

While you work on the app, a tool called vite runs a local server — that is what `npm run dev` and `npm run tauri:dev` start. Normally it watches the source files, and the moment you save one, the app updates. That was dead. Not only the fast live update: even a full page reload handed back the old code. Vite converts each source file into browser-ready code once and keeps that copy, throwing it away only when the watcher reports a change. The watcher reported nothing, so every file stayed frozen at whatever it was when the server started.

The wrong explanation cost the most time. Twice it was written off as a stale leftover server on port 5173 — kill it, start again, done. That looks right for a minute, because a fresh server does pick up everything edited before it started. Anything edited afterwards was stale again at once, on a server seconds old. What finally exposed it: a new hook file from WORK-0039, `src/lib/useScrollRestoration.ts`, was completely inert, yet it transformed fine the first time it was requested — and asking the server for `/src/App.tsx` returned that file without the day's edits in it.

The real cause is a name collision. `vite.config.ts`, the app's setup file, asked the watcher to ignore `**/AgentMonitoring/**`, meaning "any folder named AgentMonitoring, at any depth", so that the app writing its own data would not trigger reloads. But this repository sits in a folder that is itself named AgentMonitoring (`C:/Code/AgentMonitoring`). Every path in the project is under that name — `src/`, `scripts/`, the config file too. Vite could not even see edits to its own config, so it never restarted itself either.

The fix pins the rule to one real folder: the full path to the data folder at the repo root, written with forward slashes because that is what the watcher expects, instead of the any-depth wildcard.

To check it, with a desktop dev server running, one line was appended to that scroll hook — `export const __watchProbe = 1`. It showed up in the served code within 2 seconds, and disappeared again when the line was removed. Both directions, no restart.

Edits now reach the app again. Data writes still cause no reloads; the app keeps noticing new data by polling the server. The honest limit: this was checked by hand on a live server. No automated test guards it, so if the pattern breaks again, nothing will warn you.
