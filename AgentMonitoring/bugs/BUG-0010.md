## Report

The four filter menus on the bug board print counts taken from the whole project, while the
severity chips 40px below them print counts scoped to the current view. Same filter, two
controls, a different number for every value, both on screen at once — and the menu's number
is the one that is wrong.

Reproduce on the relay project (`npm run dev`, then /p/relay/bugs, the default view — no
filters set, Open tab, 2 rows):

1. Open **All severities**. It offers Critical 2 · High 4 · Medium 2 · Low 0.
2. Look at the chip row directly under the toolbar: Critical 0 · High 1 · Medium 1 · Low 0.
3. Choose Critical, which the menu just valued at 2. The board lands on "No bugs match these
   filters".
4. Open **All reporters**: nova 1 · patch 1 · quill 2 · sable 4 — the eight bugs of the whole
   project, offered on a tab holding two. Choosing sable gives 1 row, not 4.
5. **All assignees** and **All labels** do the same. Choosing nova promises 4 and gives 1.

The work list has it too: on In progress (2 rows), All agents offers nova 4 · patch 3 ·
quill 2 · sable 3, and picking nova gives 1 row.

Expected: the number a control offers is the number of rows you get after choosing it —
every other filter still applied. That is the rule the severity chips already follow and the
rule this file's own comment states: "a count shown *on* a control must not be filtered by
that control". GitHub's issue filters put no counts in the Labels/Assignees/Author menus at
all; Linear scopes them to the view. Printing the project total is neither.

Actual: `hint: bugs.filter((b) => b.severity === s).length` and its three siblings ignore the
tab, the search box and each other. This is BUG-0005 again — fixed for the tabs in that
round, and skipped for the menus.

Source: `src/pages/BugsPage.tsx`, the four `Select` blocks in the toolbar;
`src/pages/WorkListPage.tsx`, the agent and tag `Select`s.

Severity is medium rather than low because it is on the default view of the board with no
filters set, both numbers are visible at once, and the reader who trusts the bigger, bolder
one is taken to an empty screen.

## Resolution

Fixed. Every count on both triage screens is now a facet count: how many rows choosing that
control would leave, with every other filter still applied.

**The fix.** `matches(record, skip)` on `BugsPage` and `WorkListPage` already knew how to
leave one dimension out of the predicate — it just did not know all of them. It does now
(`tab | severity | label | assignee | reporter` on the board, `status | agent | tag` on the
work list), and one helper states the rule:

    const facet = (dim, has) => bugs.filter((b) => has(b) && matches(b, dim)).length;

Every menu hint goes through it, so the six menus, the four severity chips and the tab
counts are one rule with one implementation instead of two that happened to disagree.

The severity chips and the severity menu now render the same `severityCounts` array rather
than two expressions that have to be kept in step by hand. That is the part that matters
beyond this round: the drift the critic caught is no longer a thing that can be reintroduced
in one of the two places.

**What the reader sees.** On relay's default view (Open tab, 2 rows) the severity menu reads
Critical 0 · High 1 · Medium 1 · Low 0 — the chip row underneath, exactly. `All reporters`
reads nova 0 · patch 0 · quill 1 · sable 1, which sums to the two rows on screen instead of
the project's eight. On the work list's In progress tab, `All agents` reads nova 1 · patch 0
· quill 0 · sable 1, and choosing nova gives the one row it promised.

Options with nothing behind them keep their place and are dimmed. Dropping them would make
the menu jump under the cursor as filters change, and `cdn 0` is a more useful answer than a
missing line; the dimming is skipped for the current choice and the hovered row, which have
to stay legible.

**Verified**, and this is the part the last three rounds of this defect lacked:
`scripts/check-counts.mjs` (`npm run check:counts`) drives the real app and holds every
control to its number. For each project, on both screens, in four filter states — default,
the dense All view, one with another filter already narrowing the board, one with a search
query — it reads the number printed on every tab, every severity chip and every menu option,
clicks it, counts the rows, and fails if they differ; then it puts the control back the way a
reader would and checks the view returned to where it started. It also asserts that the
severity numbers printed twice on the board agree, and that "N matches" equals the rows
beneath it. 594 counts across the two projects, all honest.

The gate fails on this defect rather than sleeping through it: reverting one hint to
`bugs.filter((b) => b.reporter === r).length` produces 11 mismatches on relay alone, in the
critic's own numbers —

    MISMATCH /p/relay/bugs · reporter=sable
             the control offers 4; choosing it gives 1 row(s)

— and reverting the revert makes it clean again.

`npm run build`, `npm run smoke` (95 checks), `npm run check:clipping` (329 loads, 0 findings
on gated screens), `npm run check:urlstate` (14 checks) and `cargo test --workspace`
(74 tests) are all green on the same tree.
