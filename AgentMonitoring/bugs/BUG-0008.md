## Report

The bug board and the work list keep their tab, filters and search box in React state, so
the view exists only for as long as the component does. Press Back out of a record and the
board you spent four clicks building is gone; copy the address bar and you send somebody
the default view.

Reported by both P3 design critics ("filter/tab/search state must live in the URL, so
Back and deep-links work like GitHub triage").

Reproduce (`npm run dev`):

1. Open `/p/relay/bugs`.
2. Click the **All** tab, click the **Critical** severity chip, type `postgres` in search.
   Two rows are left. The address bar still reads `/p/relay/bugs`.
3. Click a row to open the bug, read it, press Back.
4. The board is on the Open tab, no severity, empty search — three of the four clicks
   undone. The two rows you were comparing are not on screen.
5. Copy the URL at step 2 into a new window: you get the default board, not the view you
   were looking at.

Expected: the view is addressable. Back returns to the board as it was left, a reload keeps
it, and the URL can be pasted to another person or into a bug report — the behaviour of
every issue tracker these screens are measured against.

Actual: the URL never changes, so there is nothing to return to and nothing to paste.

Notes for whoever picks this up:

- the tab belongs in the URL too, not just the filters: "which half of the board" is the
  first thing a reader chooses and the first thing they lose;
- filters must *replace* the history entry rather than push one, or a search box buries the
  previous screen under one entry per keystroke and Back becomes useless in a different way;
- defaults should stay out of the query string, so an untouched board is `/p/relay/bugs`
  and not `?tab=open&severity=all&label=all&assignee=all&reporter=all&q=`;
- a value the app does not recognise (`?tab=banana`, or a filter from a later build) must
  fall back to the default rather than filtering the board down to nothing.

## Resolution

**Root cause.** Both screens held their view in `useState`: `tab`, `severity`, `label`,
`assignee`, `reporter`, `query` on the bug board and `status`, `agent`, `tag`, `query` on the
work list. That state is owned by the component, so it dies with it — React Router unmounts
the page on navigation, and Back mounts a new one with the defaults. The URL never carried
any of it, so there was nothing to restore and nothing to share.

**Fix.** A shared hook, `src/lib/useUrlFilters.ts`, and both pages now read their filters
from it:

- values come from `useSearchParams`, with a module-level `DEFAULTS` object per screen;
- anything at its default is deleted from the query string, so an untouched board is
  `/p/relay/bugs` and a filtered one is `/p/relay/bugs?tab=all&severity=critical&q=postgres`;
- every write is `{ replace: true }`, so typing in the search box updates the view without
  pushing a history entry per keystroke. Opening a record is the only push, which is what
  makes Back land on the board as it was left;
- enumerated filters declare their allowed values (`tab`, `severity`, `status`) and anything
  else in the URL is ignored rather than obeyed, so `?tab=banana` — or a filter name from a
  later build — shows the board instead of an empty screen;
- `reset(["tab"])` clears the filters in one write while keeping the half of the board you
  are looking at; two `setSearchParams` calls in one tick would both have read the same
  "before" and the second would have undone the first.

**Verified.** `npm run check:urlstate` is a new gate that drives the real screens with
Playwright — 14 checks, all passing:

- filtering the relay board to All + Critical + `pg_stat_activity` puts all three in the URL;
- opening BUG-0004 and pressing Back returns to that exact URL, with the same single row and
  the query still in the search box;
- pasting that URL into a window that has never seen the app reproduces the view, All tab
  selected;
- `?tab=banana&severity=urgent` renders the default board rather than nothing;
- the work list does the same: `?status=done&q=sqlx`, open a record, Back, same rows.

**Cost.** The query string is now part of the app's surface: renaming a filter parameter
breaks links that people have already saved, in exactly the way renaming a route would.

## For humans

Narrow the bug board — the All tab, then Critical, then type `postgres` — and two bugs are left. Open one, read it, press Back: the board is back at its starting state, Open tab, no severity, empty search box, your two rows gone. Copy the web address at that point and send it, and the other person gets the plain board. Both design reviewers that round asked for this.

**The screen remembered your clicks and the address did not.** Those choices lived in `useState`, which holds a thing only while a page is on screen. The app throws a page away when you leave it and builds a fresh one with the standard settings. The address stayed `/p/relay/bugs` the whole time, so there was nothing to return to and nothing to paste.

It is like a form that empties itself the moment you look away.

**Every choice is written into the address now.** That same narrowed board reads `/p/relay/bugs?tab=all&severity=critical&q=postgres`, and the bug board and the work list read their tab, filters and search text back out of it through one shared piece of code. Back lands on the board as you left it, and a pasted address rebuilds it.

**Doing that plainly would have broken Back a different way.** If every change added a stop to your history, typing in the search box would add one stop per letter, and Back would walk you out one letter at a time. So each change rewrites the address in place instead, and opening a record is the only thing that adds a stop.

**A setting left alone stays out of the address**, so an untouched board is still that short one. A value the app does not know — `?tab=banana`, or a filter name from some later build — falls back to the ordinary board rather than a screen with nothing on it.

**Clearing your filters happens in one stroke, and leaves the half of the board you are on.** Dropping them one by one would not have worked: two changes made in the same instant each start from the address as it stood before, so the second undoes the first. So the clearing is a single rewrite that takes out every filter and keeps your tab where it is.

**`npm run check:urlstate` drives the real screens in a real browser, and all 14 of its checks pass.** It filters a board and confirms all three choices reach the address. It opens a bug, presses Back, and demands that exact address with the same single row and the search text still in the box. It pastes that address into a browser that has never opened the app, and it feeds in a nonsense value to see the ordinary board come back.

**The address is part of what we promise now.** Renaming one of those filter words later breaks links people have already saved, exactly as renaming a page's address would.

If you cannot paste it, you cannot show anybody what you were looking at.
