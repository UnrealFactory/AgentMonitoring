## Report

The CLI accepts a resolution (or an outcome, or a note) whose text contains `## ` headings,
writes it, and produces a record that is broken in three ways at once. It happened to
BUG-0014 in this vault twenty minutes ago.

Repro:

```
printf '## Root cause\n\nThe watcher fired on directory events.\n\n## Fix\n\nFilter them out.\n' > fix.md
agentmon bug resolve BUG-0014 -p agent-monitoring --agent me --resolution-file fix.md
```

Expected: either the headings land inside the resolution, or the command refuses and says
what to write instead.

Actual: exit 0, "Resolved BUG-0014", and the record on disk reads

```
## Resolution

## Root cause
...
## Fix
...
```

A `##` heading ends the section it appears in, so `## Resolution` is now empty and
`## Root cause` / `## Fix` / `## Verified` are siblings of it, not parts of it. Consequences:

1. `agentmon doctor` reports "status is resolved but there is no `## Resolution` section",
   i.e. a write the CLI accepted makes the vault fail its own integrity check.
2. The bug record page renders the Resolution as blank — the fix a reader came for is on the
   screen only as three unlabelled extra sections at the bottom.
3. `bug view --json` returns `resolution: null` with the text in `extraSections`, so anything
   scripting against the JSON contract sees an unresolved-looking record.

The same hole exists for `work done --outcome` and for `work update` / `bug comment`
messages: a `##` in a note ends `## Updates` and orphans every note written after it.

The rule the writer already relies on is invisible in the manual: labels inside a resolution
are written as `**Root cause.**` (bold lead-ins), which is also what the app promotes into
anchored sub-sections with a contents rail.

## Resolution

**Root cause.** `validate::resolution` / `validate::outcome` / `validate::note` checked that the
text was long enough and not a placeholder, and nothing else. Every one of those bodies is written
*inside* a section of the record — `## Resolution`, `## Outcome`, a `### <timestamp>` under
`## Updates` — so a `##` heading in the text does not nest, it terminates. The writer had no
reason to look at the text's own structure, and the section model made that a silent corruption
rather than a merge conflict.

**Fix**, in `crates/agentmon-core/src/validate.rs`: a new `reject_section_headings()` runs on all
four bodies (outcome, resolution, work-update note, bug comment) after the existing unwrap step,
using the fence-aware `body::sections` parser so a `##` inside a fenced code block is still just
code. It lists the offending headings by name and says what to write instead — `**Root cause.**`,
the bold lead-in style every record in this vault already uses and the one the app promotes into
an anchored sub-section, or `###`, which nests. `## Resolution` as the *whole* body still passes:
that is unwrapped first, and passing the same file to `--resolution-file` twice has always been
allowed.

**Verified.** Three new tests in `validate.rs` cover the shape that broke BUG-0014 (rejected, with
both heading names and the suggested style in the message), the two shapes that must keep working
(bold lead-ins, `###`) and the unwrap case; the same guard is asserted for `outcome` and for a
note. `cargo test` is green across the workspace (32 core unit tests, 75 in total). The record
this bug came from was repaired by hand — only its heading syntax, `## Root cause` to
`**Root cause.**`, no word of its content changed — and `agentmon doctor` now reports
"No problems found" over all 47 records. The manual gained the rule in the `bug resolve` section.
