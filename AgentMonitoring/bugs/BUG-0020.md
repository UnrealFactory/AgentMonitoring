## Report

**Steps.** In the shipped desktop window (WebView2, Windows 11), put the keyboard focus on
any row that has a context menu — a work row, a bug row, a project row in the sidebar — and
press the Menu key: VK_APPS, the one beside the right Ctrl. Same in browser mode with
Playwright's `keyboard.press("ContextMenu")`.

**Expected.** The row's menu opens and stays open, with the keyboard on its first item. That
is what `src/components/ContextMenu.tsx` claims in its own header: "It is invoked by pointer
(onContextMenu) and by keyboard (Shift+F10, or the Menu key beside the right Ctrl)".

**Actual.** Nothing. The menu appears and vanishes inside one frame, so the key looks dead.

**Cause**, traced with a MutationObserver plus a capture-phase listener on the running app:

```
t+0ms  keydown  key="ContextMenu"        -> the row's handler opens the menu
t+0ms  MENU IN DOM                        -> first item takes the keyboard
t+3ms  contextmenu  target=button.ctx-item  button=-1  detail=0
t+4ms  MENU GONE
```

Chromium answers VK_APPS with a keydown **and** a synthesized `contextmenu` event on
whatever has the focus; `preventDefault()` on the keydown does not suppress it. By the time
it arrives the menu is mounted and holds the focus, so the event targets `.ctx-item` inside
`.ctx-layer`, and the layer's `onContextMenu` — whose job is to dismiss the menu when the
reader right-clicks elsewhere — closes it. Shift+F10 sends no such echo, which is why it
always worked and why `scripts/check-keys.mjs`, which pressed Shift+F10 and never pressed
ContextMenu, did not catch this.

**Scope.** Every row in the app, in both the desktop build and browser mode. Pointer
right-click and Shift+F10 are unaffected. No browser menu ever appears — the echo is
suppressed either way, so this is a dead key rather than a leak.

## Resolution

Fixed in `src/components/ContextMenu.tsx`: the echo is consumed once rather than acted on.

The keyboard opener (`useContextMenu`'s `onKeyDown`) now calls `expectKeyEcho()`, which opens
a one-second window. `takeKeyEcho(e)` answers true for the first `contextmenu` event inside
that window whose `button` is not 2 — a right-click is always 2, Chromium's synthesized one
is -1 — and resets the window as it does. Three handlers ask it before acting:

* the layer's dismiss, which returns instead of closing;
* the row's opener, which returns instead of stacking a second menu;
* the document-level suppressor, which would otherwise have offered a "Copy" menu about any
  selected prose sitting behind the first.

All three still call `preventDefault()`, so no Edge menu appears on any path. Because the
window is *consumed* rather than merely timed out, a second Menu key press falls through to
the layer's dismiss and closes the menu — which is what the key does everywhere else on the
desktop.

**Verified in the real WebView2 window** (release build of the desktop app, Windows 11,
driven with `scripts/win-window.ps1 -Action menukey`, which sends VK_APPS via `keybd_event`
because SendKeys has no token for it — added in this round for exactly this check). On the
dashboard with a record row focused: one press opens Open / Copy id WORK-0021 / Copy title /
Copy link /p/agent-monitoring/work/WORK-0021, anchored under the row's leading edge with the
first item highlighted; a second press closes it and the focus ring is visibly back on the
row. Screen grabs at each step.

**In browser mode**, the same trace that recorded the defect now reads: keydown at t+14,
MENU IN DOM at t+14, `contextmenu target=button.ctx-item button=-1` at t+17 with
`defaultPrevented: true`, and the menu still on screen. `scripts/check-keys.mjs` presses the
key now — five new checks: it opens, it survives the echo, the echo is suppressed rather than
shown, the keyboard is on the first item, and a second press closes it. Gate clean at 113
checks (88 before this round).

## For humans

There is a key on Windows keyboards beside the right Ctrl that means "show me the menu for whatever I am on". Windows calls it `VK_APPS`. In our desktop app it looked dead: put the keyboard on a row, press it, nothing. The app's own menu code says in its opening lines that this key opens the row's menu.

**Windows sends that key twice, in two shapes.** I had the running app report every step: the menu opened, then closed itself four thousandths of a second later. The key press comes first and the row opens the menu on it. Three thousandths of a second later the system sends a `contextmenu` message, the kind a right-click sends, aimed at whatever holds the keyboard — which by then is the menu itself.

**The menu closed itself on that message.** It has a standing rule: a right-click on me means the reader clicked elsewhere, so close.

It is like an echo in a hall. You call out once, the room calls back, and you answer the echo as though somebody else had spoken.

**The other way in never echoes, which is why this stayed hidden.** Shift+F10 opens the same menu and sends no second message, so it always worked. And `scripts/check-keys.mjs`, the script that drives the app and presses keys the way a person would, pressed only that one.

**The app now expects the echo and swallows it.** When the key opens a menu, a one-second window opens with it, and the first right-click-shaped message inside that window that did not come from a real mouse is taken and goes no further. A real right-click carries the button number 2; the system's imitation carries -1.

**I pressed the key in the real desktop window and photographed each step.** The usual way of typing into a window has no name for this key, so `scripts/win-window.ps1 -Action menukey` sent the raw signal instead. One press opened a record's four-item menu under the row, first item highlighted. A second press closed it — the taken message uses that one-second window up — and the row had the keyboard again.

**The keys script presses this key now.** Five new checks: the menu opens, it survives the echo, the echo is refused rather than shown as a browser menu, the keyboard lands on the first item, and a second press closes it. That script went from 88 checks to 113, all clean.

**The mouse and Shift+F10 were never affected, and no browser menu ever appeared: a dead key, not a leak.**

A key nobody presses in the check is a key nobody has tested.
