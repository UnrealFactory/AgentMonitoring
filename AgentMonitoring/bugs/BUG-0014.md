## Report

A cold `npm run check:live` (and any other browser-driven gate) can load a blank app: three
`Cannot read properties of null (reading 'useState')` page errors, then a 30s timeout waiting
for `.page-title`.

Repro (reliable):

1. `npm run build` — this leaves Vite's dev dependency cache invalidated.
2. `rm -rf node_modules/.vite` has the same effect, and so does a fresh clone.
3. Run any tool that boots the dev server and immediately drives a browser:
   `npm run check:live`, `npm run screenshot`, `npm run check:clipping`.

Expected: the app renders.
Actual: with `DEBUG_SERVER=1` the dev server prints

```
[vite] ✨ new dependencies optimized: react-dom/client, @tauri-apps/api/window, @tauri-apps/api/core, @tauri-apps/api/event
[vite] ✨ optimized dependencies changed. reloading
```

Vite scans for dependencies on the first request and re-bundles when it finds new ones. If a
Playwright page arrives inside that window it loads modules from two different bundles — two
copies of React — and every hook call dies on a null dispatcher. It is not an app bug, and
that is what makes it expensive: it looks exactly like one.

Two things make it likely in this repo: the Tauri modules are behind `import()` inside an
`isTauri()` check, so they are only discovered when a page actually runs that branch, and the
gates start a server and open a browser within the same second.

## Resolution

**Root cause.** Vite discovers dependencies lazily, on the first module request, and pushes a full reload
when the scan finds any it has not pre-bundled. Two of ours are only reachable through
`import()` behind an `isTauri()` check (`@tauri-apps/api/*`), so the scan finds them on the
first page load rather than at server start. A browser that navigates during that window
loads part of the graph from the pre-bundle and part from the new one, ends up with two React
instances, and dies on the first hook.

**Fix**, two changes, one for each half of the race:

* `vite.config.ts` names the three Tauri entry points in `optimizeDeps.include`, so they are
  bundled at server start instead of discovered mid-session.
* `scripts/dev-server.mjs` gained `warmOptimizer()`, called from `waitForServer()` and from
  the reuse branch of `ensureServer()`, so every tool that drives a browser goes through it:
  it requests `/` and `/src/main.tsx` (which is what starts the scan) and then waits for
  `node_modules/.vite/deps/_metadata.json` to list react, react-dom/client, react-router-dom
  and @tauri-apps/api/window before returning. The browser is only opened once the optimizer
  has committed.

**Verified.** `rm -rf node_modules/.vite && npm run screenshot` — before the fix this produced
"page error: Cannot read properties of null (reading 'useRef')" and a 30s selector timeout;
after it, three screens shot clean on the first attempt. `npm run check:live` on a cold cache
is green (14 checks), and the full gate set — smoke, check:clipping, check:urlstate,
check:counts, check:live — runs green back to back without deleting anything between runs.

## For humans

On a fresh copy of this project, a check that opens the app in a browser can find nothing there. The page is blank. Three errors come back, all the same — "Cannot read properties of null (reading 'useState')" — and then the check waits thirty seconds for the page's title and gives up.

**It looks exactly like the app is broken, and the app is fine.** That is what makes it expensive. Anyone reading that error goes hunting through the code behind the screens, where there is nothing wrong.

**The server hands out two copies of the same toolkit.** While we work on the app, Vite serves it and packages the outside code it needs. It does not know the whole list in advance. It looks on the first request, finds pieces it has not packaged, packages them, and tells the page to load again.

A browser arriving inside that gap takes some pieces from the old package and some from the new. Two copies of React — the outside toolkit the screens are built from — are then loaded at once. The screens call into their copy, the call comes back empty, and the page stays blank. It is like two identical toolboxes on one worksite: you put the hammer back in one and reach into the other.

**Three of the pieces are only met late.** They load only when the app runs as a desktop program, so the packager does not see them until a page goes down that path. And these checks start the server and open a browser inside the same second.

**The fix closes both halves of that race.** `vite.config.ts`, the server's settings file, now lists those three desktop pieces up front, so they are packaged before the server takes a single request. And `scripts/dev-server.mjs`, the script every one of these tools uses to start the server, gained a step called `warmOptimizer()`: it asks for the page itself, then waits until the packager's own list names the four pieces that must be there. Only then may a browser open.

**Proof: throw the packages away and run it again.** `npm run screenshot`, which opens screens and saves pictures of them, used to fail there with that same empty-answer error and a thirty-second wait; afterwards it shot three screens clean on the first attempt. `npm run check:live`, which drives a real browser over the running app, passes all 14 of its checks from a cold start.

**What this buys is trust in the checks.** Nobody using the finished app ever met this; it hit the people running the checks.

A check that fails for its own reasons teaches you to ignore it.
