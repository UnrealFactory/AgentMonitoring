## Report

**Steps.** Open the app on its default route, `/p/agent-monitoring` (the dashboard).
Right-click the hero row under WORKING RIGHT NOW, the row under UNRESOLVED BUGS, or any row
of the activity feed. Then right-click the card at the top of the sidebar that names the
current project.

**Expected.** The same menu the identical row opens on `/work` and `/bugs`: Open, Copy id,
Copy title, Copy link for a record; Open, Work, Bugs, Copy slug, Archive for a project.

**Actual.** Nothing at all. The browser menu is correctly suppressed everywhere — that part
of WORK-0021 holds — but no app menu appears either, so the right button is silent on the
two surfaces a reader meets before any list. The small duplicate of the same project 300px
below the switcher card, in the vault list, opens the full project menu; the card naming
that same project does not.

**Where it is.** `src/pages/DashboardPage.tsx` was the only screen file that never imported
`useContextMenu`. `src/components/Sidebar.tsx` spread the handlers onto the rows inside the
switcher's dropdown and onto the vault list, never onto the `.switcher-button` itself.
`src/components/Related.tsx` — the cross-reference block on both record pages, whose rows
are records — had none either.

**Why it counts as a defect and not a missing feature.** The dashboard is the route the app
lands on, so its rows are the first rows anybody right-clicks, and the component's own
promise is that the right button belongs to the app. A menu that is present on one copy of a
row and absent on another, more prominent copy of the same row reads as broken rather than
as restraint. The rule the code states — "a menu is only offered where there is something to
do" — was being kept by accident here: these rows have exactly as much to do as the ones
that answered.

## Resolution

Fixed. The right button now answers on every surface that draws a record or a project.

**Dashboard** (`src/pages/DashboardPage.tsx`, which now imports `useContextMenu`): the
working-right-now rows, the last-finished row, the unresolved-bug row and every linked row
of the activity feed open the shared record menu, built by the same `useRecordMenu` the work
list and the bug board use. The feed knows only an id, so the page indexes the work logs and
bugs it has already loaded by id and hands that map down — Copy title on a feed row copies
the record's real title, which the line itself never prints, and nothing extra is fetched. On
the in-progress rows the handlers sit on the `<li>`, not the `<a>`, because the row and the
note quoted under it share one hover surface and read as one row about one work log. Feed
lines about the project itself link nowhere and still offer nothing.

**Switcher card** (`src/components/Sidebar.tsx`): one spread on `.switcher-button`, guarded
so that off a project — where the card says "All projects" — there is no menu and the
browser's stays suppressed. Right-clicking the card does not also drop its dropdown open.

**Related block** (`src/components/Related.tsx`): its rows are other records, so they carry
the record menu with Open included.

Nothing else changed about the rule: charts, the agent table, the range tabs and empty
background still open nothing at all, and text inputs still keep the native menu for
paste/undo/spellcheck.

**Verified in the real WebView2 window** (release desktop build, Windows 11): a right-click
at client 110,88 — the exact coordinate reported as dead — opens Open/Dashboard, Work/21 work
logs, Bugs/1 unresolved, Copy slug/agent-monitoring, Archive/records are kept, and no Edge
menu; the dashboard hero row at 560,249 opens the record menu; empty background at 700,620
opens nothing.

**In browser mode**, `scripts/check-keys.mjs` gained checks that name the id each menu claims
to be about, so a menu opening on the wrong record fails: the hero row, a feed row and the
unresolved-bug row (whose Copy link is asserted to be the bug's route, not the dashboard's),
Copy title on a feed row read back from the clipboard and compared with the vault's own
title, a chart on the same screen opening nothing with the contextmenu still
`defaultPrevented`, the switcher card on a project and off one, and a Related row. Gate clean
at 113 checks (88 before). `npm run build` clean, smoke 317, check:clipping 483 loads clean,
check:urlstate 30. Screenshots `progress/shots/menu-dashboard.png` and `menu-switcher.png`,
shot at 1600 and read again at 960.

## For humans

The app opens on a project's dashboard, `/p/agent-monitoring`. Right-click the row for the work somebody is doing right now, or a line in the list of recent activity: nothing happened. Same for the card at the top of the sidebar naming your project. One screen away, on the lists of work and of bugs, the identical row offered four choices.

**The sidebar disagreed with itself.** The same project appears again just below that card, in the list of all projects, and that smaller copy opened the full menu. The card itself opened none.

It is like a shop where the bell works on the side door and not on the front one.

**What came back was silence, not the browser's menu.** The app draws its screens inside a browser, and the right button had already been taken from that browser everywhere, so these rows gave nothing at all. These are the first rows anybody right-clicks. The code's rule is that a menu is offered where there is something to do, and these rows have as much to do as the ones that answered.

**The dashboard was the only screen file that never took in the shared menu opener.** In `src/components/Sidebar.tsx` the menus had gone onto the rows inside the project drop-down and onto the list of all projects, never onto the card itself, and the block of cross-references on every record page had none either.

**Now every row naming a record or a project opens the menu the lists use.** One wrinkle: a line in the activity list knows a record's id, not its title, so the screen looks it up among the records it has already loaded, and Copy title there copies the record's real title — which the line itself never prints.

**I right-clicked the exact spot the report called dead.** In the real desktop app, 110 across and 88 down: Open, Work with its 21 work logs, Bugs with its one unresolved, Copy slug, Archive. No browser menu behind it. The row for the work in progress gave the record menu.

**The checks now name the record each menu claims to be about.** `scripts/check-keys.mjs`, which drives the app the way a person would, went from 88 checks to 113: a menu opening for the wrong record fails, and Copy title is read back off the clipboard and compared with what is stored.

**Charts and the table of agents still open nothing, on purpose**, and boxes you type into keep the browser's own menu.

A menu that answers on one copy of a row and not on a more prominent copy reads as broken, not as restraint.
