## Report

`cargo test --workspace` failed once out of ~16 runs on this machine, in
`crates/agentmon-core/tests/write_roundtrip.rs`:

    running 21 tests
    test result: FAILED. 20 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.40s

**Which test it was is not known.** The run was piped through `tail -12`, so the summary
survived and the `failures:` block did not — that is the reporting lesson as much as the
defect one.

Repro attempts that did NOT reproduce it, all on the same tree, immediately afterwards:

* `cargo test --workspace` x 4 — 78/78 green every time (9 + 32 + 12 + 21 + 4);
* `cargo test --test write_roundtrip` x 6 sequentially — 21/21 green, 0.56-0.60s each;
* `cargo test --test write_roundtrip` x 4 concurrently (four cargo processes at once, to
  put the temp-dir writes under contention) — 21/21 green in all four.

The failing run was the first `cargo test` issued straight after `npm run check:clipping`
(413 browser page loads), so the machine was under heavy I/O load and the suite took 0.40s
where an idle run takes 0.57s — consistent with a timing- or filesystem-sensitive
assertion rather than a logic error. The suite includes
`concurrent_writers_never_share_an_id_or_lose_an_event`, which spawns real processes and is
the obvious suspect, but that is a guess and the record should not pretend otherwise.

Expected: a test suite that is green is green every time. A suite that fails one run in
sixteen trains everybody to re-run it, and the run where it means something gets re-run too.

Actual: one unexplained failure, unattributed.

Next step for whoever picks this up: run the suite in a loop under load and capture the
whole output, e.g.

    for i in $(seq 1 200); do cargo test --test write_roundtrip -- --test-threads=8 || break; done

with `RUST_BACKTRACE=1` and no `tail`, ideally while a `check:clipping` run is hammering the
disk. If it is the concurrency test, the fix is likely a longer wait or a retry on a
Windows sharing violation, not a change to the write path.

## Comments

### 2026-08-21T01:18:00Z — fable-notes-builder

Caught it with the whole output this time. A full-workspace run failed in write_roundtrip.rs on concurrent_writers_never_share_an_id_or_lose_an_event, and the failures: block survived: three worker threads panicked with Io { path: ".../.agentmon.lock", source: Os { code: 5, kind: PermissionDenied } }. So the suspect named in this report was the right one, and it is not timing: on Windows, create_new against a lock file that another holder's Drop is mid-deleting answers ACCESS_DENIED (delete-pending), not AlreadyExists, and ProjectLock::acquire only retried on AlreadyExists. Filing the root cause and fix under BUG-0024.

## Resolution

**Root cause.** The one-in-sixteen failure was `concurrent_writers_never_share_an_id_or_lose_an_event` hitting Windows' delete-pending state: `ProjectLock::acquire` (crates/agentmon-core/src/fsx.rs) treated the ACCESS_DENIED that `create_new` returns against a mid-deletion lock file as a fatal io_error instead of the AlreadyExists it means. Load made the release/acquire race more likely, which is why it surfaced right after a browser gate hammered the disk.

**Fix.** PermissionDenied on the lock file now takes the same wait-and-retry path as AlreadyExists, bounded by the same deadline — see BUG-0024, filed when the failure was finally caught with its `failures:` block intact (the reporting lesson this record asked for).

**Verified.** Three consecutive `cargo test --workspace` runs green, plus five back-to-back runs of the concurrent test alone; before the fix the full suite failed roughly one run in five on this machine once the notes suite added more lock traffic.

## For humans

`cargo test`, the command that runs this program's own automatic checks, reported 20 of 21 passed and one failed. Which one, nobody could say: the run had been piped through `tail -12`, which keeps only a command's last twelve lines. The tally survived; the list of failures did not. A suite that fails one run in sixteen teaches everybody to run it again — the run that means something included.

**It would not come back that day.** Four more full runs of everything: green. Then six runs of one test file, one after another, then four more runs of that file at once to make them fight over the disk. Green every time.

**The file was `crates/agentmon-core/tests/write_roundtrip.rs`**, which writes records and reads them back. Its failure came straight after `npm run check:clipping` — the check that opens the app's own pages in a browser looking for text cut off at an edge — had loaded 413 of them. The suite finished in 0.40 seconds where an idle run takes 0.57.

**One test in that file was the obvious suspect**: `concurrent_writers_never_share_an_id_or_lose_an_event`, which starts several writers at once and checks that no two hand out the same id and that nothing they write is lost. It went in as a suspect, not a finding.

**Two days later `fable-notes-builder` caught it with the whole output kept.** That agent found three of the test's writers dead on one file, `.agentmon.lock` — the marker a writer makes so the others wait their turn.

It is like a key that must be hung back on its hook before the next person can take it: for a moment it is neither on the hook nor in a hand.

**Windows gives an answer nobody was waiting for.** The way to take the marker is to make the file only if it is not there yet. Ask while the previous holder is halfway through handing it back and the answer is `PermissionDenied`, the refusal a program gets when it may not touch a file. Here it means `AlreadyExists`: someone has it, wait.

**The waiting code only knew the second answer.** The step that takes that marker before any write waited on `AlreadyExists` and gave up on the spot for anything else. A busy disk makes the hand-back and the next grab overlap more often.

**`PermissionDenied` now waits and tries again**, on the same clock as before. Three full runs of the suite are green, and five of the crowded test alone. By then it was no longer rare: once note-writing added traffic to that marker, the suite was failing about one run in five.

Never trim the output of a failing test.
