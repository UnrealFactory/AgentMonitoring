## Report

`loadDesktopLocale()` in `src/lib/i18n/index.ts` (lines 142-155) reads the saved language out of `settings.json` after boot and applies it unconditionally, with no check that the reader has chosen a language in the meantime. A press on the language toggle inside that await window is discarded, and the two places the choice is stored are left disagreeing.

The mechanism, read off the code:

1. The module picks a language synchronously at import: `fromUrl() ?? fromStorage() ?? DEFAULT_LOCALE` (line 96).
2. `loadDesktopLocale()` awaits `api.getLocale()`. The value it will use is read *before* the user can act.
3. The user presses the toggle during the await. `setLocale(next)` runs with `persist` defaulting to true, so `remember(next)` writes `localStorage` and `saveLocaleToDesktop(next)` writes `settings.json` (lines 109-118).
4. The await resolves with the stale value. `remember(saved)` overwrites `localStorage` back to it, and `setLocale(saved, { persist: false })` flips the UI back — but `persist: false` means `settings.json` is *not* rewritten, so it keeps the value from step 3.

The result is `localStorage` and `settings.json` holding different languages. The next window reads `localStorage` synchronously, opens in that language, then `loadDesktopLocale()` resolves and flips it to the other one — a window that visibly changes language a moment after it appears.

Provenance, checked and not assumed: `git show 072ad52:src/lib/i18n/index.ts` carries the same two unconditional lines, so this shipped in v1.0.5. None of the D1-D6 human-area pieces touched this file.

This is the **language** toggle, not the Agent/Human toggle. Filed rather than fixed because it is outside the human-area work and belongs to whoever owns i18n boot.

## Resolution

Fixed in `src/lib/i18n/index.ts` (WORK-0080, d11-i18n-race-builder); verified against the real
WebView2 window by d11-critic, round 1.

**Root cause, as reported.** `loadDesktopLocale()` applied what `api.getLocale()` returned with
no test of whether the reader had chosen since the module loaded, and applied it half-and-half:
`remember(saved)` rewrote localStorage while `setLocale(saved, { persist: false })` left
settings.json holding the discarded press, so the two stores split and the next window flipped.

**The fix.** The module counts accepted language changes since load — `choicesSinceLoad`, bumped
inside `setLocale` — and the boot read applies what it found only while that count is still 0,
read and applied in one synchronous step with no await between the test and the apply. The pair
cannot split either way: **applied** means nothing has written since load (`setLocale` is the only
writer of either store and bumps the count whenever it writes), so settings.json already holds
`saved` and mirroring it into localStorage is what makes them match; **stood down** means the
press that bumped the count went through `setLocale` with the default `persist: true`, which wrote
both stores on its way past. Counted rather than compared against a captured `current`, so a
reader who toggles away and back still counts as having chosen.

**How it was verified.** The report's own Steps, in the real desktop window: `npm run dev` on 5173
plus `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9223 target/debug/agentmonitoring.exe`,
driven by Playwright over CDP (note `verify-desktop-via-cdp`).

* The window itself was measured first: with the stores deliberately disagreeing and nobody
  pressing, the boot read landed at 656 ms (ko→en) and 778 ms (en→ko) warm, ~0.9-1.1 s with the
  webview cache disabled — the regime this report measured at 0.4-0.6 s.
* Presses at **100, 300, 600 and 2500 ms** after each boot, in both directions, cache disabled so
  every module is fetched fresh (what a just-launched app has). At every offset the pressed
  language stayed on screen and in the words (`Dashboard` / `대시보드`), and
  `localStorage['agentmon.locale']` and `locale` in
  `%APPDATA%\com.agentmonitoring.app\settings.json` — read off disk, not through the IPC — held
  the same language. The next boot opened directly in it: first painted content at 101 ms in the
  chosen language, no flip over the following 5 s.
* A full process relaunch after a choice made at 328 ms into a boot: attached at document age
  125 ms, English from first paint, unchanged for 6 s, both stores `en`.
* **Control, same harness, guard removed:** the fault reproduced live at every one of 100/300/600 ms
  — `197:en → 201:ko`, and `localStorage=ko settings.json=en`. That is what proves the presses land
  inside the race rather than after it.
* No-press paths: agreeing stores open with no flip; empty localStorage takes settings.json's value
  and mirrors it in, both stores agreeing after. A press at 2500 ms still persists to both stores.
  Browser mode on a sandbox port (5199): no `__TAURI_INTERNALS__`, the toggle works in both
  directions, survives reload, no console or page errors.
* The new gate genuinely encodes the race: `npm run check:locale` is 39 checks over 10 cases green;
  with the guard removed 7 go red, including the reported `localStorage=ko settings.json=en`, and it
  exits 1. Restored byte-identical afterwards.
* Gates: `npx tsc --noEmit`, `npm run build`, `check:locale`, `check-i18n` ko + en (246 screens each),
  `check-errors`, `markdown-smoke` (945 checks), `cargo test --workspace` (190 tests), `doctor --strict`.

**Left open, deliberately, and not this defect.** A press on the segment that is already lit is not
a change, so `setLocale` returns early and the count is not bumped. In a window whose localStorage
is empty or disagrees with settings.json, such a press does not stand the boot read down: measured
live, settings.json `en` with localStorage empty, 한국어 pressed at 324 ms, screen turned English at
463 ms. No store split and no flip in the window after, so this is the intended mirror, not
BUG-0026 — but a reader's press did not win, and whoever next touches this file should decide
whether a press should count as a choice even when it names the language already on screen.

## Steps

1. Open the desktop app (`npm run tauri:dev`).
2. Press the language toggle within roughly the first 0.4-0.6s of the window appearing, before `loadDesktopLocale()` resolves.
3. The language snaps back to the previous one.
4. Read `localStorage[agentmon.locale]` and the `locale` key in `settings.json`: they differ.
5. Open a new window. It starts in the `localStorage` language and then flips to the `settings.json` one.

The timing window was measured by the D6 desktop critic against the real window; the code path above is read directly from `src/lib/i18n/index.ts` at 072ad52 and at HEAD.

## Expected

A choice the reader has already made wins. `loadDesktopLocale()` should apply the saved value only if nothing has set the language since the module loaded — for example by capturing `current` (or a generation counter) before the await and skipping the apply if it changed. If it does apply, it should write both stores or neither, never one.

## For humans

Press the language button in the first half-second after a window opens and, until now, the press
was thrown away — the language snapped back. Worse, the two places the app remembers your choice
were left disagreeing, so the next window you opened started in one language and turned into the
other in front of you.

**The window now counts what the reader does while it waits.** As it opens it asks `settings.json`,
the file on this machine where the desktop app keeps the language you chose last time, and that
answer takes about seven tenths of a second to come back. Every language change made in the
meantime is counted. If the count is anything but zero when the answer lands, the answer is dropped
and your press stands. It is like a letter that arrives after you have already said the opposite in
person: it goes in the bin, not over your words.

**What fooled me first was a page that answered too quickly.** Pressing a tenth of a second in
changed nothing at all, because a window whose files were still in memory finished asking before my
press landed. Told to fetch every file fresh, which is what a just-started program does, the gap
opened up again and the press landed inside it.

**I pressed at three moments and read all three places.** In the real desktop app I pressed the
button 100, 300 and 600 thousandths of a second after each opening, in both languages, then read
the screen, the browser's own small store of settings, and the file on disk. All three agreed every
time, and the next window opened in the chosen language without changing. With the new guard taken
back out, the same script showed the old fault: English for four thousandths of a second, then
Korean again, and the two stores split. `npm run check:locale`, a new check that runs this race 39
times without a screen, goes red the same way.

**One corner is left.** Pressing the segment that is already lit is not a change, so it is not
counted. In the rare window that opens on a language the file disagrees with, that press does not
stop the file's answer landing. Both stores still agree afterwards, and no window flips.

A language you have already chosen is not overwritten by an older answer arriving late.
