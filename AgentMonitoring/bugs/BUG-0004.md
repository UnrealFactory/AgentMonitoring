## Report

The record renderer deletes a number that exists in the vault and prints one that does not.

Surfaced by the P2 comprehension critic (round P2/1, progress/rounds.jsonl) while reading
WORK-0010 in the relay project; I reproduced it in source and in a node harness before
touching anything.

The vault text, `vault/projects/relay/worklogs/WORK-0005.md` update 1, wraps like this:

    Setup: 4,300 pending deliveries for one endpoint, receiver returns 503 for three hours, then
    200. Without jitter, 4,300 deliveries came due inside the same 900ms window every step of
    the way, and the recovery burst was 4,300 requests in under a second

`parseBlocks` in `src/lib/markdown.tsx` ends an open paragraph at any line matching
`^\s*([-*+]|\d+[.)])\s`, so the second line starts an ordered list; the list block then
renders as a bare `<ol>` whose first item is numbered by the browser. On screen the reader
gets:

    Setup: 4,300 pending deliveries for one endpoint, receiver returns 503 for three hours, then
      1. Without jitter, 4,300 deliveries came due inside the same 900ms window …

Expected: `200.` is the tail of a wrapped sentence — the status the receiver returns after
recovery — and stays in the paragraph.

Actual: the literal `200` is deleted from the screen, a fabricated `1.` is printed in its
place, and one sentence is split across a paragraph, a list item and another paragraph.
The critic's reader recovered "503 for three hours then 200" only from a parenthetical in
the Outcome section, i.e. from a second copy that happened to exist.

CommonMark is explicit about this: a list may interrupt a paragraph only if it starts with
a non-blank item, and if ordered, only when the start number is 1. Any wrapped line
beginning with a number and a period is rewritten the same way today — `503.`, `2026.`,
any of them.

Two smaller defects in the same file, same root (the renderer treating markup as a regex
pass rather than a parse):

1. A list that legitimately starts at N renders as `<ol>` with no `start`, so the author's
   numbers are replaced by counted ones. A "3." in the source can print as "1.".
2. `inline()` matches `**…**` first and never re-parses its contents, so
   `**\`Retry-After\` is ignored.**` shows literal backticks around Retry-After (visible in
   WORK-0005's follow-ups), and a record id inside bold is not linked.

Severity high: this is a data-fidelity bug in the one screen whose whole purpose is to
show a record faithfully. Nothing warns the reader; the page looks correct and is wrong.

## Resolution

**Root cause.** `parseBlocks` decided "is this line a list?" with one regex,
`^\s*([-*+]|\d+[.)])\s`, used in two places: to start a block and to end an open
paragraph. The second use is the bug. CommonMark lets a bullet interrupt a paragraph but
lets an ordered item interrupt only when it starts at 1, precisely so that a wrapped
sentence ending in a number is not turned into a list. The renderer then emitted a bare
`<ol>`, so the browser numbered the items and the source number was gone from the page.

**Fix**, in the new `src/lib/markdown-parse.ts` (the parser, split out of
`src/lib/markdown.tsx` so it can be run without React):

1. `interruptsParagraph(line)` replaces the regex test in the paragraph loop: a bullet
   interrupts, an ordered item interrupts only at 1, an empty item never does.
2. `Block.list` carries `start`, taken from the author's own first marker. The renderer
   passes `start={N}` for anything other than 1, so a source number is never replaced by a
   counted one.
3. `parseInline` returns a tree instead of a flat list and recurses into `**bold**`,
   `*italic*` and link labels, with a depth cap. `code` inside bold is code, and a record
   id inside either is still a cross-reference link.
4. `markdown.tsx` keeps only the React mapping and gains `InlineMarkdown` and
   `recordPath`, which the bug pages and the Related block reuse.

**Verified.**

- `scripts/markdown-smoke.mjs` (new, `npm run smoke`): nine fixtures taken verbatim from
  vault records — this bug's sentence, a list that really starts at 3, the bold-with-code
  run from WORK-0005's follow-ups, an id inside a code span, an indented incident
  transcript, `locked_at`-style snake_case that must not become emphasis — plus a sweep of
  every record in ./vault that fails if any word of the source is missing from the render.
  55 checks pass; the sweep reads all 20 relay records and all 10 agent-monitoring ones.
- The smoke was checked for teeth rather than trusted: reverting rule 1 to "any number
  interrupts" fails two fixtures and prints the rendered text with the `200` missing.
  Restoring it passes again.
- `npm run build` (tsc --noEmit + vite) green, and the bug and work record pages were read
  as screenshots afterwards: WORK-0005's update 1 now renders as one paragraph containing
  "then 200. Without jitter", and BUG-0004's `**Fix**, in \`relay-worker/src/dispatcher.rs\``
  renders as bold with real code spans inside it.

**Not fixed, and deliberately.** Nested lists still flatten into sibling blocks — no vault
record uses them today (checked with a grep over ./vault for indented markers), and a real
nested-list parse is a larger rewrite than a data-fidelity fix should carry.

## For humans

`WORK-0005`, a work record in the relay project this app also tracked, described a receiving machine. It answered 503 for three hours, then 200, meaning it had recovered. On the page the 200 was gone, a "1." stood in its place, and one sentence had been broken into three.

**The P2 comprehension critic got the number back only by luck.** That reviewer reads a record cold and says whether a newcomer could follow it. The critic ran into this while reading `WORK-0010`, another work record of that project. The same phrase happened to sit a second time in a summing-up section, in brackets. That copy is where the 200 came back from.

**A sentence too long for one line had wrapped, and the next line began "200.".** `src/lib/markdown.tsx`, the file that turns a stored record into a page, cut that text into paragraphs and lists. It asked one test two questions. Does a numbered list start here, and does the paragraph I am in end here? That test said yes to any line opening with a dash, a star, a plus, or a number and a dot. "200." is one.

It is like a form where anything on a numbered line gets renumbered, so your "200" comes back as "1".

**CommonMark, the agreed standard for the marks writers put into plain text, forbids this**: a numbered list may cut into a running paragraph only when it starts at 1.

**I moved the reading apart from the drawing.** It now sits in its own file, which runs without the page around it. A new test there lets a dash cut in, and a number only at 1. A list the writer began at 3 keeps those numbers. And bold is read all the way through now, so a name marked as code inside bold no longer comes out wrapped in those marks.

**A record's number inside bold is a link again.** Written into a bold sentence it had arrived as plain text, pointing nowhere; it now opens that record, as it does anywhere else. The drawing file kept only the part that puts text on a screen, and the bug pages and the block of cross-references draw their text through that same file — so this repair reached all of them at once, which is why I took this bug rather than handing it back.

**`npm run smoke` is the check that would have caught this.** It draws nine passages copied word for word out of real records, this sentence among them. Then it reads every record of both projects the app held then, twenty in one and ten in the other. It fails if a word of a stored record is missing from the drawn page. All 55 checks pass.

**I made it fail on purpose before trusting it.** Putting the old behaviour back failed two of the nine passages and printed the drawn text with the 200 missing. Restoring the rule passed them again.

**Lists inside lists still come out flat.** No record uses one today; I looked through every one. Doing it properly is a bigger rebuild than this fix was.

The worst wrong page is the one that looks fine.
