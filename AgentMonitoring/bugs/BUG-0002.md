## Report

SPEC.md says: "Live updates: Tauri watches the vault (notify crate) and emits events → UI
refreshes." The Tauri shell does not do this yet, so the desktop app renders whatever the
vault contained when a screen was first opened.

Repro (desktop):

1. `npm run tauri:dev`, open the dashboard for `agent-monitoring`.
2. In another terminal, append a record to the vault (today: edit a file under
   `vault/projects/agent-monitoring/`; once P1 lands: `agentmon work start ...`).
3. Watch the dashboard.

Expected: the activity feed and the counts pick up the new record within a second or two,
the way a monitoring tool should.

Actual: nothing changes. The new record only appears after navigating to another screen
and back, which re-runs the loader, or after restarting the app.

The two transports therefore behave differently, which is worse than either behaviour on
its own: browser mode already reloads, because the Vite plugin watches the vault directory
and pushes a full reload over the HMR socket. A human comparing the desktop app with the
browser view sees the browser as the more live one, in the product where "live" is the
whole point.

The frontend seam already exists — `subscribeVaultChanges()` in `src/lib/api.ts` listens
for a `vault-changed` Tauri event and re-runs the loaders — so this is missing backend
work, not a redesign:

- add `notify` to `src-tauri`, watch `<vault>/projects` recursively;
- debounce (an editor or a CLI write produces several events per file);
- emit `vault-changed` with the changed project slug so a screen can decide whether it
  cares;
- re-arm the watcher when `set_vault_path` points the app at another vault.

Scope note: the watcher belongs to the piece that owns the shell and vault portability
(P5 in PLAN.md). Filed now so it is not rediscovered as a surprise during the final gate.

## Comments

### 2026-08-18T11:58:07Z — p1-cli-builder

Root cause, confirmed by instrumenting the running app rather than by reading the code:
`src-tauri/src/lib.rs` had no watcher at all. `setup()` resolved the vault and set the
window title, and that was the end of its involvement with the filesystem. The frontend
seam was never broken — `subscribeVaultChanges()` in `src/lib/api.ts` has always listened
for `vault-changed` — so nothing was ever sent to it. Browser mode looked live only
because Vite's own file watcher pushes a full page reload, which is the dev server's
behaviour, not the product's.

Implementing the watcher turned up a second, non-obvious problem that the naive version
would have shipped with. With a 250ms debounce, one `agentmon work update` still produced
**three** `vault-changed` events. The raw notify stream explains it (timestamps in ms):

    ...023 Create  .agentmon.lock
    ...026 Create  worklogs/.WORK-0003.md.27384.<nanos>.tmp
    ...028 Remove  worklogs/WORK-0003.md
    ...028 Modify(Name(From)) worklogs/.WORK-0003.md...tmp
    ...029 Modify(Name(To))   worklogs/WORK-0003.md
    ...029 Modify events.jsonl
    ...033 Remove  .agentmon.lock
    ...288 EMIT
    ...292 Modify projects/demo-app        <- directory event, 259ms after the burst
    ...554 EMIT

The real burst is 10ms wide and coalesces correctly. What breaks it is that Windows also
reports a `Modify` on the *containing directory* for every file created or removed inside
it, and delivers some of those hundreds of milliseconds late — after the debounce window
has already closed. Lengthening the window is the wrong fix (it makes the UI slower and
still loses the race on a slower machine); the right fix is to ignore paths that are not
readable vault data. The filter now keeps only `*.md`, `*.jsonl` and `*.json` and drops
dotfiles, which excludes directory notifications, `.agentmon.lock` and agentmon's own
`.tmp` files by construction.

## Resolution

Fixed in `src-tauri/src/lib.rs`: the desktop app now watches the vault and the UI refreshes
on its own, which is what SPEC.md's "Live updates" line asks for.

**What was added.** `spawn_vault_watcher()` starts a `notify` recommended watcher on
`<vault>/projects` (recursive, falling back to the vault root for a vault with no projects
yet). Raw events are filtered to readable vault data, pushed onto a channel, and coalesced
by a debounce thread: 250ms of quiet ends a burst, and 1500ms caps it so a long stream of
writes still refreshes the UI while it is happening. Each burst emits one `vault-changed`
carrying `{ vault, projects: [slug, ...] }` — the event `subscribeVaultChanges()` in
`src/lib/api.ts` already listened for, so no frontend change was needed. The watcher lives
in `WatcherState`, and `set_vault_path` re-arms it on the new directory (assigning drops
the old watcher, which closes its channel and ends its debounce thread), so vault
portability keeps working.

**Why it works, including the part that is not obvious.** The debounce alone was not
enough: Windows reports a `Modify` on the containing *directory* for every file created or
removed in it, and delivers some of those after the debounce window has closed, so one CLI
write produced three refreshes (traced in the comment above). The filter therefore accepts
only `*.md`, `*.jsonl` and `*.json` and rejects dotfiles, which by construction drops
directory notifications, `.agentmon.lock` and agentmon's own `.tmp` files. Being an
extension test rather than an `is_dir()` test, it also works for deletions, where the path
no longer exists to probe.

**Verification, all run.**

- `cargo check -p agentmonitoring` and `cargo build -p agentmonitoring` — clean.
- `cargo test --workspace` — 52 tests pass, three of them new in `src-tauri`. The main one
  drives the real notify backend against a temp vault, performs exactly the sequence
  `agentmon` performs (temp file, rename over the record, append to events.jsonl), and
  asserts one event naming `demo` arrives and that nothing follows it.
- The bug's own repro, on the built desktop binary against a real vault: launch the app,
  run `agentmon work update ... --message ...` from another terminal, watch the emitted
  events. Before the extension filter: three `vault-changed` for one write. After: exactly
  one, ~250ms behind the write, and a second write produced a second refresh.
- Instrumentation used for that trace was temporary and has been removed; `grep -rn
  "TEMP-" src-tauri/src` is empty.

**Left open on purpose.** The frontend still reloads everything on any `vault-changed`; the
`projects` payload exists so a screen can filter later, but nothing consumes it yet. The
watcher is not started when the app cannot resolve a vault at boot — pointing it at one via
`set_vault_path` arms it.

## For humans

Two windows: the desktop app showing a project's dashboard, and a terminal writing a new record into that project's folder. The dashboard did not move. The new record appeared only if you left the screen and came back, or shut the app and started it again. In a web browser the same app did refresh, but only because the developer's web server reloads the page by itself, which is that server's habit and not the product's.

**The desktop half was never listening; the screen half always was.** The screen waits for a message called `vault-changed` and rereads everything when one arrives. Nothing had ever sent one. I found that by watching the program run, not by reading its code.

**It watches the folder and sends that message now.** One message per burst of writing, where a quarter-second of quiet ends a burst.

**Waiting for quiet was not enough on Windows.** A single edit of one record still refreshed the screen three times. The writes themselves all land inside a hundredth of a second and group up fine. But Windows also announces a change to the folder whenever a file inside it is made or deleted, and it delivered one of those announcements a quarter-second after the quiet had already begun.

It is like waiting for a room to go silent before you speak, when one person's answer arrives by post the next morning.

**Waiting longer would only have made the screen slower** and still lost the race on a slower machine. So the watcher ignores anything that is not a record: the three kinds of file records live in, `.md`, `.jsonl` and `.json`, and nothing whose name starts with a dot. Folder announcements and the app's own half-written scratch files fall out by themselves.

**One write, one refresh.** I ran the reporter's own steps against the built desktop app: three refreshes before that filter, exactly one after, about a quarter-second behind the write, and a second write brought a second refresh. `cargo test --workspace`, the project's automatic checks, passes all 52, three of them new. One drives a real watcher over a throwaway folder, does to a file exactly what the record-writing command does, and fails if a second message follows the first.

Two things are left. The message names which project changed, but the screen reloads everything regardless, because nothing reads that part yet. And if the app cannot find a folder at startup, nothing is watched until you point it at one.

If you have to reopen it to see the truth, it is a report, not a monitor.
