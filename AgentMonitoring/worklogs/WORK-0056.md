## What

Two small fixes from user review. (1) The reference note kind now wears blue (--blue/--blue-soft) in its pill and status dot — it was the only kind in grey/outline and read as 'missing a colour'. (2) mcp update_work's response header now reports the record's real status: appending a note to a done log said 'WORK-XXXX in_progress · note added' (app-feedback FB-0001).

## Why

The user flagged both: the colourless reference pill looked wrong next to indigo/amber/purple siblings, and FB-0001 (filed by an agent) showed the misleading header sends agents on a 'did it reopen?' round trip.

## How

app.css: .pill-note-reference grey→blue tokens, .sdot-note-reference outline→solid blue, comment updated. mcp/lib/tools.mjs updateWork: state is no longer inferred from which args were passed — the note branch takes record.status from the CLI's JSON (verified in a sandbox: work update --json returns record.status='done' on a closed log), outcome/abandon branches set it explicitly. Regression check added to mcp/test/server.test.mjs on the existing correction-on-closed-log case.

## Outcome

Shipped both. mcp npm test 115/115 green incl. new FB-0001 regression check ('WORK-XXXX done · note added' on a closed log); check-i18n clean (182 screens). FB-0001 marked done.

## For humans

The app shows each note's kind as a small coloured tag with a dot beside it. Three kinds wore a colour — indigo, amber, purple. The fourth, `reference`, was grey with a thin outline, and beside the others it read as a tag somebody had forgotten to finish.

The second thing was a wrong word. An agent added a note to a job it had already finished, and the answer came back saying that job was in progress.

**The grey tag is now blue, its dot filled in like the rest.** `.pill-note-reference` is the tag's own style, and it took the blue the app already keeps for that purpose. All four kinds look like members of one set.

**The answer used to guess the state rather than read it.** `update_work` is the tool an agent calls to add a note to a job it logged. It worked out what to report from which pieces the caller had handed it. A note and nothing else meant "still working" — even on a job closed days ago. It is like a receptionist deciding you must be a new patient because you arrived without a letter.

**Now it asks, and repeats the answer.** In a throwaway project made for the test, I checked that `work update --json` really does report a closed job as done. The tool now takes the state straight from that answer. Where the same tool is used to finish a job or abandon one, it says which of those it did outright.

**`npm test` guards the agents' tools, and all 115 of its checks pass.** One is new and written for this exact case: it adds a note to a closed job and demands the answer say "done". A check like it fails the moment the wrong word comes back.

**An agent told "in progress" about a finished job goes looking for what reopened it.** That wasted round trip is what `FB-0001`, the complaint an agent filed about this very line, described. It is now closed.

Report what you looked up, not what you inferred from the shape of the question.
