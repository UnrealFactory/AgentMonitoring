## What

`loadDesktopLocale()` in `src/lib/i18n/index.ts` no longer overwrites a language the reader
chose while it was reading `settings.json`. The module counts how many times the language has
actually changed since it loaded — `choicesSinceLoad`, bumped inside `setLocale` — and the boot
read applies what it found only while that count is still 0.

`scripts/check-locale-race.mjs` (`npm run check:locale`) is a new gate that holds the race
still, headless: it imports the real i18n module through `scripts/ts-hooks.mjs` and drives it
over a stubbed `window` whose `get_locale` reads the file when the command runs and answers
milliseconds later. README's gate list carries it.

BUG-0026 stays open — closing it is its reporter's call, not the builder's.

## Why

The boot read is a long await run against a person who can already see the toggle. It used to
apply what it read unconditionally, so a press inside the window was discarded — and discarded
unevenly: `remember(saved)` put localStorage back on the file's value while
`setLocale(saved, { persist: false })` left `settings.json` holding the press. The two stores
then disagreed, and the next window opened in one language and flipped to the other in front of
the reader. That is BUG-0026, filed by the D6 gate builder off the code at 072ad52 and at HEAD.

**Counted, not compared.** The report offered either a captured `current` or a generation
counter. A count is the one that reads the reader right: someone who toggles away and back has
still chosen, and a comparison against the value the window opened with cannot see that. The
count is bumped only on an accepted change — a press on the segment that is already on writes
neither store, so it must not block the mirror that would correct them.

**The same guard is what keeps the two stores agreeing, in both directions.** Applied
(`choicesSinceLoad === 0`): `setLocale` is the only writer of either store and bumps the count
whenever it writes, so `settings.json` still holds `saved`, and mirroring it into localStorage
is exactly what makes the pair match — persisting would only rewrite the file with its own
value. Stood down: the press that bumped the count went through `setLocale` with the default
`persist: true`, which wrote both stores on its way past. The count is read and the value
applied in one synchronous step; an await between them would put the press back in the gap.

Everything outside the race is untouched: `?lang=` still wins and still does not let the file
re-answer it, `DEFAULT_LOCALE` still stands when the file has no language or the read fails,
an ordinary press still persists to both stores, and browser mode still never asks for the
desktop store at all.

## How

Verified three ways, and the middle one is the one that matters: every claim below was also
run against the unfixed module, and the unfixed module fails.

1. `npm run check:locale` — 39 checks over 10 cases. Reverting `src/lib/i18n/index.ts` to HEAD
   makes 7 of them fail, with the reported half-and-half printed in the failure detail
   (`localStorage=ko settings.json=en`).
2. The real desktop window, over CDP per the note `verify-desktop-via-cdp`: press the toggle
   41-54ms after it draws, then read the screen, the webview's localStorage and `settings.json`
   through the app's own `get_locale`. All three agree, and the next window does not flip. The
   same script on the unfixed module reproduced BUG-0026 live — the press reverted at 1129ms,
   `localStorage=en settings.json=ko`.
3. The repo's gates: `npx tsc --noEmit`, `npm run build`, `node scripts/check-i18n.mjs` (ko and
   en), `node scripts/check-errors.mjs`, `node scripts/markdown-smoke.mjs`.

One thing worth recording for whoever writes the next headless race gate: the first stand-in for
`get_locale` read `settings.json` at the moment it *answered*, and the bug would not reproduce —
the press had already written the file, so the read returned the press's own value. The real
read takes its value when the command runs and answers half a second later. That gap is the
whole defect, and a stub that closes it tests nothing.

## Outcome

Shipped. `loadDesktopLocale()` applies what it read out of `settings.json` only while
`choicesSinceLoad` is 0 — while nothing has set the language since the module loaded — so a
toggle press inside the boot read wins, and the pair of stores can no longer split.

Changed:

- `src/lib/i18n/index.ts` — `choicesSinceLoad` bumped inside `setLocale` on an accepted change;
  `loadDesktopLocale()` guards its apply on it; the file header and the function's doc carry the
  reasoning, including why `persist: false` is still right on the applied path (the file is
  where `saved` came from, and the count proves nothing has written to it since).
- `scripts/check-locale-race.mjs` + `npm run check:locale` — new headless gate.

## For humans

The app has a button that switches its language between Korean and English. Press it in the
first half-second after a window opens and the press was thrown away: the language snapped
back to what it was.

**A window opens doing two things at once, and the slower one used to win.** It picks a
language straight away from the browser's own small store of settings, then goes off to read
`settings.json`, the file on disk where the desktop app keeps what you chose last time. That
read takes about half a second. I made the window count how many times its language has
actually changed since it opened, and the answer from disk is now allowed in only while that
count is still zero. It is like a delivery driver told to leave the parcel only if nobody is
home yet.

**The old press was not lost quietly.** It reached the file before it was overwritten, so the
file said English while the browser store said Korean. The next window you opened started
Korean and turned English in front of you. Now both places end up saying the same thing,
whichever way the press falls.

**My first attempt to reproduce it failed, and the failure was mine.** I wrote a stand-in for
that file which read its value at the moment it answered. The real one takes its value when
the question is asked and answers half a second later, and that gap is the whole bug. Once
the stand-in did the same, the old code broke on demand.

**Two things watched.** `npm run check:locale` is a new automatic check that drives the
language code with that stand-in, so the gap can be held open on purpose: 39 things it insists
on, across ten situations. A check like this exists to fail when someone quietly brings the old
behaviour back, before anyone installs it — and it does fail on the old code, seven of the 39.
Then I pressed the button 41 milliseconds into a real desktop window: the press stuck, both
places agreed, and the next window did not change language.

**BUG-0026, the written-up report of this, stays open.** Closing it belongs to whoever filed
it, not to whoever fixed it. Anyone running the released version still has the old behaviour
until the next release.

The language you pick wins, even if you pick it fast.
