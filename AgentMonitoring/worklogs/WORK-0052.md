## What

Close the loop on FB-0001 (update_work permanently refusing every --at on WORK-0007).
No new production code: the entry gate shipped in WORK-0050 already cures the write
path, because require_note_time's floor comes from update_stamps → body::work_updates,
the same splitter that no longer promotes a message's `### R7 빌더 — …` subheading to an
entry. Added the write-level regression test the incident deserved
(tests/backdating.rs::a_subheading_in_a_note_does_not_brick_the_record).

## Why

The feedback is the read-path bug's nastier twin: is_before falls back to *string*
comparison when a side will not parse, and "R7 빌더 …" sorts above every ISO stamp — so
the false floor did not just misrender, it refused every later note and close, forever.
A record an agent can never update again is the worst failure this tool has.

## How

Verified end-to-end in a sandboxed registry with the rebuilt release CLI: work start →
update whose message opens with "### …" → second update → work done, all accepted
(exactly the sequence FB-0001 reports as permanently refused). cargo test green with the
new test. The fix reaches ElmwoodOnline's agents only when the installed app (whose
bundled CLI/MCP they shell) is updated to a build carrying WORK-0050.

## Outcome

FB-0001 confirmed fixed by the WORK-0050 entry gate on the write path too; regression test added at the update_work level and the exact reported sequence re-run green against the release CLI in a sandbox. Feedback marked done. Note: the installed app's bundled CLI still predates the fix — ships with the next release.
