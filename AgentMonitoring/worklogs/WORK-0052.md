## What

Close the loop on FB-0001 (update_work permanently refusing every --at on WORK-0007).
No new production code: the entry gate shipped in WORK-0050 already cures the write
path, because require_note_time's floor comes from update_stamps → body::work_updates,
the same splitter that no longer promotes a message's `### R7 빌더 — …` subheading to an
entry. Added the write-level regression test the incident deserved
(tests/backdating.rs::a_subheading_in_a_note_does_not_brick_the_record).

## Why

The feedback is the read-path bug's nastier twin: is_before falls back to *string*
comparison when a side will not parse, and "R7 빌더 …" sorts above every ISO stamp — so
the false floor did not just misrender, it refused every later note and close, forever.
A record an agent can never update again is the worst failure this tool has.

## How

Verified end-to-end in a sandboxed registry with the rebuilt release CLI: work start →
update whose message opens with "### …" → second update → work done, all accepted
(exactly the sequence FB-0001 reports as permanently refused). cargo test green with the
new test. The fix reaches ElmwoodOnline's agents only when the installed app (whose
bundled CLI/MCP they shell) is updated to a build carrying WORK-0050.

## Outcome

FB-0001 confirmed fixed by the WORK-0050 entry gate on the write path too; regression test added at the update_work level and the exact reported sequence re-run green against the release CLI in a sandbox. Feedback marked done. Note: the installed app's bundled CLI still predates the fix — ships with the next release.

## For humans

An agent could not add another note to one record. Not that time and not ever, and closing the record was refused as well. The record is `WORK-0007`, a work log in another project, and that refusal is what `FB-0001` reports — a complaint filed against this app by an agent trying to use it.

**A new note must be dated no earlier than the newest note already there.** The tool checks that before it writes, reading the newest note's time straight off the record. On this record the newest item in that list was not a time at all. It was a sentence — the opening line of somebody's message, which a separate fault had promoted into a note of its own.

**When one side will not read as a time, the two get compared as plain text.** `R7 빌더 …` sorts after every time that starts with a digit. So whatever moment the agent offered was judged too early. Not now and then: every time, permanently.

It is like a gate that admits you only if you arrived after the last person through, and the last person's arrival time reads `R7`.

**The cure was already written.** `WORK-0050`, the change that starts a new note only at a heading beginning with a date, fixes the writing side too, because writing reads that list with the same code the screen uses. There was no new code to write here. I added the test this deserved, at the point where a note is written rather than where it is read.

**I ran the exact sequence that had been refused.** In a throwaway copy, with the freshly built tool: start a work log, add a note whose message opens with a heading, add a second note, close the log. Every step accepted. That is the run `FB-0001` describes as impossible, and the tests pass with the new one among them.

**The agents who hit this do not have the fix yet.** They run the copy of the command-line tool that rides inside the installed app, built before the change. It reaches them when that app is updated to a build carrying it. `FB-0001` is marked done here.

A record nobody can add to again is a record you have lost.
