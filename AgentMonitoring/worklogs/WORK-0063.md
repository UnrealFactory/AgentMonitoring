## What

Patched the app-feedback item FB-0001 (essential index note silently demoted to memory
by a note rewrite). Three changes:

- mcp/lib/tools.mjs `note(action="write")`: the exists-probe now distinguishes "no such
  note" (exit 3, legal first write) from every other `note view` failure (lock, malformed
  file, spawn), which now surfaces as its own error instead of falling into the create
  path and demanding first-write metadata for a note that exists. The rewrite response
  warns when a passed `type` takes `essential` off a note, naming the exact restore call;
  and a named write that misses says "no note named 'x' here — this is a first write"
  instead of a bare demand for title/type/description.
- crates/agentmon-cli/src/main.rs `note update`: when `--type` demotes an essential note,
  the CLI prints a warning with the restore command — stdout in human mode, stderr in
  --json mode so the envelope stays pure.
- docs/MCP.md and docs/AGENT_MANUAL.md say the contract out loud: a type left off is
  preserved; taking essential away is honored but warned.

## Why

FB-0001: an agent rewrote an essential index note via note(action="write", name, body)
and the type ended up memory, unpinning required reading (the human found it). The core
already preserved omitted fields — reproduced and confirmed — so the demotion had to
come from an explicitly passed type. The trap that induces one: any transient failure of
the exists-probe turned a rewrite into "needs title, type, description", teaching the
caller to re-send with a guessed type; and an explicit wrong type was honored in silence.
Refusing explicit --type retypes would break legitimate curation, so the guard is a loud
warning plus the restore call, at both call surfaces.

## How

Reproduced first (sandboxed registry + fixture project, per registry-sandbox-in-gates):
body-only and full-meta-minus-type rewrites preserve essential on current code; only an
explicit type demotes, silently — that silence is the patch surface. MCP side keeps the
view JSON it already fetched for the exists check, so the old type costs no extra CLI
call; exit 3 is the only code that means "create". CLI side reads the note once before
the update, only when a demoting --type was passed. Five new E2E cases in
mcp/test/server.test.mjs: type-left-off preserves, demotion warns with the restore call,
restore itself does not warn, a missing name reads as a first write, a malformed note
file surfaces its own error rather than posing as a first write.

## Outcome

Shipped on main (unreleased): the MCP note write and the CLI note update both warn — with
the exact restore call — when a passed type takes essential off a note; an omitted type
was already preserved and now the docs say so; the MCP exists-probe no longer turns a
transient view failure into a first-write demand (only exit 3 means create), and a named
write that misses names the miss. Verified: cargo test all green (125 across suites),
node mcp/test/server.test.mjs 126 passed / 0 failed including 5 new cases, result budgets
hold (largest 595 <= 600), plus a manual sandbox run of demote/restore in human and
--json CLI modes (warning on stderr, envelope stays valid JSON). FB-0001 marked done.

## For humans

The notes here have kinds, and one kind, `essential`, is the mark that makes a note required reading. One such note stopped being one. An agent rewrote it, and afterwards its kind read `memory`, an ordinary note. Nothing said so. A person noticed, and filed it on this app's own board for complaints about the app itself, as `FB-0001`.

**My first guess was wrong.** I assumed the rewrite had wiped the kind by leaving it out. In a throwaway copy of a project I found that a rewrite leaving the kind out keeps it, and so does one supplying everything else. Only a rewrite that spells out a different kind moves it, and it moved it without a word. That silence was the thing to fix.

**So why would an agent spell out the wrong kind?** `note`, the tool an agent rewrites with, first asks whether that note is already there. Any failure of that question was read as "there is no such note" — the file locked, the file unreadable, the program not starting. The agent was then told to supply a title, a kind and a description, as though making a new one. So it guesses a kind and sends again.

It is like a switchboard that answers every call it cannot hear with "no such person works here".

**Only the reply that really says "no such note" now means "make a new one".** That is one exact answer, exit code 3, and nothing else counts. Every other failure is reported as itself, and a rewrite aimed at a name that is not there says so in those words.

**Changing a kind is still allowed, but it shouts now.** Forbidding it would break honest tidying. Passing `--type` on the command line, or the same kind through that tool, prints a warning naming the exact command that puts `essential` back. Where the output has to be machine-readable the warning goes to the error channel, so the answer stays clean. Both manuals say the bargain out loud: leave the kind out and it is kept; take `essential` away and it happens, loudly.

**`cargo test` passes 125 checks on the Rust side.** `mcp/test/server.test.mjs`, which drives the tools an agent calls, passes 126, five of them written for this. I also did it by hand: demoted a note, restored it, in both output modes. The warning landed on the error channel with the answer still valid. `FB-0001` is closed.

This lives in the shared code only, so anyone running an installed copy keeps the silent version until a release carries it out.

A tool that changes something without saying so has hidden it.
