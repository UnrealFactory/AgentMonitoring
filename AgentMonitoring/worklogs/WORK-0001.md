## What

Stood up the repository skeleton described in SPEC.md and made the vault format real in
code: a Cargo workspace with three members (`src-tauri`, `crates/agentmon-core`,
`crates/agentmon-cli`) on top of a Vite + React 18 + TypeScript frontend, plus the first
working implementation of the v1 vault schema.

`agentmon-core` now contains the whole on-disk contract:

- `model.rs` — `VaultInfo`, `Project`, `Event`, `Worklog`, `Bug` and the list/detail DTOs.
  Frontmatter is read with the spec's key spelling (`resolved_by`) and serialised to the
  UI as camelCase (`resolvedBy`); `to_frontmatter()` writes the spec spelling back so the
  CLI can round-trip a file without reformatting it.
- `body.rs` — splits a record into `## ` sections and `### ` entries (Updates,
  Comments), ignoring headings inside fenced code blocks.
- `vault.rs` — resolution (`--vault` > `AGENTMON_VAULT` > `./vault`), readers for
  projects/worklogs/bugs/events, per-project counts, and the status snapshot the
  dashboard needs.

Ten Tauri commands wrap those readers (`get_vault_info`, `list_projects`, `get_project`,
`list_worklogs`, `get_worklog`, `list_bugs`, `get_bug`, `list_events`, `get_status`,
`set_vault_path`). The `agentmon` binary declares the full CLI surface from SPEC.md so
`--help` is the real contract; read commands (`project list`, `work list/view`,
`bug list/view`, `status`, `doctor`) are implemented, write commands exit 4 with a message
naming the piece that owns them (P1) rather than half-writing a vault.

## Why

Every later piece — CLI, work pages, bug board, dashboard — reads and writes the same
files. If each of them parsed markdown its own way, the pieces would disagree about what
a record *is*, and the "single source of truth = the vault directory" line in SPEC.md
would quietly stop being true. Putting parsing in one crate makes the schema a contract
instead of a convention, and it is why the Tauri layer is 200 lines of forwarding.

Two decisions came from the same worry:

- **Lenient parsing.** Unknown frontmatter keys are ignored and unknown `##` sections are
  preserved in `extraSections`, so a newer writer never bricks an older reader.
- **Ids are validated before they touch the filesystem.** `WORK-0001` arrives from a URL
  and from agent-supplied CLI arguments, so `validate_id`/`validate_slug` reject anything
  that is not `PREFIX-NNNN` / `[a-z0-9_-]` before a path is built from it.

## How

Wrote the workspace by hand rather than running `create-tauri-app`, because the template
assumes a single-crate layout and would have had to be unpicked. `identifier` is
`com.agentmonitoring.app`; the window ships a real CSP instead of the template's `null`.

App icons were generated by rendering the mark in Chromium (`scripts/make-icon.mjs`) and
feeding the PNG to `tauri icon`, which avoids adding an image dependency for a one-off.

Sorting rules live in core so both transports agree: worklogs by last activity
descending, bugs open-first then by severity, events newest-first with malformed lines
skipped instead of failing the whole feed.

Unit tests cover the parts most likely to rot: frontmatter round-trip, headings inside
code fences, comment-heading splitting on the em dash, id validation against traversal,
and a test that parses the repo's own vault and asserts every `done` worklog has an
`## Outcome`.

## For humans

Four parts of this app read the same folder of plain-text records: the command-line tool, the work pages, the bug board, the summary screen. Each could have learned to read those files on its own. Then they would slowly drift apart about what a record even is.

**I put the reading in one place.** `agentmon-core` is a shared piece of code the other parts call instead of doing the job themselves. It knows how a record is laid out — the small block of settings at the top, the sections underneath — what sits in the folder, and what order to list it in.

It is like a household keeping one address book instead of six: nobody has to work out whose copy is right.

**The desktop window has ten ways to ask, and no opinions of its own.** Each one hands a question straight to that shared code: which folder is open, list the projects, list the work, show me this one record, show me what has happened lately. The window holds no knowledge of how a record is written, so it cannot disagree with the reader that does.

**Two ways to wreck a file, guarded on sight.** A later version of this tool may write a setting this one has never heard of, so anything the reader does not recognise is carried through untouched rather than dropped. Separately, an id such as `WORK-0001` arrives from a web address, or from whatever an agent typed, and it becomes part of a file path — so it is refused unless it is capitals, a dash and four digits.

**The usual starter tool would have fought me.** The standard command for beginning a desktop app of this kind builds one bundle of code; this needed three. Unpicking that template was more work than writing the layout by hand, so I wrote it by hand.

**The build is clean and the tests read our own records.** `cargo build --workspace`, the command that compiles every part, finished with both programs produced. `cargo test -p agentmon-core` checks the reader against traps it will really meet: a heading inside a fenced-off block of sample code, an id shaped like a path out of the folder. One test reads this project's real records and fails if a finished work log has no outcome written down, so our own history cannot rot quietly.

**It reads; it cannot write.** The tool already answers `--help` with every command the written plan asks for, so what it prints is the contract rather than a subset of it. Every command that would change a file stops there and names the piece of work that owns it, rather than leaving half a record behind. The desktop app does not yet notice a file changing under it, which is filed as `BUG-0002`.

A reader that guesses is worse than one that refuses.
