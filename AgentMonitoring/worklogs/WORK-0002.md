## What

The visual and data foundation the other pieces build on:

- `src/styles/tokens.css` — the dark design system: three background layers
  (`#0e0f11` app, `#16171a` surface, `#1c1d21` raised), hairline borders at 6–10% white,
  13–14px type on Inter Variable bundled through `@fontsource-variable/inter`, one
  indigo accent, and status/severity colours defined once and reused by every pill.
- App shell — left sidebar with the app mark, a project switcher that reports active work
  and open bugs, and nav for Dashboard / Work / Bugs / Projects.
- Six routed screens (`/p/:project`, `/work`, `/work/:id`, `/bugs`, `/bugs/:id`,
  `/projects`), all rendering real vault records: no placeholder copy anywhere.
- `src/lib/api.ts` — one API, two transports. In the desktop app it calls Tauri
  `invoke()`; in a browser it calls `/vault-api/...`, served by a Vite middleware that
  reads the same directory.
- `scripts/screenshot.mjs` — Playwright captures of every screen at 1600x1000 @1.5x, and
  `scripts/capture-refs.mjs`, which captures the quality bars (two merged VS Code PRs,
  the VS Code issue list, a Grafana Play dashboard, linear.app) into `progress/refs/`.

## Why

P0 is judged on whether the thing runs end to end and can be photographed, but the part
that outlives P0 is the token layer: every later screen inherits its spacing, type and
status colours from this file. Getting "small dot plus label" defined once is what stops
the bug board and the dashboard from inventing two different visual languages for
"critical".

The two-transport data layer exists for a practical reason from PLAN.md: critics screenshot
the app with Playwright on every round. Booting a full Tauri window for that is slow and
flaky; a browser tab against a dev middleware is neither. The desktop app stays the
product, and because both transports return byte-identical JSON, nothing above `api.ts`
can tell them apart.

Markdown is rendered by a small in-house renderer that builds React elements directly.
Record bodies are written by agents — that is generated text landing in a UI — so
`dangerouslySetInnerHTML` was never an option, and a full markdown dependency would have
been more surface than the six section types in SPEC.md need.

## How

The Vite middleware and `agentmon-core` are two implementations of one contract, so the
JS side (`scripts/vault-fs.mjs`) documents the parity rules it must hold at the top of the
file: camelCase keys, the same sort orders, the same lenient event handling, the same id
validation. The dev server also watches the vault directory and pushes a full reload, so
browser mode reacts to an agent writing a record the way the desktop app should.

Deviation from CLAUDE.md, recorded as SPEC requires: this vault's first records were
written by hand rather than through `agentmon work start`, because the CLI's write path
does not exist yet (P1). The files were written to the exact schema the parser validates —
`agentmon doctor` reads them clean — and every later record goes through the CLI.

## For humans

This app has six screens: a project's summary, the list of work, one work record, the list of bugs, one bug, and all the projects. Every one shows real records, with no filler text anywhere.

**One frame holds all six.** Down the left edge sit the app's mark, a switcher naming the project you are in — with how much work is running and how many bugs are open printed beside the name — and four links: Dashboard, Work, Bugs, Projects. The folder all of this is read from is pinned at the bottom, so you can always see which one you are looking at. Each of the six has a web address of its own, so a link to one record opens that record.

**Every colour and size is written down once.** `src/styles/tokens.css` holds the whole look — three shades of dark background, hairline borders, the type sizes, one indigo accent, and one colour per status and per severity. The bug board and the summary screen read those same lines, so one app cannot invent two ways to say "critical".

**There are two doors into the same folder of records.** The desktop app asks the code built into it. A browser tab asks a small server that reads that same folder. Both hand back identical answers, so only `src/lib/api.ts`, the one file that picks a door, knows which was used.

It is like a shop with a counter and a hatch: the same stock room behind both.

**The browser door exists because of photographs.** Reviewers photograph every screen each round, and starting the whole desktop window for that is slow and unreliable. `npm run screenshot` starts that small server itself and waits until it truly answers, rather than pausing a fixed number of seconds — so a slow machine cannot photograph a half-painted page.

**A second script photographs the apps we are being measured against.** It saves ten shots into the project's own folder: two finished code reviews and the list of open problems from VS Code, a public Grafana dashboard, and linear.app. A reviewer can then hold our screen beside theirs instead of beside a memory of theirs.

**The first Grafana page made a poor bar.** Half of it is welcome text, and two of its panels say "No data". Two further pages failed the same way — each is pinned to a date range its numbers do not fall in — so I settled on Grafana's own time-series example, which invents its numbers and therefore always draws axes, a grid and a legend. The scrolling was lying as well: the usual scroll-the-page command did nothing there, because that page scrolls a box inside itself, and every shot meant to show the lower half was the top of the page again. It sends a wheel turn over the middle of the window now.

**Records are written by agents, so their text is handled as untrusted.** A small piece of code written here turns that text into what you see, building the page one element at a time. Handing a lump of text over to be inserted as it stands was never on the table for text a program wrote.

**Looking at the photographs found a bug.** In the work list, the marks agents type to format their text were showing up unchanged in the preview line, filed and fixed as `BUG-0003`.

**Both ways of opening the app now show the same six screens.** `cargo test --workspace` passes 11 checks, one of which walks this project's own records and fails if a work log is missing a section it must have. Type is bundled inside the app, so nothing fetches a font over the network while you use it.

**What is missing, none of it quietly.** No command writes a record yet, so the first records here were typed by hand — then read clean by `agentmon doctor`, which reports any record the app could not show. The desktop app does not notice a file changing under it, filed as `BUG-0002`. One project is all this folder holds, so the bug board is judged on thin data until a second lands.

One file holding the colours is the only way two screens ever agree on what red means.
