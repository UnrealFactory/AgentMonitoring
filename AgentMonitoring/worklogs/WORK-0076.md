## What

Closed the D6 final-gate punch list, and the live-corpus hole the round-1 closer failed on.

- `doctor` now checks an event's **claim**, not only its shape: every `work_updated` is paired against a `### <ts>` entry under its record's `## Updates`, and an unpaired one is an **error** (`crates/agentmon-core/src/doctor.rs`, `pair_work_updated` / `accounted_orphans`).
- Where an orphan cannot be repaired, it is accounted for by exact `WORK-NNNN@<ts>` token in `notes/event-reconciliation.md`. Accounted orphans are not problems, but doctor prints them on every run and `--json` carries them in `reconciledEvents`.
- Wrote that reconciliation note for this project's own nine orphans (WORK-0059/0066/0068/0069/0070/0071/0072/0073/0075, actor `fable-human-backfill`).
- Two tests in `crates/agentmon-core/tests/write_roundtrip.rs`: the check fires and the message names the record, the timestamp, the entries the record does hold and both repairs; the reconciliation note accounts for an exact token and refuses a near-miss timestamp and a bare record id.
- Docs told three small untruths, all confirmed at the binary: `note add/update/list --type` help omitted `essential` (`crates/agentmon-cli/src/main.rs`); SPEC listed `doctor` with no `--strict`; SPEC claimed all four refresh verbs log `human_updated` when `app-feedback update` logs nothing (that board has no `events.jsonl`). - Filed BUG-0026: a language-toggle press in the first ~0.5s is discarded and leaves `localStorage` and `settings.json` disagreeing. Pre-existing in v1.0.5, not this work's.

## Why

`SPEC.md` sells `doctor` as "validate project integrity, exit non-zero on problems", and it was not checking integrity. It read an event's JSON shape, its type, that its `ref` resolved and that its timestamp parsed — never whether what the event said had happened. Nine events in this project's own log said a progress note was posted on a work log that holds no such note, and `doctor --strict` printed "No problems found" over all nine while `src/lib/dashboard.ts` counted them as progress notes and the feed rendered "posted an update on". The dashboard and the files disagreed on live data and nothing in the product could see it.

## How

Pairing uses `body::work_updates`, the same parser the reader and the writer use, so doctor pairs against exactly what a reader sees rather than a second, looser grammar.

The severity had to be error: `write.rs` emits `EV_WORK_UPDATED` only in the `Some(note)` branch of `update_work`, and that branch calls `body::append_entry(.., "Updates", ..)` first, so the event and the entry are written together or not at all. An event without its entry proves something other than the CLI wrote half a pair, and by doctor's own rubric "a human reads something untrue" is an error.

That collided with doctor's other contract — a `fix:` line is always an action someone can take. Some orphans have no repair. The nine here do not: their note text exists nowhere in this repo. Each event summary is 152-160 characters, cut on a word boundary with a trailing ellipsis, which is what `body::excerpt(text, 160)` produces, so a longer text existed; searching `AgentMonitoring/`, `progress/`, `docs/`, `scripts/` and `.tmp-restore/` for their opening phrases matches `events.jsonl` and nothing else. Writing a truncated summary into a live record as though it were the note is invention, not restoration, and backdating a fresh note with `--at` would stamp today's words with 2026-08-23T08:13:28Z and emit a second event at the same timestamp. Neither is a repair.

So the escape hatch is a note in the corpus rather than a flag or a source allowlist: `notes/event-reconciliation.md`, one exact `ref@ts` per orphan plus a sentence. It is auditable, the app renders it, and it cannot be created by accident. No wildcards — a bare record id accounts for nothing, so a waiver costs a sentence per orphan.

Evidence that the nine record halves were never written rather than stripped: seven of the nine work logs were created in 07b3f9c and carry no `## Updates` in any committed state; WORK-0059 has none before or at that commit; WORK-0069 holds exactly one entry, `2026-08-22T13:40:00Z`, unchanged across it, so a strip would have had to remove the new entry and leave the old; four events share the second `08:13:28Z` and three share `08:13:39Z`, which one-process-at-a-time `work update` cannot produce; and the same actor logged 381 `human_updated` events in the same sweep, including WORK-0014 at 08:13:20Z and WORK-0015 at 08:13:49Z, eight seconds either side.

## For humans

The app keeps a list of everything that has happened in a project, and the front page reads that list back as sentences: who did what, and when. On 23 August a check found nine of those sentences pointing at nothing. Each said someone had posted a progress note on a job, and the job held no such note. Anyone clicking through would find an empty spot.

**`agentmon doctor`, the command that checks a project for damage, could not see any of them.** It was reading each line in the list for the wrong things: that it was written correctly, that it named a job that exists, that its date made sense. It never asked whether what the line said had actually happened. It printed "No problems found" over all nine.

**It now compares every progress-note line against the job it names**, using the same reader the screen uses, and fails when they disagree. That is the part that matters: the front page and the files can no longer drift apart without something saying so.

**The nine themselves could not be repaired, and pretending otherwise would have been worse.** Each line keeps only the first 160 characters of what was written, cut off mid-sentence. Copying that fragment into the job would look like a fix and would be an invention, and live records here must never carry made-up history. So they are written down instead, by name, in a note called `event-reconciliation` that doctor reads. Being written down stops them counting as damage; it does not stop doctor listing them every single run. It is like a crack in a wall that has been measured and dated rather than painted over.

**Three things the documents claimed turned out not to be true**, each checked against the program itself: the help text for adding a note left out one of the five kinds it accepts, the specification described the checking command without one of its options, and it credited a fourth command with recording something it does not record. All three now match the program.

If the front page ever counts something the files do not contain, doctor says so before a person has to find it.
