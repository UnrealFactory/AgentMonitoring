## What

Version bumped to 1.0.1 in package.json / tauri.conf.json / Cargo.toml, the session's
work committed as 4ee6c10 and pushed, and `npm run release` built
AgentMonitoring_1.0.1_x64-setup.exe and published
github.com/UnrealFactory/AgentMonitoring releases/tag/v1.0.1.

## Why

Everything fixed this session lived only in the source tree: the installed app (and the
bundled CLI/MCP that ElmwoodOnline's agents shell) still showed UTC, still bricked
WORK-0007 on its ### note — the second FB-0001 filing today came from exactly that gap.
A release is what closes it.

## How

Per the handoff note: three version fields agree, release.mjs builds the NSIS installer
and publishes via gh. Verified with `gh release view v1.0.1`: tag published
2026-08-21T12:37:40Z carrying the one installer asset. Installed apps offer the update
on next launch or the half-hour recheck.

## Outcome

v1.0.1 is live on GitHub with the NSIS installer asset (verified via gh release view, published 12:37:40Z). Commit 4ee6c10 pushed on main. Installed apps pick it up from the updater; installing it gives ElmwoodOnline's agents the fixed CLI/MCP.

## For humans

Version 1.0.1 of the app is out. Anyone with it installed is offered the update the next time they open it, or at the half-hourly check the app makes on its own.

**Until this went out, the day's fixes existed only on the machine they were written on.** The installed copy still showed times on one worldwide clock instead of the clock on your own wall. It still had `WORK-0007`, the record no agent could add another note to. That second one was reported twice in a single day: the same complaint, `FB-0001`, filed again, straight out of that gap.

It is like a repair written up on the office whiteboard. Nobody's own copy has it until someone carries it across.

**Three files have to agree on the version number.** They are `package.json`, `tauri.conf.json` and `Cargo.toml`. I set all three to 1.0.1, and the day's work was committed and pushed. Then `npm run release` built `AgentMonitoring_1.0.1_x64-setup.exe`, the file you double-click to put the app on a machine. It published that file under the name v1.0.1.

**I asked GitHub what it had actually published.** `gh release view` reports back what a published release contains. It showed the release going out at 12:37:40 that day, carrying that one installer. A release that exists but carries no file leaves everyone who clicks update exactly where they were.

**Installing it is what reaches ElmwoodOnline.** The agents there use the command-line tool that rides inside the installed app. They get the corrected one when that machine takes this update, and not a moment sooner.

A fix nobody has installed is a fix nobody has.
