## What

Rebuild the Human view on the agent page's own skeleton (owner decision, 2026-08-25): an "Overview" `record-section` (the opening telling, one title — a blob cannot be split back into What/Why/How), the `timeline-rail` with one `.update-card` per dated node ("N번째 노드" header + timestamp, chronological), and the ending's telling inside the agent page's `.outcome-card` (결과/해결 내용 by kind) — the ending is the node stamped exactly at `finished`/`resolved`, found anywhere in the list so a post-close correction does not displace it. The eli5 reading treatment stays inside each block (standfirst on the page's first paragraph only, per-telling beat numbers, scenes, accent takeaway). Both agent timelines flip to chronological: work Updates (start edge → notes 1..N → status edge; Outcome section moved below the trail, contents-rail order updated) and the bug thread (claim → findings → end marker; ResolutionCard moved below, `bd.fixAbove` renamed `bd.fixBelow`). Gate scripts repointed from `.human-sheet` to `.human-view` (check-keys, check-i18n, screenshot), and the feedback board's row CSS keeps its no-frame reading column with the Overview title suppressed per row.

## Why

Owner feedback in three steps this session: a bare dated seam did not read as a boundary; a node card fixed that but was a third design; the conclusion was that two designs for one record is itself the confusing thing — the human half should be the agent page's layout carrying easy-language content, and both halves should read the way the work ran (1 → 2 → 3 → 결과) rather than newest-first. The old newest-first ordering optimized for "the reader came for the latest round"; the owner chose story order for both, and the record head already carries the current state.

## How

`HumanStoryView` splits tellings into opening / nodes / ending and reuses the agent page's classes (`record-section`, `section-title`, `timeline-rail`, `trail-node`, `update-card`, `outcome-card`) so the two halves cannot drift; `HumanArea` passes `finished` (work) / `resolved` (bug) and became a div (sections inside a section is a heading lie). The sheet CSS collapsed into `.human-view` (detail-main's own gap, reading sizes kept, the centred `--human-measure` column gone — the measure is the renderer's own again). New key `view.overview` (개요/Overview).

## For humans

한 기록을 읽는 두 화면 — 에이전트용과 사람용 — 이 서로 다른 생김새를 갖고 있었고, 소유자가 보기에 그 차이가 이제 도움이 아니라 혼란이었습니다.

**사람 화면이 에이전트 화면과 같은 뼈대가 되었습니다.**

![에이전트 페이지와 사람 페이지가 같은 뼈대로 나란히 선 모습](assets/work-0091-1-one-skeleton-two-halves.svg)

이제 사람 쪽도 에이전트 쪽과 똑같은 구성으로 그려집니다: 맨 위에 "개요"라는 제목이 달린 글 섹션(기록을 만들 때 쓴 시작 이야기), 그 아래 세로줄에 점이 찍힌 타임라인과 노드 카드들, 맨 마지막에 초록 체크가 달린 결과 카드(끝맺음 이야기). 카드 안의 읽기 방식 — 큰 도입 문장, 번호 달린 단락, 그림, 강조된 마무리 문장 — 은 쉬운 말 화면의 것을 그대로 지켰습니다.

**두 화면 모두 일이 흘러간 순서로 읽힙니다.** 지금까지 에이전트 화면은 최신 것이 위로 오는 역순이었고 결과가 타임라인 위에 있었습니다. 소유자의 결정으로 양쪽 다 정순이 되었습니다: 시작 → 1번째 노드 → 2번째 → … → 결과. 버그 화면의 스레드와 해결 카드도 같은 순서로 바뀌었습니다.

**어떻게 확인했는지.** 타입 검사와 빌드, 화면 단어·잘림 검사(양 언어), 그림 기하 검사가 모두 통과했고, 실제 기록을 두 화면으로 열어 개요 → 노드 카드 → 결과 카드가 순서대로 서는 것을 보았습니다. 확인이라는 사실 자체는 그릴 장면이 없어 이 단락에는 그림이 없습니다.

같은 것을 두 번 디자인하면 읽는 사람이 두 번 배워야 한다.

실제 기록을 두 화면으로 열어, 개요 → 노드 카드 → 결과 카드가 같은 뼈대로 같은 순서로 서는 것을 보았습니다.

큰 표제 활자는 첫 문단이 짧을 때만 쓰입니다. 긴 벽 문단은 본문 크기로 내려갑니다.

글줄 폭은 다시 읽기 폭(62자)으로 좁혔습니다. 기록 본문용 넓은 폭이 읽기 크기에서는 벽처럼 보였기 때문입니다.

남색 강조 블록은 페이지 맨 마지막 하나에만 칠해집니다. 이야기 중간마다 큰 블록이 서던 것이 무거움의 정체였습니다.

### 2026-08-25T04:35:29Z

이제 카드 안 글이 소제목 없이 온 경우, 문단 하나하나가 번호 달린 블록으로 그려집니다. 글은 한 글자도 바뀌지 않고, 번호와 사이 공간만 얻습니다.

앞으로 쓰일 글도 그 모양에 맞게, 작성 규칙에 "사실 하나당 짧은 문단 하나 — 화면이 번호를 붙인다"가 들어갔습니다. 규칙을 알려주는 세 통로가 모두 새 문장을 실어 나르는 것을 검사로 확인했습니다.

예시가 되는 두 기록의 카드 글도 그 모양으로 다듬어, 지금 화면에서 바로 1·2·3·4로 정리되어 보입니다.

### 2026-08-25T04:40:28Z

결과 카드 안에 남색 강조 블록이 서서 초록 카드와 색이 부딪혔습니다. 이제 결과 카드 안에서는 마무리 문장도 번호 블록으로 이어지고, 남색 강조는 결과 카드가 없는(아직 진행 중인) 페이지의 맨 끝에만 쓰입니다.

### 2026-08-25T04:44:43Z

개요만 카드 없이 맨살로 떠 있어서 페이지에서 혼자 미완성처럼 보였습니다. 이제 개요도 아래 노드·결과와 같은 카드로 그려집니다 — 머리띠에 "개요"와 기록의 시작 시각, 안에는 표제 문장과 번호 블록. 페이지 전체가 같은 모양의 상자 세 가족으로 정리됐습니다.
