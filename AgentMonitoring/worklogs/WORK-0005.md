## What

Generate the `relay` scenario project in the live vault — the second project SPEC.md and
`scenario/BRIEF.md` ask for, a fictional but realistic webhook-delivery service built by four
agents (`nova` backend, `sable` frontend, `patch` infra, `quill` docs/API). 12 work logs
(9 done, 2 in progress, 1 abandoned), 8 bugs (6 resolved, 1 in progress, 1 open), 85 events
spread over the three weeks ending today, and `scenario/GROUND_TRUTH.md` — the per-record
grading key that states the intended what/why/how and, for bugs, root cause and fix.

Every record was written through `target/release/agentmon.exe`; nothing in
`vault/projects/relay/` was hand-edited.

## Why

Until now the vault holds one project with four work logs, so the dashboard, the bug board
and the activity feed are all judged on data too thin to show what they do — no in-progress
work, no open bugs, no severity mix, no second project in the switcher, and a timeline four
records long. The screens cannot be evaluated, and neither can the comprehension question
this product exists for: can a human reconstruct work they did not do from the vault alone.

The generation goes through the CLI rather than by writing files because that doubles as an
end-to-end stress test of the write path: 85 mutations across every command, including the
backdating flags that had never been exercised in bulk.

## How

The codebase was invented once and then held consistent across all 20 records: crate names
(`relay-core`, `relay-store`, `relay-api`, `relay-worker`), module paths, table names, the
delivery status vocabulary, the retry ladder, the signature header format. Records reference
each other the way real ones do — WORK-0001 ships with "no lease sweeper yet" as a follow-up
and BUG-0004 is that gap detonating in production two weeks later; WORK-0006's method finds
BUG-0002; WORK-0007 is abandoned with a benchmark that disproves its own premise and names
WORK-0010 as its replacement.

Commands were issued in global chronological order, each with the backdating flag for the
moment it describes (`--started-at`, `--at`, `--finished-at`, `--created-at`), so
`events.jsonl` is written in timeline order and the app's feed, durations and per-agent
rollup are all true. Bodies were passed as `--body-file` / `--message-file` /
`--outcome-file` / `--resolution-file` / `--reason-file` from a scratch directory outside the
repository, because prose this size fed through shell quoting is where mangled records come
from.

## Updates

### 2026-08-18T13:10:00Z

Twelve work logs and eight bugs are in, written through the CLI in chronological order.
Backdating held up across 85 mutations: every `--at` was accepted, the ordering rule
(a note cannot predate `started` or the previous note; a resolution cannot predate the claim
or the last comment) never fired incorrectly, and no command needed a retry — the timeline in
`events.jsonl` came out sorted without any post-processing.

Two things the bulk run confirmed about the write path. `--message-file`, `--reason-file` and
`--resolution-file` all read correctly, so bodies of 400–2,000 words never touch shell
quoting — the run contains backticks, `$`, `%`, SQL and unicode em dashes, none of which
survived intact in an early inline-heredoc draft. And `work abandon --at` stamps `finished`,
so the abandoned record (WORK-0007 in `relay`) shows a real six-day span instead of sitting
open on the dashboard.
