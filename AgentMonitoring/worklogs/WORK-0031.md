## What

One global tooltip layer — `src/components/Tooltip.tsx`, mounted once in `src/App.tsx` —
draws every `title` attribute in the app, in the app's own design language, and the WebView
never draws one of its own.

It works by document-level delegation, not by editing components. On `mouseover` the layer
finds `closest("[title]")`, stashes the value and sets the attribute to the empty string
(which per HTML means "no advisory information", and also stops the browser consulting an
ancestor's title); 400ms later it draws the stashed text; on `mouseout` the attribute goes
back exactly as it was. Nothing else in `src/` changed: the ~144 `title=` attributes across
the screens are the API, and this is the renderer.

## Why

The user's ask, with a screenshot of the defect attached:

> hovering shows the NATIVE WebView tooltip (white system box) for title attributes — ugly
> against the dark app. Replace it app-wide with a custom tooltip in the app's own design
> language.

It is the same defect the context menu was rebuilt for in P8: a desktop app that leaks the
browser it happens to be drawn in. A white box with a grey border and Segoe UI inside it,
sitting on a #0b0c0e sidebar, is Edge's tooltip — nobody hovers a count in Linear and meets
Chromium.

The attribute had to survive, which is why the fix is a layer and not 120 edits.
`scripts/check-i18n.mjs` sweeps `[title]` for Latin left in a Korean window (two passes, at
lines 878 and 986); a screen reader uses `title` for the accessible name of an element that
has no visible label; and rewriting every call site to a `<Tooltip>` wrapper would have
touched every component in the app and broken both.

## How

**The layer.** `TooltipLayer` mounts once inside `ContextMenuProvider`. One listener per
event on `document` — `mouseover`, `mouseout`, `mousemove`, `focusin`, `focusout`,
`mousedown`, `mouseup` — plus the enders: `scroll` and `wheel` (capture, so a scroll inside a
pane counts), `click`, `keydown`, `contextmenu`, `dragstart`, `visibilitychange`, window
`blur` and `resize`, `onModalChange` (the palette), and the route change.

**Blanking, and when it is not done.** The blank happens on `mouseover`, the instant the
hover begins, not when the tooltip is shown: the native one appears after ~500ms and this
waits 400, so leaving the attribute live in between is a race. Restoring is guarded — if the
attribute is no longer the empty string, a re-render wrote a newer value and the stash is
stale, so it is dropped rather than put back.

**Keyboard focus never blanks anything.** No browser raises a native tooltip for focus, so
there is nothing to suppress, and a focused element whose accessible name *is* its title
would otherwise go nameless to a screen reader for as long as it held the focus. Focus
tooltips are drawn from the live attribute, anchored to the element rather than to a cursor
the reader is not holding, and only when the focused element matches `:focus-visible` — so
clicking a row does not pop one under the pointer.

**Placement.** Preference, then flip, then clamp: off the cursor (right 12, below 20) or
under the element (gap 6); flipped above the cursor near the bottom edge and back to the left
near the right one; then clamped to an 8px margin, which is what catches a box taller than
the room above *and* below. Measured in a layout effect and `visibility: hidden` until it
lands, so nothing is ever painted at 0,0.

**Timing.** 400ms cold; instant if the last one was on screen within 150ms, so reading across
the sidebar's counts is one gesture and not five. Instant hide. A 90ms opacity fade and
nothing else — and between two tooltipped siblings the box is *reused* rather than unmounted
(the `mouseout` defers the swap to the `mouseover` already on its way), so it moves instead of
blinking.

**Never while a button is down.** `mousedown` hides and sets a flag; `mouseover`/`mousemove`
re-read `e.buttons` every time, so the flag self-heals after a title-bar drag — which hands
the gesture to Windows and never sends the matching `mouseup` into the page at all.

**The chart keeps its own tip.** `.chart-tip` (components/charts.tsx) follows the burn-up's
crosshair, and the legend's ±n deltas underneath it carry titles. If a `.chart-tip` is live
inside the same `.chart`, this layer draws nothing — checked both when the timer is armed and
again at the moment of showing. The title is blanked all the same, so the WebView cannot draw
a third box over the two.

**The design** is the context menu's, one step smaller: `--bg-raised`, a 1px hairline at 9%
white, `--radius-sm`, `--shadow`, 12px `--text-primary`, 5px/8px padding, `max-width: 360px`,
`white-space: pre-line`, `word-break: keep-all` with `overflow-wrap: break-word` (Korean
breaks at the author's spaces; a spaceless vault path still has to fit). `pointer-events:
none`, `z-index: 90`. `role="tooltip"` with `aria-hidden` — the text is already on the
element as `title`, which is what a screen reader reads; announcing it twice from a box the
reader cannot reach would be worse than not drawing it.

Middle dots are joints, not bullets: ` · ` is drawn with a no-break space in front of the dot,
so a wrap happens *after* the separator instead of starting a line with what looks like a list
marker.

One tool change: `scripts/win-window.ps1` gained a `hover` action (cursor onto a client point,
rest, optional screen grab in the same invocation). It is the only way to answer the question
this record is about — whether the WebView's own tooltip appears — because that tooltip is an
OS popup window rather than an element, and only a screen grab contains it.

## For humans

Someone hovered a count in the app and a small white box appeared with the text for it. The app is dark; the box was not. They sent a picture.

**That white box came from the browser, not from us.** The desktop app is drawn inside `WebView2`, Microsoft's browser engine, which draws its own hover label in the system's plain style. So the app leaked the browser it sits in.

**The app now draws every one of those labels itself.** Each hover text is attached to its button or row by a standard web attribute called `title` — about 144 across the screens — and one new file, `src/components/Tooltip.tsx`, watches for hovers, reads that text, and paints it in the app's own dark style.

**Those 144 had to stay exactly where they were.** `scripts/check-i18n.mjs` hunts English left behind in the Korean window, and it sweeps them; when a check of that kind comes back no, a Korean reader gets a half-English screen. A screen reader speaks the same text as the name of a button with no visible label.

**So the app borrows the text and puts it straight back.** The moment your pointer arrives, it lifts the text off the button and holds it. 400 milliseconds later it paints its own box. When you leave, it puts the text back exactly as it was.

It is like taking a book off a shelf to show someone and sliding it into the same gap.

**Lifting it any later would have been a race**: the browser's own box arrives at about 500 milliseconds, and ours at 400.

**I watched the real window, because that is where it was reported.** The browser's box is an operating-system popup, not part of the page, so only a photograph of the screen contains it. `scripts/win-window.ps1`, which drives the real mouse pointer onto a point and photographs it, gained a hover step.

All four hovers on the running desktop build gave a dark box, one of them straight after dragging the window by its title bar, and no white box appeared anywhere. 136 automatic checks in Korean and English then found all 144 texts still on their buttons at rest, with exactly one lifted while a row was hovered.

**What is different: the box you see is the app's own.** `.chart-tip`, one chart's own little readout, still draws itself, and this layer stands aside while that is up, so two boxes never meet.

A desktop app that borrows a box from the browser it is drawn in is showing you someone else's furniture.
