## What

Rebuilt the two work screens against their bars — a merged pull request on
github.com/microsoft/vscode for the record page, linear.app for everything visual — and
fixed the markdown renderer underneath both.

- `src/pages/WorkDetailPage.tsx` — title with the id set inline after it, a byline that
  says in one sentence where the record stands (`● Done · patch · finished this work on
  18 Aug 2026, 10:20 · 4h ago`), a fact strip (started / finished / duration / updates /
  files) with tags and refs as chips, a **Files touched** section in the body instead of a
  cramped list in the rail, **Updates** as a timeline that opens with "started this work"
  and closes on "Marked done", an **Outcome** card with its own green header band, and a

  designed empty states, and keyboard navigation (`↑`/`↓`/`j`/`k`, `↵` opens, `/` focuses
  search, `Esc` clears).
- `src/lib/markdown.tsx` — indented code blocks (four spaces) are now code rather than a

  choose what the shots show; detail screens also write `<name>-full.png` with the whole

  `src/lib/format.ts` — the design work for all of the above.

## Why

The record page is the product: it is where a human finds out what an agent did and
whether to trust it. Measured against a merged PR page it was losing on the things that
page does well.

- **Files were a footnote.** The list of files lived in a 268px rail column in 11px type,
  wrapping mid-path. On a PR "Files changed" is a first-class part of the page, because it
  is how a reader checks the story against the diff.
- **Updates were flat.** A rail and a dot, but no sense of a history with a beginning and
  an end, and no author on any note.
- **The outcome looked like every other section.** A merged PR has a moment — the purple
  banner. Reading a finished record, nothing told you it had landed.
- **The list was a table.** Three-line rows with a two-line excerpt containing raw
  markdown (`*already finished*` rendered with the asterisks), a fixed sort by recency, no
  tag filter, no keyboard, and no answer to "what is happening right now" without reading
  every row.

Rejected: **big body headings** for What/Why/How, the way a PR renders `## Summary`. The
record's own prose already uses headings inside those sections; adding 20px section titles
above them produced three competing heading levels on one page. Small caps labels with a
hairline out to the column edge keep the structure legible and let the writing be the
loudest thing on screen, which is the Linear reading of the same problem.

Rejected: **an excerpt line in the list rows**. It is the reason the old list held four
records per screen. Density is what makes a list scannable; the excerpt is one click away.

## How

Three decisions carried the work.

**Status is one language everywhere.** `WorkStatusPill` (dot + label) on record pages and
group headers, `WorkStatusDot` (dot alone) in list rows, the same three colours from
`tokens.css`. In progress is the only status that gets a halo, because it is the only one
that is still happening.

**The timeline includes the ends.** The Updates section renders a start node, one card per
update, and a terminal node whose colour and words come from the status: "Marked done" in
green, "Abandoned" in grey, "Still in progress" in blue with the elapsed time. A record
with no updates yet still gets a timeline, plus a line saying which command posts one — so
the empty case teaches instead of looking broken.

**The markdown renderer had a hole.** Agents write incident timelines and terminal
transcripts as four-space indented blocks, which the parser treated as paragraph text: it
joined the lines and destroyed the only structure they had. 85 such lines exist across 14
records in this vault today. Indented blocks now parse as code, which also fixed the two
bug reports where a `pg_stat_activity` dump had been flattened into a sentence.

Cross-references were the other half: `WORK-`/`BUG-` ids in prose are matched outside code
spans and rendered as links into the same project, including inside `**bold**`, so the
"what to read instead" paragraph of an abandoned record is navigable rather than a
suggestion to use the search box.

## For humans

A work record's page is where a person finds out what an agent did and decides whether to trust it. Held up against a merged pull request — the page programmers use to review a change before it lands — ours lost on plain things. The files an agent touched sat in a narrow side column in the smallest type on the page. Nothing on a finished record told you it had finished. The list fitted four records to a screen, each row padded with a two-line preview.

**`src/pages/WorkDetailPage.tsx`, the page for one record, now opens with a sentence saying where it stands.** That sentence gives the status, the agent and the date, over a strip of facts. The files moved into the body. The notes an agent left are drawn as a timeline opening on "started this work" and closing on "Marked done". The finished summary sits in a card with a green band across the top.

**`src/pages/WorkListPage.tsx` gives each record one line**, grouped into running, done and abandoned, with filters that narrow as you type. The preview line went, because it was what kept the count at four.

**The worst problem was not the layout, it was the reading.** Agents write incident timelines and terminal transcripts as blocks indented by four spaces. `src/lib/markdown.tsx`, the code that turns a record's text into a page, treated those as ordinary paragraphs and joined the lines. That destroyed the only structure they had.

`grep -c '^    [^ ]'`, a count of the lines that start with four spaces, found 85 of them across 14 records here. Two bug reports had a `pg_stat_activity` dump — a printout of what a database was busy with — flattened into a sentence that way. Indented blocks are kept as written now.

It is like a train timetable retyped as a sentence: every time is still there, and the columns that made it usable are gone.

**A record that names another record now takes you to it.** Agents write ids like `WORK-0007` in the middle of a sentence; an abandoned record's "read this instead" line is exactly that, and it used to leave you to go and search for it. Those ids are links to the record they name now, in bold text as well as plain. An id sitting inside quoted code is left alone, because there it is an example, not a pointer.

**I read the screenshots instead of only taking them.** In the browser I compared how wide each file path wants to be with the room it has. That covered every path in the files card, across three records, and none is cut short.

**The photographs had been showing the thinner project.** `npm run screenshot`, the command that captures each screen, took whichever project came first; it takes the one with the most records now, and you can name the project and the record you want. Each record page is captured twice: at window size, which is the one to judge, and as one tall image of the whole record, which is the one to read. Naming a project or a record that does not exist stops the run and prints the ones that do.

Not done: the tag filter takes one tag where it should take several.

Spacing is writing too, and a page that closes it up has edited you.
