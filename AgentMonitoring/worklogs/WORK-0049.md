## What

Live updates for the App feedback board. Desktop: src-tauri/src/lib.rs arms one extra
watcher on ~/.AgentMonitoring/feedback at startup (created first so an empty machine
still gets one), held in WatcherState.feedback so roster rewrites cannot drop it; it
emits feedback-changed, which src/lib/api.ts now subscribes to beside project-changed.
Browser: the /project-api/cursor stat walk in scripts/project-fs.mjs also stats the
board's FB-*.md files, resolving the dir exactly as core's feedback_dir() does
(AGENTMON_REGISTRY_DIR override, then home).

## Why

FB-0001: the app watched only project folders, so an agent filing feedback via CLI/MCP
did not move the board or the sidebar count until some unrelated record write refreshed
the app. The board existing to catch friction and then sitting stale is the friction.

## How

The existing debounced watcher (spawn_store_watcher) is reused as-is — the board is a
bare folder with no project.json, and the id in the change payload is simply None. A new
Rust test pins that shape; a node check pins that the cursor moves when an FB file lands
in a sandboxed registry dir. Everything downstream is free: feedback-changed feeds the
same app-wide nonce every screen already reads.

## Outcome

Feedback filed via CLI/MCP now refreshes the board and sidebar count live: dedicated Rust watcher on ~/.AgentMonitoring/feedback emitting feedback-changed (desktop), FB-*.md stats folded into the /project-api/cursor hash (browser). Verified: cargo test -p agentmonitoring 10/10 incl. new bare-folder watcher test, node cursor check moves on a sandboxed filing, tsc clean, check:live 19/19. FB-0001 marked done.

## For humans

An agent hits something awkward in this app and files a note about it from the command line. A screen in the app lists those notes, with a count down the side. Neither moved. The note appeared only later, when something unrelated was written and the app redrew. That complaint is `FB-0001` — feedback about this app, filed from inside it.

**The app only watched the folders it had been handed.** It keeps an eye on each project's folder and reacts the moment a file there changes. Feedback notes do not live in a project folder. They sit together in one folder of their own, `~/.AgentMonitoring/feedback`, and nobody was watching that.

It is like a night watchman working from a list of doors. The door that is not on the list never gets tried.

**That folder now has a watcher of its own.** `src-tauri/src/lib.rs`, the desktop app's own startup code, sets it up before the project ones, so it exists even where there is nothing else to watch. It sits in its own slot, so the reshuffle when the project list changes cannot drop it. A file landing there makes the app call out `feedback-changed`, and the screens already listen for that.

**The watching code expects a project, and this folder is not one.** Every folder it had watched before holds a small file naming its project, and the call-out carries that name. This one holds none, so the name goes out empty. I let it, rather than touch the watching code; a new test pins that shape so nobody tidies it away.

**The browser version does not watch. It asks.** `/project-api/cursor` is the question it asks: it looks over the files and compares that with what it saw last time. The feedback notes were not among them. Now they are.

**I filed a note into a throwaway folder and watched that answer move.** An answer that sits still is the whole of `FB-0001`. `cargo test`, which runs every test written against the Rust code, passes ten of ten, the new one included.

**`check:live` passed all 19 of its cases.** It covers the parts of the app meant to redraw themselves while you are looking. When one of those comes back no, people sit reading yesterday's screen and decide on it.

**Feedback filed from the command line now moves that screen and the count while you watch.** `FB-0001` is marked done. The browser half I proved against a throwaway folder, not a real one.

A screen built to collect complaints becomes one if it waits to be asked.
