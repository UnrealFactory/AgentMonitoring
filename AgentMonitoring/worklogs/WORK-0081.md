## What

Stopped the desktop shortcut from re-appearing on every app update. Two layers: src-tauri/src/update.rs now runs the downloaded installer with '/S','/UPDATE' (the NSIS template's own update mode, whose CreateOrUpdateDesktopShortcut skips creation when $UpdateMode = 1), and a new src-tauri/windows/hooks.nsi (wired via bundle.windows.nsis.installerHooks in tauri.conf.json) covers the transition: NSIS_HOOK_PREINSTALL records whether $DESKTOP\${PRODUCTNAME}.lnk existed, NSIS_HOOK_POSTINSTALL deletes it on a SILENT install when it did not — so even the currently-installed app, whose old updater passes only /S, stops resurrecting a deleted icon the moment it installs the next version. Interactive installs are untouched.

## Why

Owner report: every update re-created the desktop icon they keep deleting. Read off target/release/nsis/x64/installer.nsi: the template already supports /UPDATE (GetOptions on $CMDLINE, line ~479) and skips the shortcut in update mode (~line 918), but update.rs's worker ran Start-Process $setup -ArgumentList '/S' only — first-install path every time.

## How

update.rs: one-line ArgumentList change + the assertion updated to demand '/S','/UPDATE' and say why. hooks.nsi: Var + IfFileExists in PREINSTALL, IfSilent + StrCmp + Delete in POSTINSTALL — silent-only so a human clicking through the installer still gets the icon; prior-existence check so a kept icon is never deleted. Verified: cargo test -p agentmonitoring 11/11 (the updated assertion among them); npx tauri build --bundles nsis compiles the hooks (installer.nsi line 31 includes hooks.nsi, POSTINSTALL inserts after the template's silent-path CreateOrUpdateDesktopShortcut call, so the delete runs after any creation); fresh setup exe at target/release/bundle/nsis. Not verified by installing — the NSIS remembered-dir gotcha (handoff note) makes scratch installs on this machine redirect the next real one.

## Outcome

Shipped. src-tauri/src/update.rs runs the installer with '/S','/UPDATE' (template's update mode skips shortcut creation; assertion updated to demand it), and src-tauri/windows/hooks.nsi + bundle.windows.nsis.installerHooks guard the transition: a SILENT install now leaves the desktop exactly as it found it (pre-existing icon kept, absent icon not re-created) while interactive installs keep today's behaviour. Verified: cargo test -p agentmonitoring 11/11; npx tauri build --bundles nsis compiles the hooks (installer.nsi !includes hooks.nsi at line 31; POSTINSTALL inserts after the silent-path CreateOrUpdateDesktopShortcut call, so the guard runs after any creation); fresh AgentMonitoring_1.0.5_x64-setup.exe bundled. Deliberately NOT installed on this machine (NSIS remembered-dir gotcha, see handoff-v1-release). Takes effect for users on the next release they update into; the icon stops resurrecting one update later for copies still running the old /S-only updater — the hook in the new installer covers exactly that gap.

## For humans

Every time the app updated itself, a shortcut icon reappeared on the desktop — even for people who had deleted it. The updater was running the new version's installer in its quiet mode, and that quiet install walked the same path as a first install, icon and all.

**The installer already knew how to behave; nobody was asking it to.** Inside the installer there is a switch, `/UPDATE`, that says "this is an update, not a first install — leave shortcuts alone". Our updater passed only `/S` (the quiet switch) and never `/UPDATE`. One line in `src-tauri/src/update.rs` now passes both.

**The copy already on people's machines needed a second net.** That copy still runs updates the old way, with `/S` alone — it downloads the NEW installer though. So the installer itself gained a small rule (`src-tauri/windows/hooks.nsi`): before installing quietly, note whether a desktop icon exists; afterwards, if it had not existed, remove the one the quiet install just made. A person clicking through the installer by hand still gets the icon; a person who kept theirs keeps it.

**Checked without gambling the machine.** The app's own tests pass (11 of 11, including one that now insists on the `/UPDATE` switch and says why), and the freshly built installer provably contains the new rule in the right order — the cleanup runs after the step that would create the icon. Actually installing it was skipped on purpose: this computer's installer remembers install folders in a way that would misdirect the next real install.

An icon you delete now stays deleted through updates, starting with the very next one.
