## What

Make [[note-name]] written in record prose render as a linked chip to that note, the way WORK-/BUG- ids already do.

## Why

Live vaults already write it: ElmwoodOnline's UnrealNetCore project keeps a memory-map note whose index rows say [[unrealnetcore-mission-decisions]], [[unrealnetcore-queue]] — and the renderer shows them as dead literal text. Agents reach for the Obsidian-style link naturally; the app should honour it. Bare kebab words in prose stay unlinked (false-positive risk, recordPath's old reasoning) — the double brackets are the explicit opt-in.

## How

Add a [[...]] token to INLINE_RE in src/lib/markdown-parse.ts constrained to the note-name shape (2-64 alnum/hyphen, no edge hyphens), emit the existing ref inline node; the renderer, titles map, recordPath and recordKind already handle kebab note names end to end. Fixtures in scripts/markdown-smoke.mjs; document in SPEC.md notes section + docs/AGENT_MANUAL.md.

## Outcome

**Root cause.** The inline grammar had no [[...]] token: WORK-/BUG- ids linkify via REF_RE, but a note's kebab name in prose was deliberately never matched (false-positive risk), so the explicit [[note-name]] spelling agents actually write — ElmwoodOnline's unrealnetcore-index memory-map note — rendered as dead literal text.

**Fix**, in src/lib/markdown-parse.ts: a new WIKILINK_RE alternative in INLINE_RE, constrained to the note-name shape core validates (2–64 alnum/hyphen, no edge hyphens), emits the existing ref inline node with a wiki flag; matched by WIKILINK_RE in the dispatch rather than a startsWith, because [[label](url) is a link whose label opens with a bracket. inlineText flattens a wiki ref back to [[name]] — the sweep found Korean particles welded to the brackets (unrealnetcore-queue]]의) and eating them is data loss. Renderer, titles map, recordPath and recordKind already handled kebab names end to end, so chips, tooltips, context menus and the unknown-name state work unchanged.
