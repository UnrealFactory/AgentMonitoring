## What

Tighten the Updates/Comments entry boundary in both parsers. `entries()` in
agentmon-core/src/body.rs (and its twin in scripts/project-fs.mjs) now opens a new
`###` entry only when the heading starts with a date (`2026-08-21…`), the shape every
stamp the CLI writes has. A `###` an agent puts inside its message stays in that
update's body.

## Why

ElmwoodOnline's WORK-0007 carries an update whose message begins with "### R7 빌더 — …".
The old splitter promoted it to a fourth entry whose "timestamp" was that sentence: the
app drew "— · —" for its clock (the user asked whether that was a bug — it is), and
because entry timestamps are compared as strings, "R7…" > any ISO stamp, so it also
hijacked the record's lastActivity and sort position on both transports.

## How

`entries()` takes an `is_entry` predicate; `work_updates` and `bug_comments` pass
`starts_with_date` (first ten chars are `NNNN-NN-NN`). Same regex gate in the JS twin.
Records are untouched — WORK-0007 now reads as three updates with the R7 subheading
rendered inside the third. Verified: cargo test -p agentmon-core (new test included),
the real WORK-0007 through both the JS reader (3 updates, sane lastActivity) and
`agentmon work view`, check:keys 256/256, markdown smoke 418.

## Outcome

Updates/Comments split only on date-shaped ### headings in core and the JS twin; WORK-0007-style records show every note with its clock and correct lastActivity. cargo test green incl. new regression test, real-file check on ElmwoodOnline WORK-0007 (3 updates, all ISO), check:keys 256/256, smoke 418. Release CLI rebuilt.

## For humans

A progress note on `WORK-0007` appeared with "— · —" where its date and time belong. That record is a work log belonging to another project, ElmwoodOnline. The owner asked whether that was a bug. It was.

**Notes get cut apart at headings, and an agent had written a heading of its own.** The notes on a record sit one after another in a plain text file. Each opens with a heading line holding the time it was written. The program started a new note at every line beginning with `###`, the mark for a heading of that size.

**One agent opened its message with `### R7 빌더 — …`.** The program cut there and made a fourth note, whose time was that sentence.

**A sentence then behaved like a time.** These times are put in order by comparing them as plain text, character by character. That sentence starts with a letter, and a letter comes after every digit, so it outranked every real stamp on the record. The invented note became the record's most recent activity. It dragged the "last active" time and the record's place in the sorted list with it, in the desktop app and the browser version alike.

It is like filing letters by the first character alone: everything starting with a letter ends up behind everything starting with a number.

**A note now starts only where the heading starts with a date.** That is the shape of every stamp this tool writes, and a heading an agent puts inside its own message stays inside that message. I changed both readers of these files: `agentmon-core/src/body.rs` behind the desktop app, and `scripts/project-fs.mjs` behind the browser version. Nothing stored on disk was edited.

**I read the real record back through both of them.** `WORK-0007` comes out as three notes now, each with its own clock, and the same sensible "last active" time either way. A new test holds the boundary in place, and `cargo test` over the reader is green.

**The test is the date at the front, and nothing more.** A heading written inside a message that does begin with a date is still read as the start of a new note.

A timestamp that can lose a comparison to a sentence was never really a timestamp.
