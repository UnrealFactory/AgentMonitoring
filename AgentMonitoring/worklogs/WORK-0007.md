## What

The P3 pieces — bug board (`src/pages/BugsPage.tsx`) and bug record
(`src/pages/BugDetailPage.tsx`) — rebuilt to the vscode-issues bar for content and the
linear.app bar for design, plus three carry-over fixes from the P2 critics that live in
code both pairs of pages share.

Carry-over, shared:

1. `src/lib/markdown.tsx` split into a pure parser (`src/lib/markdown-parse.ts`) and a
   renderer, with three data-fidelity rules: an ordered marker interrupts an open
   paragraph only when the number is 1 (CommonMark), a list that starts at N renders
   `<ol start={N}>`, and inline parsing recurses inside `**bold**`/`*italic*`/link labels.
   `scripts/markdown-smoke.mjs` runs the parser under plain node against fixtures taken
   from the vault and then sweeps every record in it.
2. Row collapse for both lists, driven by container queries on `.work-rows`: tag chips go
   first, then the agent name (avatar and tooltip stay), then the severity word and the
   comment count. `.work-row-title` gets `min-width: 30ch`.
3. A shared Related block (`src/components/Related.tsx`) used by the work record and the
   bug record: refs with id, title and status, *and* incoming references — every record in
   the project whose `refs:` point back — each side under its own relationship label.

P3 proper:

- Bug board: Open/Resolved/All with live counts, filters for severity, label, assignee,
  reporter and free text, severity as one coloured pill everywhere, dense single-line rows
  (severity, id, title, labels, reporter → assignee, comments, age), grouped by state with
  open groups sorted by severity then recency, three designed empty states, and the work
  list's keyboard model.
- Bug record: report rendered as a document, the claim moment as an event in the thread,
  comments as a real conversation, a status strip (filed → claimed → resolved with the
  gaps between), and the resolution as a merged-PR-style banner naming who fixed it, when,
  and how long it had been open.

## Why

The bug pages were the two screens P0 left roughest: the board was a two-line list with a
severity dot and no filters beyond severity/label, and the record printed Report, then
comments, then Resolution as three flat sections of equal weight. Against
github.com/microsoft/vscode/issues that loses on both counts — no assignee or reporter
filter, no sort a triage screen can defend, no visible claim, no comment count — and
against linear.app it read as a different, older product than the work pages P2 had just
rebuilt.

The carry-over items are shared code, so leaving them to P2 would have meant shipping the
bug pages on top of a renderer that silently rewrites numbers (the WORK-0005 case: a
wrapped sentence ending "…503 for three hours, then / 200." rendered as a list item "1.",
deleting the 200) and a row that sacrifices its title first when the window narrows. Both
defects would have been inherited by the bug pages verbatim.

The Related block is the same argument in the other direction: `refs:` is a relationship
and a relationship has two ends. A reader of WORK-0005 could not see that its follow-ups
became BUG-0008, BUG-0006 and BUG-0003, because nothing on the page reads the index
backwards.

## How

- **Parser.** `markdown-parse.ts` exports `parseBlocks`/`parseInline` and no React, which
  is what makes it testable from node 24 (type stripping) without a test runner. The
  paragraph guard now asks `interruptsParagraph(line)` instead of "does this look like a
  list marker": a bullet may interrupt, an ordered item may only at 1, an empty item never.
  Lists carry `start`, and the renderer emits `<ol start>` only when it is not 1.
  `parseInline` recurses into emphasis containers with a depth cap.
- **Smoke.** Nine fixtures taken verbatim from vault records (the 200 case, a list that
  really starts at 3, `**\`Retry-After\` is ignored.**`, ids inside code spans, indented
  transcripts, snake_case that is not emphasis) plus a sweep that fails if any word of any
  record's source is missing from the rendered output. Verified it has teeth by breaking
  the rule again and watching it fail.
- **Rows.** `.work-rows` becomes an inline-size container, so a row responds to its own
  width rather than to the window's — the sidebar takes 232px of it, and the same list is
  1176px wide maximised and 662px wide at the app's declared minimum. Breakpoints at
  1150 (bug labels), 1100 (work tags), 900 (agent name) and 760 (severity word, comment
  count). The bug row spends less on every other column than the work row does, because it
  carries two more of them.
- **Board.** One `matches(bug, skip)` predicate with the ability to leave one dimension
  out, so a count shown *on* a control is not filtered by that control: the tab counts
  answer "how many will I see if I switch", and the severity chips count what choosing
  each would give. Grouping by state reuses the work list's group header; sorting is
  severity rank then recency inside open groups and closed-date inside closed ones.
- **Record.** The status strip is the only place the three dates appear — the header fact
  strip and the sidebar's date rows were deleted rather than repeated. The thread merges
  the claim event and the comments into one chronological list, and when a resolution
  banner follows, the thread's closing node hands over to it instead of restating it.
- **Keyboard.** `src/lib/useListKeyboard.ts` is now the one implementation for both lists,
  so they cannot drift apart.

## Updates

Renderer split and the fidelity rules are in. `src/lib/markdown-parse.ts` is pure data — blocks plus an inline tree — and `markdown.tsx` is now only the React mapping, which is what lets `scripts/markdown-smoke.mjs` run the real module under node with no test runner and no bundler.

The rule that mattered: an ordered marker interrupts an open paragraph only when the number is 1. WORK-0005's update 1 wraps as "…receiver returns 503 for three hours, then" / "200. Fixtures cover that case, a list that genuinely starts at 3 (now `<ol start={3}>`), nested `code` inside bold, ids inside code spans staying literal, and indented transcripts keeping their columns. The sweep then reads every record in ./vault and fails if any word of the source is missing from the render: 55 checks, all green.

Checked the check: reverting the rule to "any number interrupts" makes the fixture fail with the 200 gone from the output, so the smoke has teeth rather than agreeing with whatever the parser does.

### 2026-08-18T14:52:00Z

Board and record are rendering against the relay project, and the row collapse is measured rather than eyeballed.

Counting titles whose `scrollWidth` exceeds their `clientWidth` on /p/relay/work, the widths the P2 critic used: 1440 → 1/12 clipped (worst title still 93% visible), 1280 → 1/12 at 95%, 1152 → 1/12 at 96%, 960 → 8/12 but never below 66% and never below the 30ch floor. The critic measured 9/12 at 1280, 12/12 at 45% at 1152 and 12/12 with one glyph left at 960, so the order of sacrifice is now chips first and title last. No row overflows its container at any width I tested, on either list.

Container queries rather than media queries, because the row's problem is its own width: the sidebar takes 232px and the page padding another 64, so a 1440px window gives a 1142px row. One catch worth writing down — a container query and a plain rule of the same specificity are settled by source order, so the collapse block has to sit after every base column width or it silently loses.

Bug rows drop their labels one step earlier than work rows (1150 vs 1100) because they carry two more columns; at 1440, the default window size, that buys zero clipped bug titles.
