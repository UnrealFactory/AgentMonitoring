## What

Round 4 of the bug board, and one defect: every count printed on a filter control now counts
what choosing that control would put on the screen, and a new gate clicks all of them to
prove it.

- the bug board's four filter menus (severity, label, assignee, reporter) and the work
  list's two (agent, tag) hint with counts scoped to the current view, exactly like the
  severity chips already did (BUG-0010);
- the severity chips and the severity menu are now literally the same array of numbers, so
  they cannot drift apart again;
- an option with nothing behind it in this view keeps its place in the menu but is dimmed,
  so the reader can see before clicking that `cdn 0` will empty the board;
- `scripts/check-counts.mjs` (`npm run check:counts`) is a new gate: for every project, on
  both triage screens, in four filter states, it reads the number on every tab, chip and
  menu option, clicks it, counts the rows, and fails if they differ.

This continues WORK-0009. A new record rather than an update to it because
`agentmon work update` refuses to touch a finished log — the deviation is recorded in the
outcome, as CLAUDE.md asks.

## Why

The board opens on `relay` showing two rows. Its severity menu offered Critical 2 · High 4 ·
Medium 2, and forty pixels below it the chip row read Critical 0 · High 1 · Medium 1. Same
filter, two controls, a different number for every value, both visible at once — and taking
the menu at its word emptied the screen: severity=critical promised 2 and landed on "No bugs
match these filters". `All reporters` offered nova 1 · patch 1 · quill 2 · sable 4, which is
the whole project's eight bugs, on a tab holding two.

That is the same defect as BUG-0005, which was fixed for the work list's status tabs in an
earlier round and skipped for the menus beside them. Worse, this file's own comment states
the rule it broke — "a count shown *on* a control must not be filtered by that control" —
so the piece was arguing with itself in the same screen.

It is the kind of failure that survives every check this repo had: the types are right, the
build is green, the screen is well laid out, and only a reader who clicks twice discovers
that the numbers were furniture. The two bars refuse it from opposite directions — GitHub's
issue filters carry no counts in the Labels/Assignees/Author menus at all, and Linear's are
scoped to the view — so printing a project-wide total was the one option neither bar allows.

## How

`matches(record, skip)` on both pages already knew how to leave one dimension out of the
predicate; it only knew two dimensions on the board (tab, severity) and one on the work list
(status). It now knows all of them, and one helper reads the rule out loud:

    const facet = (dim, has) => bugs.filter((b) => has(b) && matches(b, dim)).length;

Every menu hint goes through it. The severity chips and the severity menu share one
`severityCounts` array rather than two expressions that happen to agree, which is what makes
the round-3 drift structurally impossible rather than merely fixed.

The option *lists* are still built from the whole project, deliberately: a menu that drops
entries as the view narrows is a menu that moves under the cursor, and "quill 0" answers the
reader's question better than a missing line. `Select` dims an option whose hint is zero,
except when it is the current choice or under the cursor — the one line the reader is
looking at has to stay legible.

## Updates

### 2026-08-18T19:46:00Z

Both screens scoped, and the gate that was supposed to prove it now does.

`facet(dim, has)` on `BugsPage` and `WorkListPage` runs every menu hint through the same
`matches(record, dim)` the chips use, so the six menus, the four chips and the tab counts are
one rule with one implementation. The severity chips and the severity menu are the same
`severityCounts` array, not two expressions that agree by luck.

`scripts/check-counts.mjs` drives the real app: for each project, on the board and the work
list, in four filter states each (default, dense, one with another filter already narrowing
the view, one with a search query), it reads the number on every tab, chip and menu option,
clicks it, counts the rows and compares — then puts the control back the way a reader would
and checks the view returned to where it started. An option that is already the current
choice is not clicked; its number is compared against the rows in front of the reader.
594 counts, all honest.

Proof the gate is not decorative: reverting one hint to `bugs.filter((b) => b.reporter === r)
.length` turns it red with 11 mismatches on relay alone, naming the critic's exact numbers —
"reporter=sable: the control offers 4; choosing it gives 1 row(s)". Reverted back.

## Outcome

Shipped. Every number printed on a filter control on both triage screens is now the number of
rows you get after choosing it, and a gate clicks all 594 of them to say so.

**The menus were counting the project; they count the view now** (BUG-0010). On relay's
default board — Open tab, two rows — `All severities` used to offer Critical 2 · High 4 ·
Medium 2 while the chip row forty pixels below read Critical 0 · High 1 · Medium 1, and
choosing Critical landed on "No bugs match these filters". The menu now reads Critical 0 ·
High 1 · Medium 1 · Low 0: the chip row, exactly. `All reporters` reads nova 0 · patch 0 ·
quill 1 · sable 1 — two, the rows on screen — instead of the project's eight. On the work
list's In progress tab, `All agents` reads nova 1 · patch 0 · quill 0 · sable 1, and choosing
nova gives the one row it promised instead of the four it used to.

**One rule, one implementation.** `matches(record, skip)` already knew how to leave a
dimension out of the predicate; it now knows every dimension (`tab | severity | label |
assignee | reporter` on the board, `status | agent | tag` on the work list), and `facet(dim,
has)` is the single expression every hint goes through. The severity chips and the severity
menu render the same `severityCounts` array rather than two expressions kept in step by hand,
so the specific drift the critic caught cannot be reintroduced in one place and not the other.

**Zero is said out loud.** An option with nothing behind it in the current view keeps its
place in the menu and is dimmed. Dropping it would make the menu move under the cursor as
filters change, and `cdn 0` answers the reader's question better than a missing line; the
dimming is skipped for the current choice and the hovered row, which have to stay legible.

**The gate this defect needed.** `scripts/check-counts.mjs` (`npm run check:counts`) drives
the real app: for each project, on the board and the work list, in four filter states each
(default, the dense All view, one with another filter already narrowing it, one with a search
query), it reads the number printed on every tab, every severity chip and every menu option,
clicks it, counts the rows, compares — then restores the control the way a reader would and
checks the view came back to where it started. It also asserts that the severity numbers the
board prints twice agree with each other, and that "N matches" equals the rows beneath it.
