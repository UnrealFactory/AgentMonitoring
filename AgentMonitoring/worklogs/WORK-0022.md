## What

Three gaps left by WORK-0021, which put this app's own context menu on five record and
project surfaces and missed the two that a reader meets before any list.

1. **The dashboard** — `/p/<slug>`, the route the app lands on — had no menu anywhere.
   Right-clicking the hero row under WORKING RIGHT NOW, the row under UNRESOLVED BUGS or
   any row of the activity feed gave nothing at all, while the identical record row on
   /work and /bugs offered Open / Copy id / Copy title / Copy link.
   `src/pages/DashboardPage.tsx` was the one screen file that never imported
   `useContextMenu`.
2. **The sidebar project switcher** — the card at the top of the shell that names the
   project you are standing in. `Sidebar.tsx` spread the handlers onto the rows *inside*
   its dropdown and onto the vault list below, never onto the card itself.
3. **The Menu key (VK_APPS)** opened the menu and killed it about a millisecond later, so
   the keyboard entry point the component's own header advertises did nothing on every row
   in the app.

Also closed here: the `Related` block on both record pages (rows that are records, with no
menu), and the smaller defect the same critic recorded — Ctrl+K over an open menu left the
palette and the menu on screen together and cost two Escapes to get back to the page.

## Why

The user's report was: right-clicking a project in the sidebar shows the WebView2/Edge
default menu — "새 창에서 링크 열기 / 링크 복사 / 검사" — which offers to open an internal
`tauri://` address in a browser window and to inspect a shipped product. A Linear-grade
desktop app never leaks the browser menu.

WORK-0021 closed that. But a right button that answers on five surfaces and is silent on
the other four is a different failure of the same promise: the reader has to remember which
list they are looking at. The critic put the cost precisely — the dashboard is the default
landing route, so its rows are the first rows anybody right-clicks, and the switcher card
is the most prominent project affordance in the product and the closest thing on screen to
the row the bug was actually filed against. A menu that is present on the small duplicate of
a project 300px down the sidebar and absent on the card naming that same project reads as
broken, not as restrained.

The Menu key mattered for a different reason: it was *claimed*. The component's header says
it is invoked "by Shift+F10, or the Menu key beside the right Ctrl", and an app whose
actions are only reachable with a mouse has hidden them from half its readers. The claim was
false in the shipped desktop window, and the gate that was supposed to hold it up pressed
Shift+F10 and never pressed the Menu key.

## How

**The Menu key.** Chromium — and therefore WebView2 — answers VK_APPS with a `keydown` of
`key: "ContextMenu"` *and then*, about a millisecond later, a synthesized `contextmenu`
event on whatever has the focus; `preventDefault()` on the keydown does not stop it. By then
the menu is mounted and has pulled the keyboard into itself, so that second event lands on
`.ctx-item` inside `.ctx-layer`, whose handler reads it as a right-click somewhere else and
closes. Traced with a MutationObserver on the live app: keydown at t+0, `.ctx-menu` in the
DOM at t+0, Chromium's contextmenu at t+3 with `button: -1`, menu gone at t+4. Shift+F10
sends no such echo, which is exactly why the gate never saw it.

The echo is the same gesture as the keypress, not a new one, so `ContextMenu.tsx` now
consumes it once: the keyboard opener sets a short window, and the first keyboard-origin
contextmenu (`button !== 2`) inside that window is swallowed by all three handlers that
would otherwise act on it — the layer's dismiss, the row's opener, and the document-level
suppressor, which would have offered a second "Copy" menu about any selected prose behind
the first. The default is still prevented in every case, so no browser menu appears. Because
the window is consumed rather than merely elapsed, a *second* Menu key press closes the menu,
which is what the key does everywhere else on the desktop.

**The dashboard.** Rows that are about a record get the record menu, built by the same
`useRecordMenu` the work list and the bug board use, so there is one definition of what a
record row offers. A feed line carries only a `ref` — "WORK-0012" — and a summary, never a
title, so the page indexes the work logs and bugs it has already loaded by id and hands that
map to the feed; Copy title on a feed row copies the record's real title, which the line
itself does not print. Nothing was fetched to make this work. On the in-progress rows the
handlers sit on the `<li>` rather than the `<a>`, because the row and the note quoted under
it share one hover surface and read as a single row about one work log. The charts, the
agent table and the range tabs are not records and still open nothing — a menu only where
there is something to do.

**The switcher card.** One spread, and the guard that matters: off a project the card says
"All projects", so there is no single project to act on and no menu — the browser's stays
suppressed there too. Right-clicking the card does not also drop its dropdown open.

**Ctrl+K over an open menu.** `lib/modal.ts` gained a subscription to its own depth counter,
and the menu closes when anything takes the keyboard above it. A menu is the shallowest
thing in this app; a modal stack of two, one of them straddling the other's scrim, was never
the intent. The reader had to press Escape twice, and the first one closed the menu they had
already stopped looking at.

**The gate.** `scripts/check-keys.mjs` now presses the key it used to only claim: the Menu
key opens the menu, the menu survives the echo, the echo comes back `defaultPrevented` so no
Edge menu appears, the keyboard is on the first item, and a second press closes it. Plus the
dashboard's three row kinds by the id each menu names, a chart on the same screen opening
nothing, the switcher card on a project and off one, a Related row, and the Ctrl+K
hand-over. 88 checks before this round, 113 after.

## Outcome

All three gaps closed, plus the Related block and the Ctrl+K nit the same critic recorded.
Filed and resolved as BUG-0020 (the Menu key) and BUG-0021 (the two missing surfaces).

**The Menu key.** `expectKeyEcho()` / `takeKeyEcho()` in `ContextMenu.tsx`. Chromium's
synthesized `contextmenu` (button -1) following VK_APPS is now consumed once by whichever of
the three handlers sees it first — the layer's dismiss, the row's opener, the document
suppressor — and every one of them still prevents the default, so no Edge menu appears on any
path. Because the window is consumed rather than merely elapsed, a second press closes the
menu, which is the desktop's own behaviour.

**Surfaces.** The dashboard's four record-row kinds, the sidebar switcher card, and the
Related block on both record pages. The record menu is still defined once in `lib/menus.ts`;
the dashboard indexes the records it has already loaded so a feed row can copy a title the
feed line does not contain.

**Ctrl+K over an open menu.** `lib/modal.ts` gained `modalDepth()` and `onModalChange()`; the
menu stands down when anything takes the keyboard above it, so one Escape now puts the reader
back on the page instead of two.

**Verified in the real desktop window** — release build, WebView2, Windows 11, driven with
`scripts/win-window.ps1` and screen-grabbed at each step:

* right-click at client 110,88, the exact coordinate the critic recorded as dead: the app's
  own menu, Open/Dashboard, Work/21 work logs, Bugs/1 unresolved, Copy slug/agent-monitoring,
  Archive/records are kept. No Edge menu.
* right-click on the dashboard hero row at 560,249: Open, Copy id WORK-0021, Copy title,
  Copy link /p/agent-monitoring/work/WORK-0021.
* VK_APPS on the focused row: the menu opens, survives the echo, first item highlighted; a
  second press closes it with the focus ring back on the row.
* right-click on empty background at 700,620: nothing at all.

**Gates**, all run here: `npm run build` clean; `check:keys` **113 checks clean** (88 before
this round — 25 new: the Menu key sequence, the dashboard's three row kinds by the id each
menu names, Copy title on a feed row read back from the clipboard and compared with the
vault's own title, a chart opening nothing with the event still prevented, the switcher card
on a project and off one, a Related row, and the Ctrl+K hand-over); smoke 317;
`check:clipping` 483 screen loads clean; `check:urlstate` 30; `cargo test --workspace` all

Screenshots `progress/shots/menu-dashboard.png` and `progress/shots/menu-switcher.png`, shot

**Not done, deliberately.** A right-click *while a menu is open* still only dismisses it
rather than re-targeting to the element under the new cursor. The command palette's result
rows have no menu. And the native menu kept inside text inputs is still Edge's, with its own
Inspect item — that is the sanctioned exception, since paste, undo and the spell checker
cannot be rebuilt honestly by a web app.

## For humans

Right-click a row on the screen this app opens on — the project dashboard — and nothing happened: it was the one screen that never asked for a menu. The same row on the work list had answered since the round before. The card at the top of the sidebar, the one naming the project you are standing in, gave nothing either. A reader had to remember which list they were on.

**The menu now opens on the rows a reader meets first.** Every record row on the dashboard, and that card: the pair filed as `BUG-0021`. A line in the activity list carries only a record's number and a short summary, never its title, so the page looks that title up among the records it had already loaded — copy title on such a line gives the real title, and nothing was fetched to make that work.

**The Menu key opened the menu and killed it a millisecond later** — `BUG-0020`. `VK_APPS` is the key beside the right Ctrl that opens a right-click menu without a mouse. `WebView2`, the browser engine inside this app's window, answers it twice. First as a key press, then a moment later as a right-click aimed at whatever holds the focus.

By then the app's own menu had opened and taken the focus. So that second event read as a right-click on the menu itself, and the menu closed. Refusing the key press does not stop it.

**I watched it happen in the running app.** A `MutationObserver`, which reports every change to a page as it happens, timed it: the menu was there at the same instant as the key press, the echo came three milliseconds later, and the menu was gone at four. The app now expects one echo after a keyboard open and swallows the first that arrives.

It is like a doorbell that rings twice: you answer once and ignore the second ring.

**The check had been pressing the other key.** `Shift+F10` opens the same menu and sends no echo, and that is the one it pressed. Meanwhile the app's own text said the Menu key worked.

**Two more came off the same review.** The block of related records at the foot of a record page is a list of records like any other and had no menu; it has the same one now. And opening the search box while a menu was up left both on screen together, so getting back to the page took two presses of Escape — the first spent closing a menu the reader had already stopped looking at. A menu now stands down the moment anything above it takes the keyboard.

**113 checks, 25 of them new.** `npm run check:keys` drives the app with keyboard and mouse and checks what each key and click does. It presses the key it used to only claim now: the menu opens, survives the echo, shows no browser menu, lands the keyboard on the first item, and closes on a second press. The rest cover the dashboard's rows and the card both on a project and off one.

**I drove the shipped desktop window by hand.** At the exact spot on that card a reviewer had recorded as dead, I got the app's menu and no browser menu.

**A right-click while a menu is open still only closes it**, rather than moving to whatever is under the new cursor.

A gesture that answers on some rows and not others teaches nobody to use it.
