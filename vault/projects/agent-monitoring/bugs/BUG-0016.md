## Report

`cargo test --workspace` failed once out of ~16 runs on this machine, in
`crates/agentmon-core/tests/write_roundtrip.rs`:

    running 21 tests
    test result: FAILED. 20 passed; 1 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.40s

**Which test it was is not known.** The run was piped through `tail -12`, so the summary
survived and the `failures:` block did not — that is the reporting lesson as much as the
defect one.

Repro attempts that did NOT reproduce it, all on the same tree, immediately afterwards:

* `cargo test --workspace` x 4 — 78/78 green every time (9 + 32 + 12 + 21 + 4);
* `cargo test --test write_roundtrip` x 6 sequentially — 21/21 green, 0.56-0.60s each;
* `cargo test --test write_roundtrip` x 4 concurrently (four cargo processes at once, to
  put the temp-dir writes under contention) — 21/21 green in all four.

The failing run was the first `cargo test` issued straight after `npm run check:clipping`
(413 browser page loads), so the machine was under heavy I/O load and the suite took 0.40s
where an idle run takes 0.57s — consistent with a timing- or filesystem-sensitive
assertion rather than a logic error. The suite includes
`concurrent_writers_never_share_an_id_or_lose_an_event`, which spawns real processes and is
the obvious suspect, but that is a guess and the record should not pretend otherwise.

Expected: a test suite that is green is green every time. A suite that fails one run in
sixteen trains everybody to re-run it, and the run where it means something gets re-run too.

Actual: one unexplained failure, unattributed.

Next step for whoever picks this up: run the suite in a loop under load and capture the
whole output, e.g.

    for i in $(seq 1 200); do cargo test --test write_roundtrip -- --test-threads=8 || break; done

with `RUST_BACKTRACE=1` and no `tail`, ideally while a `check:clipping` run is hammering the
disk. If it is the concurrency test, the fix is likely a longer wait or a retry on a
Windows sharing violation, not a change to the write path.
