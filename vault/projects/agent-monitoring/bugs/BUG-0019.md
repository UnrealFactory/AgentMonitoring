## Report

Reported by the user against the shipped desktop build, with a screenshot.

Repro:

1. Open the desktop app (Tauri 2 / WebView2 on Windows).
2. Right-click any project row in the sidebar — the switcher list, or the vault list under
   **Projects**.

Expected: the app's own menu, or nothing at all.

Actual: WebView2's default menu, in the OS language rather than the app's — on the
reporter's machine "새 창에서 링크 열기 / 링크 복사 / 검사" (Open link in new window / Copy
link / Inspect).

Three separate problems in those three items:

* **Open link in new window** targets the app's internal `tauri://` address. There is no
  browser to open it in and nothing useful happens.
* **Copy link** puts that same internal address on the clipboard, so a reader who uses it
  to point a colleague at a project hands over a string that resolves nowhere.
* **Inspect** offers the developer tools of a shipped product.

It is not limited to project rows: nothing in `src/` had ever called `preventDefault` on a
`contextmenu` event (`git grep -i contextmenu HEAD -- src/` = zero hits at 92c36d5), so the
browser's menu was the app's answer to the right button on every element of every screen, in
the desktop build and in browser mode alike. The app draws its own scrollbars, its own
select menus and its own focus rings precisely so that no OS or browser chrome shows
through; this was the one interaction that gave it away.

Severity medium rather than high: nothing is lost, no data is wrong, and every other route
through the app still works. It is "visibly wrong but survivable" — a break of the product's
own promise on an interaction people try in the first minute.

## Resolution

**Root cause.** Nothing in the frontend had ever answered the `contextmenu` event, so the
default action — the webview's own menu — was the app's behaviour on every element of every
screen. It is not a Tauri setting or a WebView2 flag: the fix is a page that says
`preventDefault`, which is why it also reproduces in browser mode and is measurable there.

**Fix.** `src/components/ContextMenu.tsx` mounts one provider above the router
(`src/App.tsx`) that owns a single `contextmenu` listener on `document`, in the bubble phase.
It prevents the default everywhere, with one exception it makes on purpose: inside an
`<input>`, a `<textarea>` or a contenteditable the browser keeps its menu, because paste,
undo and the spell checker live there and a page cannot rebuild them. A right-click inside a
non-empty text selection gets a one-item **Copy** menu drawn by the app, so a reading app
does not lose Copy to its own fix. Because the listener sits after the rows in the bubble
phase, a row that opened its own menu has already prevented the event and this one stands
down.

In place of the browser's menu, the rows that have something to do now open the app's:
project rows (switcher, sidebar, Projects screen) offer Open / Work / Bugs / Copy slug /
Archive — no Delete, the vault is append-only, and the Archive item's hint says `records are
kept` — and record rows and record heads offer Open / Copy id / Copy title / Copy link,
where the link is the app route rather than an internal `tauri://` URL. The menu is a real
`role="menu"`: it takes the keyboard on open, ↑↓/Home/End move, ↵ runs, esc and click-away
close, the focus returns to the row, and Shift+F10 opens it without a mouse.

**Verified.**

* In the real desktop app (Tauri 2 dev build, WebView2, Windows 11), driven with real mouse
  input and photographed: right-clicking the **Relay** row in the sidebar now opens the
  app's menu (Open · Dashboard / Work · 12 work logs / Bugs · 2 unresolved / Copy slug ·
  relay / Archive · records are kept) and no Edge menu appears. The bug's own repro, on the
  build the report was about.
* Same session, same window: right-clicking a record's head opens Copy id / Copy title /
  Copy link and nothing else; **Copy id** put `WORK-0019` on the real Windows clipboard
  (read back with `Get-Clipboard`) and the toast said so; right-clicking empty sidebar
  background produced nothing at all; and right-clicking the command palette's search box
  still produced WebView2's own edit menu (잘라내기 / 복사 / 붙여넣기 / 모두 선택), which is
  the exception working as designed.
* `npm run check:keys` — 88 checks, clean, 42 of them new: that the contextmenu event comes
  back `defaultPrevented` on a row and on empty background and **not** in the search input,
  that the menu carries no Delete, the whole keyboard contract from Shift+F10 onward, edge
  flipping at 960px, and an archive round trip (on a throwaway copy of the vault, never
  `./vault`) proving the records survive it and the undo works.
* `npm run build` clean, `npm run smoke` 305 checks, `npm run check:clipping` 469 screen
  loads clean.
