## Report

Right-clicking any of the twelve rows under ACROSS THE VAULT on /projects opens nothing at
all, and Shift+F10 on a focused one does nothing either. Every other record row in the app
answers with Open / Copy id / Copy title / Copy link.

Steps: open /projects, scroll to ACROSS THE VAULT, right-click any row that names a record
(on the live vault all twelve do: WORK-0022, BUG-0021, BUG-0020 ...). Nothing appears.
Then right-click the byte-identical row on the dashboard's activity feed one screen over:
four items.

The rows are the same component shape as the dashboard's — `ol.vault-feed` of
`a.feed-row.tone-*`, the same icon/actor/verb/ref/summary/time layout, the same
`refHref(slug, event.ref)` destination (src/pages/ProjectsPage.tsx, VaultFeedRow) — and the
dashboard's copy (src/pages/DashboardPage.tsx, FeedRow) was wired in WORK-0022 while this
one was not. src/lib/menus.ts enumerated the surfaces in its header and this screen was
simply not in the list.

The failure is silent, which is what makes it worse than a missing feature: the
document-level suppressor in ContextMenuProvider still calls preventDefault, so the reader
gets no menu, no browser menu and no feedback of any kind. Somebody who learned the gesture
on the dashboard finds it dead here and cannot tell whether they mis-clicked.

/projects is the permanent sidebar destination, the screen the app falls back to when a
vault is empty or will not open, and the only place records from every project appear
together — so this is also the only feed in the product whose Copy link would carry a
project other than the one the sidebar is standing in.

Same defect class three rounds running: the round that introduced the menu shipped five
surfaces, the next was failed for the dashboard and the switcher card, and this is the
fourth activity feed in the product, left behind.

Two lesser holes of the same shape, found with it and not charged separately: the record
head's project breadcrumb (`a -> /p/<slug>`, on every work log and every bug) opens no
project menu, and a record id written into prose (`a.ref-inline.mono ->
/p/<slug>/work/WORK-0021`) opens no record menu while the Related row naming that same
record 200px below it does.

## Resolution

**Root cause.**

The menus were wired surface by surface from a list kept in a doc comment
(`src/lib/menus.ts`), and `VaultActivity`/`VaultFeedRow` on /projects was never in that
list. Nothing in the code marked the omission as a decision — the header enumerated "a
record in nine" and this screen was simply absent — so each round closed the surfaces its
critic named and left whichever one nobody had looked at yet.

The silence is the suppressor doing its job: `ContextMenuProvider`'s document handler calls
`preventDefault` on every contextmenu the app does not answer, which is what keeps Edge's
menu out of the window. A row with no menu of its own therefore produces nothing at all, so
a missing wiring looks exactly like a deliberate "nothing here".

**Fix.**

`src/lib/menus.ts` now opens with the rule rather than the list: every link to a project
opens the project menu, every link to a record opens the record menu. The surfaces are still
enumerated under it, explicitly as not-the-contract.

`VaultFeedRow` (src/pages/ProjectsPage.tsx) builds its `RecordRef` from the same `refHref`
test that decides where the row goes, so the row's destination and the menu's Copy link
cannot disagree; rows about the project itself open `useProjectMenu`. Archive from there is
answered by the toast, not by this screen's undo bar, because the bar is at the top of a page
whose feed is at the bottom.

Copy title needed a title this screen never reads — an event carries a summary, not a title.
`RecordRef.title` is now optional and `useCopy` takes a promise for its value, so Copy title
reads that one record when it is clicked and reports a failed read as a sentence. The item is
therefore present, in the same position, on every copy of the menu.

The two lesser holes in the report are closed the same way: the breadcrumb at the head of
every record takes the project menu (`useCurrentProject()`), and a record id in prose takes
the record menu through a factory passed down the markdown render options — except on an
`is-unknown` chip, where the app has read the project and no record answers to that id.

**Verified.**

`npm run check:keys` — 126 checks, clean (was 88). New: a vault-feed row opens the record
menu named for its ref with the same four items the dashboard row has; the browser's menu is
suppressed on it; Copy link's hint equals the row's own href and the slug in it belongs to
the project the row prints (this screen has no project in its URL); Copy title puts the
record's real title on the clipboard, compared against the vault API; Shift+F10 on the
focused row opens the same menu with the keyboard on its first item, and esc hands focus
back to the row; a project-event row opens the five-item project menu (checked on the
12-project scratch vault, where the newest events are project creations); the breadcrumb
opens the project menu while the Work crumb beside it opens nothing and no browser menu
either; an id in prose opens the record menu.

Driven in the real desktop window (WebView2, `npm run tauri:dev`, live vault): right-clicking

row prints. Shift+F10 on the same row opens the menu under the row's leading edge. The
