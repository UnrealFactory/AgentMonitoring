## Report

SPEC.md says: "Live updates: Tauri watches the vault (notify crate) and emits events → UI
refreshes." The Tauri shell does not do this yet, so the desktop app renders whatever the
vault contained when a screen was first opened.

Repro (desktop):

1. `npm run tauri:dev`, open the dashboard for `agent-monitoring`.
2. In another terminal, append a record to the vault (today: edit a file under
   `vault/projects/agent-monitoring/`; once P1 lands: `agentmon work start ...`).
3. Watch the dashboard.

Expected: the activity feed and the counts pick up the new record within a second or two,
the way a monitoring tool should.

Actual: nothing changes. The new record only appears after navigating to another screen
and back, which re-runs the loader, or after restarting the app.

The two transports therefore behave differently, which is worse than either behaviour on
its own: browser mode already reloads, because the Vite plugin watches the vault directory
and pushes a full reload over the HMR socket. A human comparing the desktop app with the
browser view sees the browser as the more live one, in the product where "live" is the
whole point.

The frontend seam already exists — `subscribeVaultChanges()` in `src/lib/api.ts` listens
for a `vault-changed` Tauri event and re-runs the loaders — so this is missing backend
work, not a redesign:

- add `notify` to `src-tauri`, watch `<vault>/projects` recursively;
- debounce (an editor or a CLI write produces several events per file);
- emit `vault-changed` with the changed project slug so a screen can decide whether it
  cares;
- re-arm the watcher when `set_vault_path` points the app at another vault.

Scope note: the watcher belongs to the piece that owns the shell and vault portability
(P5 in PLAN.md). Filed now so it is not rediscovered as a surprise during the final gate.
