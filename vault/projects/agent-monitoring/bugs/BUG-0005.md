## Report

The work list's status tabs count the whole project, not what the other filters left, so
the tabs contradict the list underneath them.

Reproduce on the relay project (`npm run dev`, then /p/relay/work):

1. Set the agent filter to `quill`.
2. The list shows 2 rows and the filter summary says "2 matches".
3. The tabs still say **All 12 · In progress 2 · Done 9 · Abandoned 1**, and "Done 9" is
   next to a Done group containing 2 rows.
4. Add tag `signing` on top: 1 row, and the tabs are still 12 / 2 / 9 / 1.

Expected: a count printed on a control counts what choosing that control would give, with
every *other* filter applied — "In progress 0 / Done 2" for quill above. That is what
GitHub's Open/Closed counters do under a label filter, and it is the only reading under
which the number answers a question the reader has ("if I switch tabs, what will I see?").

Actual: the tabs restate the size of the project, which the page header already gives as
"12 records · 2 in progress". Worse, "Done 9" sits directly above a group header reading
"Done 2", so the screen states two different numbers for the same set within 40px of each
other, and the wrong one is the bigger, bolder one.

Source: `src/pages/WorkListPage.tsx`, the `STATUSES.map` in the toolbar —
`s === "all" ? works.length : works.filter((w) => w.status === s).length` — computed over
`works` rather than over the rows the agent/tag/query filters leave.

Filed rather than fixed because the work list is P2's piece and it is being iterated on;
the equivalent on the bug board (WORK-0007) went the other way and computes each count
with its own dimension left out of the predicate, which is a ~10 line shape that would
port over directly.

Severity low: nothing is lost or corrupted, the rows themselves are right, and a reader
who trusts the group headers is not misled. It is a credibility problem rather than a
correctness one — on a screen whose whole promise is that its numbers are the real ones.

## Resolution

**Root cause.** `src/pages/WorkListPage.tsx` computed each tab's number over `works` —
every record in the project — while the rows underneath were `filtered`, so the two
disagreed the moment any other filter was set:

    {s === "all" ? works.length : works.filter((w) => w.status === s).length}

**Fix.** The filter is now one `matches(work, skipStatus)` predicate, the same shape the bug
board already uses, and the tabs count `works.filter((w) => matches(w, true))` — every
filter applied except the one the control itself owns. `filtered` calls the same predicate
with nothing skipped, so the list and the tabs cannot drift apart: there is one definition of
"matching" on the page now instead of two.

**Verified.** The reporter's own repro, driven in the browser against the live vault
(`/p/relay/work`), reading the tabs, the row count and the group headers together:

- no filter: `All 12 · In progress 2 · Done 9 · Abandoned 1`, 12 rows, groups
  `In progress 2 · Done 9 · Abandoned 1` — unchanged, which is the case that must not move.
- agent `quill`: `All 2 · In progress 0 · Done 2 · Abandoned 0`, 2 rows, group `Done 2`.
  The tab and the group header now state the same number; before, the tab said 9.
- agent `quill` plus the search `signing`: `All 1 · In progress 0 · Done 1 · Abandoned 0`,
  1 row, group `Done 1`. Before: 12 / 2 / 9 / 1.
- `npm run build` green, `npm run smoke` 83 checks.

**Left as it was.** The page header still reads "12 records · 2 in progress" — the size of
the project, deliberately unfiltered, because that line answers "how big is this project"
rather than "what am I looking at". It is the only unfiltered number left on the screen and
it is labelled by its position, next to the title rather than on a control.
