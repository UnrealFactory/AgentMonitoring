## What

The right button now answers on every surface in the app that links to a record or to a
project, and `src/lib/menus.ts` states that as a rule instead of a list, because a list is
what three rounds have now lost a screen from.

Closed here:

1. **ACROSS THE VAULT on /projects** (BUG-0022) — twelve record rows, the same
   `ol.vault-feed > a.feed-row` shape and the same `refHref` destination as the dashboard's
   activity feed, and the only rows in the app the right button did not answer. Right-click
   and Shift+F10 both gave nothing, silently, because the document suppressor eats the event
   either way. A line about a record now opens that record's menu; a line about the project
   itself — created, renamed, which links to `/p/<slug>` — opens the project's. No row in
   that list is dead.
2. **The record head's breadcrumb**, on every work log and every bug: it is a link to the
   project, so it opens the project's menu. "Work" / "Bugs" beside it stay plain — a list
   screen is not a thing there is anything to copy or archive about.
3. **A record id written into prose** (`a.ref-inline`): a link to a record, so it opens the
   record's menu — the same one the Related row naming that record a few hundred pixels
   below already opened. Not offered on an `is-unknown` chip, where the app has read the
   project's records and none of them answers to that id.

## Why

The user's report is still the Why: right-clicking a project in the sidebar showed
WebView2's own menu — "새 창에서 링크 열기 / 링크 복사 / 검사" — which offers to open an
internal `tauri://` address in a browser window and to inspect a shipped product.

The fix for that has been shipping one screen short each round. This round's critic found
the fourth activity feed in the product: "the same class string, the same icon/actor/verb/
ref/summary/time layout and the same refHref(slug, event.ref) record link as the dashboard's
FeedRow that this very round wired ... a reader who learned the gesture on the dashboard
finds it dead here with no feedback." /projects is the permanent sidebar destination, the
recovery screen when a vault will not open, and the only place records from every project
appear together — so it is also the only feed whose Copy link carries a cross-project slug.

The reason it kept happening is that the menus were wired surface by surface from a list in
a doc comment. The list is now subordinate to a sentence — every link to a record opens the
record menu, every link to a project opens the project menu — and the gate measures the
surfaces each round lost.

## How

**Copy title on a screen that never read one.** The vault feed reads events, and an event
carries a summary, never a title. Two wrong answers were available: drop Copy title where
there is no title (the same item meaning different things on different screens), or have
/projects read every record of every project in case somebody right-clicks a row. Instead
`RecordRef.title` became optional and `useCopy` accepts a promise for its value, so Copy
title reads that one record at the moment it is clicked — one file, over the transport the
app already uses, with the failure reported as a sentence rather than a silence. That is
also what lets a prose chip and a breadcrumb offer complete menus with nothing preloaded.

**Wiring.** `VaultFeedRow` builds a `RecordRef` from the same `refHref` test that decides
its own destination, so the menu's Copy link and the row's link can never disagree; rows
that point at the project take `useProjectMenu`. The breadcrumb takes the project from
`useCurrentProject()`. The chips take a factory handed down through the markdown render
options, since `renderInline` is a plain function called in a loop and cannot hold a hook.

**Gate.** `npm run check:keys` grew from 88 to 126 checks: the vault feed's menu, its four
items, its suppression, Copy link carrying the row's own project (checked against the name
the row prints, not against the URL), Copy title fetching a title the screen never read,
Shift+F10 from the focused row and esc handing the keyboard back, the breadcrumb's five
items, the Work crumb beside it opening nothing and no browser menu either, and the prose
chip. The project-event row is checked on the 12-project scratch vault, where the newest
events really are project creations. Which rows are records is read off the destination and
not off the `.feed-ref` chip — a project event carries a ref too (it is the slug), and a
gate that took the chip as the tell would have measured the wrong row.

## Outcome

**Shipped.** The right button answers on every link to a record and every link to a project
in the app, and `src/lib/menus.ts` leads with that as a rule instead of a list of screens.
New this round: the twelve rows of ACROSS THE VAULT on /projects (record rows open Open /
Copy id / Copy title / Copy link; the lines about a project open the project's five items,
so no row in that list is dead), the project breadcrumb at the head of every work log and
bug, and a record id written into prose. `RecordRef.title` is now optional and `useCopy`
accepts a promise for its value, so Copy title reads the one record it needs at the moment
it is clicked — which is what lets a feed line, a chip and a breadcrumb carry complete
menus without any screen pre-reading records in case somebody right-clicks.

**Verified.** `npm run check:keys` — 126 checks, clean (88 before). The new ones measure the
vault feed's menu and its four items, its suppression, Copy link's hint against the row's
own href *and* against the project name the row prints (this screen has no project in its
URL, so a cross-project slug is the whole claim), Copy title against the title held in the
vault, Shift+F10 from the focused row with esc handing the keyboard back, the project-event
row's five items on the 12-project scratch vault, the breadcrumb's menu with the Work crumb
beside it opening nothing and no browser menu either, and the prose chip.
`npm run build` clean · `npm run smoke` 342 · `npm run check:clipping` 504 screen loads ·
`npm run check:urlstate` 30 · `npm run check:counts` 798 · `npm run check:live` 15 ·
`npm run check:vault` 32, ./vault byte-identical after every gate.
Read as pictures, not just as assertions: `progress/shots/menu-vault-feed.png` at 1600 and
the same screen again at 960 (the menu stays whole and inside the window on a row that had
to be scrolled to), plus the breadcrumb and prose-chip menus.
Driven in the real desktop window (`npm run tauri:dev`, WebView2, live vault): a record row
under ACROSS THE VAULT gives the app's four items and no Edge menu; Copy title there put
WORK-0022's real title on the Windows clipboard (`Get-Clipboard`), which is not the summary
the row prints; Shift+F10 opens the same menu under the row's leading edge; and the surface
the user reported — a project row in the sidebar — still gives the app's menu.

**Found by driving it.** Two, both in the tooling rather than the product. The gate's
contextmenu watcher does not survive a navigation, so a check that a *browser* menu was
suppressed was passing on an empty array — it now re-arms after the goto. And
`scripts/win-window.ps1` had no way to scroll, which is how a row below the fold is reached
in the real window; it has a `scroll` action now, with the wheel delta reinterpreted rather
than cast, since PowerShell will not cast a negative number to the unsigned argument
`mouse_event` declares.

**Not done.** The menu still has no submenus and no typeahead, and nothing here needs
either. Copy title shows no hint anywhere — a title is a sentence, not a value that fits a
menu's right edge — and now that the title can arrive after the click, a hint would also
have to be a promise. A right-click on a *selection* still offers only Copy, drawn by the
app, which is the deliberate exception the component's header documents.
