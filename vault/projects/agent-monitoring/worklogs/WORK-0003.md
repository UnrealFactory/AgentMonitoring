## What

The write half of the product. Until now every record in this vault was typed by hand,
because `agentmon` could only read: its mutating subcommands exited 4 with "P1 owns this".

This work log covers:

- `agentmon-core`'s write path — `init`, `project create`, `work start/update/done`, the
  bug lifecycle (`create/claim/comment/resolve`), and one `events.jsonl` line per
  mutation;
- content validation that refuses a work log without `## What` / `## Why` / `## How` and
  a `done` without a real `## Outcome`, printing the template it wanted;
- `agentmon doctor` rewritten as a real integrity checker: corrupt frontmatter,
  id/filename mismatches, duplicate ids, contradictory status transitions, unparseable
  event lines, dangling event refs;
- `docs/AGENT_MANUAL.md`, written so an agent that has never seen SPEC.md can record work
  and run a bug from filing to resolution without a second attempt;
- dogfooding: this record, and BUG-0002 (the desktop live-refresh watcher) fixed and
  resolved through the CLI it documents.

## Why

The vault is supposed to be *written by agents*. Every record in it today was written by
a human-driven editor session against a schema, which is exactly the workflow this product
exists to replace — and it is unverifiable: nothing proved the files agents would write
match the files the app parses.

There is a second reason, less obvious and more important. The bar for this piece is the
gh CLI manual: a fresh agent, given only the manual, has to succeed one-shot. That is only
achievable if the CLI itself teaches — if a rejected body prints the template, if every
error ends with the command that fixes it, and if `--help` carries a worked example for
every subcommand. Documentation alone cannot carry an interface that answers "invalid
input" and stops.

## How

Three rules drove the implementation.

**One writer per project, and never write in place.** Two agents appending at once is the
normal case here, not the edge case. Id allocation and every read-modify-write happen
under a `create_new` lock file (`.agentmon.lock`, stolen after 120s so a killed process
cannot freeze a vault); record files are written to a temp file and renamed over the
target, so a reader sees the old file or the new one and never a half-written one; and
`events.jsonl` lines are appended with a single write of a single line, which keeps the
log readable even by a reader holding no lock.

**Validation belongs in core, not in the CLI.** `agentmon-core` owns what a valid body is
and which state transitions are legal; the CLI only maps errors to exit codes and prints.
That is what lets the tests assert on the rejection text rather than on a binary's stderr.

**Forward compatibility is a write-path problem.** The reader was already lenient about
unknown keys, but a lenient reader plus a rewriting writer still loses data: the first
`work update` would drop any frontmatter key this build does not know. Every rewrite now
carries unknown keys and unknown body sections across untouched.

## Updates

### 2026-08-18T11:54:10Z

Write path and doctor are in, and the CLI is dogfooding itself: this note was appended by
`agentmon work update`, and the record it is appended to was created by `agentmon work start`.

Two decisions worth recording, both made after seeing the alternative fail:

**The rejection message carries the template.** The first version of `work start` answered a
bad body with "body is missing required sections". That is the failure mode the gh manual
bar exists to prevent — an agent that gets it wrong learns nothing about the shape it should
have written. A rejection now prints what is missing, the full expected structure, and a
copy-pasteable command that would have worked, so the second attempt is informed rather than
a guess.

**Rewrites preserve what this build does not understand.** The reader was already lenient
about unknown frontmatter keys, but leniency in the reader is worthless if the writer drops
them: the first `work update` on a record written by a newer build would silently delete its
keys. `body::extra_frontmatter()` carries unknown top-level keys across every write, and
unknown `##` sections keep their position in the body. There is a test that writes
`reviewers: [human-1]` into a record by hand and asserts it survives a CLI update.

5 CLI). Left in this work log: BUG-0002 (claimed, watcher implemented, needs verification)

### 2026-08-18T12:03:41Z

BUG-0002 is fixed and resolved through the CLI: `bug claim` → implement → `bug comment`
with the root cause → `bug resolve`. Full trace is on the bug; the part worth keeping here
is that the obvious implementation was wrong in a way only the running app revealed.

A `notify` watcher plus a 250ms debounce is the textbook answer, and it still produced
three `vault-changed` events for one `agentmon work update`. Instrumenting the real
desktop binary showed why: the file events all arrive inside a 10ms burst and coalesce
correctly, but Windows *also* reports a `Modify` on the containing directory for each file
created or removed — and delivers some of those ~260ms later, after the debounce window
has closed. Widening the window would have hidden it on this machine and lost the race on
a slower one. Filtering to paths that are actually readable vault data (`*.md`, `*.jsonl`,
`*.json`, no dotfiles) removes the whole class: directory notifications, `.agentmon.lock`
and agentmon's own `.tmp` files all stop being events by construction.

Two smaller things found while dogfooding, both fixed:

- The event feed ordered ties wrongly. Timestamps have second precision, so several events
  routinely share one; the sort left them in file order, which put the *first* line of a
  tied group at the top of a newest-first feed. Ties now break on append order reversed, in
  `agentmon-core` and in the `scripts/vault-fs.mjs` twin so both transports agree.
- `agentmon project list` now prints the vault path it read. "Which vault did that write go
  to" is the question behind most confused reports, and it was only answerable from the
  empty-state message.

## Outcome

`agentmon` can write. Every command in SPEC.md's CLI surface is implemented, the vault this
record lives in was written by it, and `docs/AGENT_MANUAL.md` is the interface a fresh
agent reads.

**Shipped**

- **Write path** (`crates/agentmon-core/src/write.rs`, 800 lines) — `init`,
  `project create`, `work start/update/done`, `bug create/claim/comment/resolve`, each
  appending exactly one `events.jsonl` line and returning the record *re-parsed from disk*,
  so what a command prints is what a reader will see.
- **Concurrency** (`fsx.rs`) — a per-project `create_new` lock guards id allocation and
  every read-modify-write; records are written temp-then-renamed; event lines are appended
  in one write each. A stale lock is reclaimed after 120s so a killed agent cannot freeze a
  vault. Tested with six threads writing at once: 24 unique ids, 24 events, doctor clean.
- **Content validation** (`validate.rs`) — `## What` / `## Why` / `## How` required at
  start, a real `## Outcome` required at done, `## Report` around a bug, a `## Resolution`
  on resolve, and placeholder text (`TODO`, `n/a`, `fixed`) rejected by name. Every
  rejection prints what is missing, the expected structure, and a command that would have
  worked — exit 4, nothing written.
- **`doctor`** (`doctor.rs`, 680 lines) — walks files directly so one corrupt record cannot
  hide the rest, and reports errors (unparseable frontmatter, id/filename mismatch,
  duplicate ids, done-without-outcome, resolved-without-resolution, in_progress-with-
  finished, finished-before-started, open-bug-with-assignee, malformed event lines,
  non-UTC timestamps) separately from warnings (events pointing at deleted records,
  directories with no project.json, abandoned lock files). Exit 1 on errors, `--strict`
  to fail on warnings too.
- **CLI** (`crates/agentmon-cli/src/main.rs`) — a thin clap wrapper: eight distinct exit
  codes, `--json` on every command (successes are `{ok, id, path, event, record}`, failures
  are `{ok: false, error: {kind, message, exitCode}}`), `$AGENTMON_AGENT`/`$AGENTMON_PROJECT`
  as defaults, `--body-file -` for stdin, and a worked example in every subcommand's
  `--help` — enforced by a test that walks the command tree and fails if a leaf has none.
- **Forward compatibility** — unknown frontmatter keys and unknown `##` sections survive
  every rewrite. A lenient reader is worthless if the writer drops what it does not
  understand.
- **BUG-0002** — the desktop app now watches the vault and live-refreshes. Root cause and
  the Windows directory-event trap are on the bug.
- **docs/AGENT_MANUAL.md** — vault model, binary location, resolution rules, the body
  contract, three copy-pasteable recipes (record work, file a bug, take and fix a bug),
  every command with a synopsis and a runnable example, JSON shapes, an exit-code table,
  and a troubleshooting section keyed by the exact error strings the CLI prints.

**Known gaps, none silent**

- `work_abandoned` and `bug_closed` are legal event types with no CLI verb; SPEC.md's
  command surface does not list one, so adding a subcommand was left as a deliberate
  non-deviation.
- The desktop `invoke()` path still has no automated smoke test over all ten commands (the
  P0 critic's ask). This log adds three `src-tauri` tests and a manual run of the built
  binary against a real vault, which is progress, not closure — it belongs with P5/P6.
- Second-precision timestamps mean several events can share a `ts`; ordering falls back to
  append order, which both readers now agree on, but a burst of writes inside one second is
  ordered by arrival rather than by causality.
- The frontend reloads everything on `vault-changed`. The event carries the changed project
  slugs so a screen can filter, but nothing consumes them yet.
