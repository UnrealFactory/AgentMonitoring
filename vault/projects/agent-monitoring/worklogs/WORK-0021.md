## What

The right button belongs to the app now, everywhere in it.

Two halves. The browser's own context menu is suppressed for the whole document — in the
Tauri webview and in browser mode, the same code — with one deliberate exception: inside an
`<input>`, a `<textarea>` or a contenteditable, where the native menu carries paste, undo
and the spell checker and no web page can rebuild them honestly. And in its place, one
shared menu component wired to the rows that actually have something to do:

* **project rows**, in all three places they appear — the switcher, the sidebar's vault
  list, and the Projects screen: Open (the project's dashboard), Work, Bugs, Copy slug, and
  Archive / Unarchive. There is deliberately no Delete: the vault is append-only, and the
  Archive item says `records are kept` before the click.
* **work and bug rows, and the head of a record**: Open, Copy id, Copy title, Copy link.
  The head has no Open — the reader is already on it.
* **everywhere else: nothing at all.** Not the app's menu, and not the browser's.

Copy writes the clipboard and answers with a small toast that says what landed on it.
Archive answers with the way back the app already had.

## Why

A user reported it against the shipped desktop build, with a screenshot:

> right-clicking a project in the sidebar shows the WebView2/Edge default context menu
> ("새 창에서 링크 열기 / 링크 복사 / 검사" — screenshot confirmed). A Linear-grade desktop
> app never leaks the browser menu.

Every word of that is right, and it is worse than a cosmetic slip. Those three items are
Edge's, in Edge's UI language rather than the app's: "Open link in new window" points at an
internal `tauri://` address that means nothing outside the window, "Copy link" copies that
same address, and "Inspect" offers the developer tools of a shipped product. It is the one
interaction in the app that admits it is a web page in a frame. Nothing in `src/` had ever
called `preventDefault` on a `contextmenu` event (`git grep -i contextmenu HEAD -- src/`
before this work: zero hits), so this was every screen, every element, every build.

The second reason is the smaller one and the reason this is a menu rather than a
suppression: the app is a reading tool whose rows are records, and the two things a reader
of it keeps wanting are *that record's id* and *a way to point somebody at it*. Both were
mouse-only trips through another screen.

## How

**One provider, mounted above the router** (`src/components/ContextMenu.tsx`, wired in
`src/App.tsx`). It owns a single `contextmenu` listener on `document`, in the bubble phase —
deliberately *after* the rows, so a row that opened its own menu has already called
`preventDefault` and this one sees it and stands down. Everything else it prevents. Text
entry it lets through. A right-click inside a non-empty selection (hit-tested against the
selection's own client rects) gets a one-item Copy menu drawn by the app, because taking
Copy away from a reading app would be a worse defect than the one being fixed.

**The menu is a menu, not a popover.** It is a `role="menu"` of real `role="menuitem"`
buttons, so the keyboard goes into it: the first item takes focus on open, ↑ ↓ move and
wrap, Home/End (and PageUp/PageDown, so no key can scroll the page out from under it) jump,
↵ runs, esc and a click away close, Tab closes, and the focus goes back to the row it came
from. The pointer moves the focus rather than painting a second highlight beside it, so
there is exactly one current item however you are driving it. It holds the app's modal lock
(`src/lib/modal.ts`) while it is up, so the list screens' own arrow keys stand down behind
it — the same contract the command palette keeps. Shift+F10 and the Menu key open it from a
focused row, anchored under the row's leading edge rather than at the window corner.

It is positioned at the cursor, measures itself in a layout effect and **flips** rather than
clipping when it would cross the right or bottom edge.

**Two menu builders, defined once** (`src/lib/menus.ts`) — a project row appears in three
places and a record in four, and three copies of a menu is how one of them quietly loses an
item. Hints carry the value that is about to be copied (`relay`, `WORK-0011`, the route), so
the reader knows before the click rather than after.

**Copy link copies the app route** (`/p/agent-monitoring/work/WORK-0011`), not
`location.href`: in browser mode the full URL carries a dev-server port that is gone
tomorrow, and in the desktop app the origin is an internal address. `src/lib/clipboard.ts`
tries the async clipboard API and falls back to the old textarea trick, restoring the focus
it borrows, and reports honestly which happened.

**Archive keeps each screen's own way back.** On the Projects screen the row menu hands the
archive to the page, which raises the undo bar it already had beside the list. From the
sidebar, where there is no such bar, the same action answers with a toast that carries Undo
and — like the bar — waits rather than fading, because an undo that fades is an undo for
people who were already looking.

## Updates

### 2026-08-19T12:05:00Z

Driving the first build in a real browser (Playwright, live vault) found two defects before any gate did, both invisible to a type checker. (1) The menu never took the keyboard: it renders one frame with `visibility: hidden` while it measures itself to decide which way to flip, and a hidden element cannot be focused — so the first item's focus() was a no-op, the focus stayed on the row, and ArrowDown drove the list behind the menu. It renders at opacity 0 instead now, which measures the same and is still focusable. (2) The row handler called stopPropagation, which meant the contextmenu event never reached the document — so the suppression could not be observed at all, by a gate or by anybody. The row now calls preventDefault only and lets the event carry on; handlers bail out if it is already prevented, which keeps the innermost row the one that wins.

### 2026-08-19T12:22:00Z

The new gate caught a third one, and it was mine. I had given the menu the rule the filter menu keeps — close on scroll — which is right for a control anchored to a button in the layout and wrong for one anchored to a cursor. A menu opened on a row that had to be scrolled into view first dismissed itself a frame later, because the scroll that brought the row into view was still being dispatched (check-keys' archive check, on a 12-project vault where the row sits below the fold, failed as 'element is not stable' then 'detached'). Instrumented it rather than guessing: the app's scroll container is 'main', and the event landed after the menu opened. The rule is gone — the full-window layer under the menu means the wheel cannot reach the page anyway, and PageUp/PageDown are now answered inside the menu so no key can scroll it out from under itself. Hovering an item also focuses with preventScroll now, for the same reason.

## Outcome

**Shipped.** The right button is the app's everywhere. `src/components/ContextMenu.tsx` is
one provider, one menu component, one keyboard contract and one toast; `src/lib/menus.ts`
holds the two menus this app actually has, so the project menu is the same object in the
switcher, the sidebar and the Projects screen, and the record menu is the same in the work
list, the bug board and the head of a record. `src/lib/clipboard.ts` writes the clipboard
and says whether it worked. The browser's own menu survives in exactly one place — text
entry — and everywhere with nothing to do, the right button now does nothing at all.

**Deviations from the brief, both deliberate, both visible on screen.** The project menu has
no separate `Dashboard` item: Open *is* the dashboard, so it says so in its hint rather than
appearing twice under two names. And a right-click inside a text selection offers Copy
rather than nothing — suppressing the menu on prose would have taken Copy away from a
reading app, which is a worse defect than the one this closes.

**Verified.**

* The reported defect, on the build it was reported against: the Tauri dev app driven with
  real Windows mouse input and photographed (`scripts/win-window.ps1`, added for this).
  Right-clicking the Relay row in the sidebar gives the app's menu — Open · Dashboard /
  Work · 12 work logs / Bugs · 2 unresolved / Copy slug · relay / Archive · records are
  kept — and no Edge menu. A record head gives Copy id / Copy title / Copy link and no Open.
  Copy id put `WORK-0019` on the real Windows clipboard (`Get-Clipboard`), and the toast
  said `Copied WORK-0019`. Empty sidebar background: nothing. The palette's search box:
  WebView2's own edit menu, still there, which is the exception working.
* `npm run check:keys` — **88 checks, clean**, 42 of them new (`scripts/check-keys.mjs`,
  header updated). They measure the thing the report is about — `defaultPrevented` on a row
  and on background, *not* prevented in the search input — plus the keyboard contract from
  Shift+F10 through esc-returns-focus, edge flipping at 960px, that no menu offers a delete,
  and a full archive round trip with its undo. The archive checks run against a throwaway
  copy of the vault in a temp directory; `./vault` was read and never written by any gate
  (`git status --porcelain vault/` empty after every run).
* `npm run build` clean, `npm run smoke` 305 checks, `npm run check:clipping` 469 screen
  loads clean.
* Screenshots: `npm run screenshot` gained `menu-project` and `menu-record`, shot and read
  at 1600 and at 960. The 960 pass is what caught the last visual defect: `Copy link`'s hint
  was ellipsised to `/p/agent-monitoring/work/WORK-…`, cutting off the id — the identifying
  half of the path, and the same class of defect as BUG-0009. The menu now sizes to print
  the route whole.

**Three defects found by driving it rather than by reading it**, all recorded in the notes
above: a menu that could not take the keyboard because it measures itself behind
`visibility: hidden` (unfocusable — it uses opacity now); a `stopPropagation` that hid the
suppression from the document, so nothing outside the component could observe it; and a
close-on-scroll rule, correct for the filter menu and wrong here, that made a menu opened on
a row below the fold dismiss itself a frame later.

**Not done.** The menu has no submenus and no typeahead — nothing here needs either yet.
`Copy title` shows no hint (a title is a sentence, not a value that fits a menu's right
edge). And the record menu is on rows and record heads only: the dashboard's activity feed
and the Related block still have no menu of their own, though right-clicking them correctly
does nothing rather than opening the browser's.
