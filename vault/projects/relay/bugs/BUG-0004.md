## Report

One slow customer endpoint took the ingest API down for nine minutes this morning. The
workers hold a Postgres transaction open for the entire duration of the outbound HTTP
request, so a black-holing endpoint converts "some deliveries are slow" into "the database
has no connections left for anything else".

Incident timeline, 2026-08-11 UTC:

    06:12  acme-prod endpoint starts timing out (no RST, no response — connections just hang
           until our 30s client timeout)
    06:16  API p99 crosses 30s; /healthz starts timing out
    06:18  liveness probe kills relay-api-0, then relay-api-1 ninety seconds later
    06:19  POST /v1/events returns 503 — customer ingest is now failing
    06:29  scaled workers to 1 replica by hand; API recovers within 40s
    06:41  RELAY_WORKER_CONCURRENCY dropped 32 -> 8, workers back to 3 replicas, all green

Nine minutes of rejected ingest. Those events were never sent to us again by two of the
three customers involved, so this is data loss, not just downtime.

What the database showed at 06:20:

    SELECT state, count(*) FROM pg_stat_activity WHERE usename='relay' GROUP BY 1;
     idle in transaction | 94
     active              |  4
     idle                |  2

    -- and every one of the 94:
    SELECT query FROM pg_stat_activity WHERE state='idle in transaction' LIMIT 1;
     UPDATE deliveries d SET status='in_flight', locked_by=$2, locked_at=now() ...

`max_connections` is 100. Three worker pods at a pool of 32 each is 96, and every one of
those connections was parked in `idle in transaction` waiting for an HTTP request to a dead
endpoint to time out. The API's pool could not open a connection, so `/healthz` (which is
`SELECT 1`) failed, so Kubernetes restarted the API pods, so the reconnect storm made it
worse.

Repro without a customer (I did this on staging afterwards to confirm):

1. `iptables -A OUTPUT -d <receiver-ip> -j DROP` so packets vanish rather than being
   refused — a refused connection fails fast and does not reproduce this.
2. Queue ~500 deliveries for that endpoint.
3. Watch `pg_stat_activity`: `idle in transaction` climbs to the worker pool size within one
   claim cycle and stays there for 30 seconds per batch.

Expected: a slow endpoint slows down deliveries to that endpoint.

Actual: a slow endpoint exhausts the connection budget of the whole system, including the
ingest path that has nothing to do with it.

Severity critical: customer data was rejected, and the blast radius of one bad endpoint is
currently "everything". Mitigations from this morning are still in place
(`RELAY_WORKER_CONCURRENCY=8`), which caps the damage at 24 connections and also caps our
throughput at about a third — so this is holding the whole delivery pipeline down until it
is fixed properly.

## Comments

### 2026-08-11T09:15:00Z — patch

Two more things from the incident that belong on the record before they are lost.

The liveness probe made it worse, not better. `/healthz` does `SELECT 1`, so it fails
precisely when the database is out of connections — which is the moment when restarting the
API is the least helpful thing you can do, because the restart drops the connections it
still had and then queues for new ones behind 94 idle-in-transaction workers. I am splitting
the probes regardless of how this bug is fixed: liveness becomes a process check with no
database in it, readiness keeps the `SELECT 1`. A pod that cannot reach the database should
stop taking traffic, not die.

And we were blind. It took 29 minutes to find `pg_stat_activity` because nothing exports
connection state, queue depth or oldest-pending age. The graph that would have made this
obvious in one glance does not exist. That is my next piece of work and this incident is the
justification I will cite.

For whoever fixes the actual bug: the constraint from my side is a connection budget that
holds when the endpoints are slow, not just when they are fast. Worker pool 32 × 3 pods + API
pool 10 × 2 pods = 116 against `max_connections=100`, which was already oversubscribed
before this morning — it only worked because worker connections were normally returned in
milliseconds. Please write the budget down somewhere, and I will make the pool sizes match
it in the Helm values.

### 2026-08-11T13:10:00Z — nova

Root cause confirmed, and it is one line of structure in `relay-worker/src/dispatcher.rs`:

    let mut tx = pool.begin().await?;
    let batch = queue::claim_batch(&mut *tx, worker_id, 64).await?;
    for delivery in batch {
        let outcome = http_client.send(&delivery).await?;   // <- up to 30s, inside the tx
        queue::release(&mut *tx, delivery.id, outcome).await?;
    }
    tx.commit().await?;

The transaction exists because I wanted the claim and the release to be atomic — if the
process dies mid-batch, nothing is left half-claimed. What I did not think through is that
the transaction is then held across the network I/O, and the connection is unusable by anyone
else for the whole time. With concurrency 32 that is 32 connections parked per pod, for as
long as the slowest endpoint in the batch takes to time out.

The atomicity I was protecting is also worth less than it cost: `claim_batch` already marks
rows `in_flight` with `locked_by` and `locked_at`, so a crash does not lose them — it leaves
a lease that nothing reclaims. WORK-0001 shipped with exactly that as follow-up 1, and this
incident is that follow-up presenting its bill.

The shape of the fix:

1. Claim in its own short transaction and **commit immediately**. The rows are `in_flight`
   with a lease; the connection goes back to the pool in about 2ms.
2. Send with no database connection held at all.
3. Record the attempt and release the delivery in a second short transaction, one per
   delivery, taken after the response (or the timeout).
4. `queue::reclaim_expired(pool, ttl)` sweeps `in_flight` rows whose `locked_at` is older
   than the send timeout plus a margin, back to `pending`, incrementing nothing — a
   reclaimed delivery has not had an attempt recorded, so the ladder position is unchanged.
   Runs every 30s in every worker; it is idempotent and safe to have several of them.

Consequence to be explicit about: at-least-once gets a little more visible. A worker that
dies after sending but before recording will have its delivery reclaimed and sent again. That
is the same guarantee we always documented, it just becomes reachable through a new door —
and the alternative (recording before sending) invents a worse failure, where a delivery is
marked succeeded and never sent.

Connection budget, as asked: worker pool = concurrency + 4 (currently 8 + 4 = 12), api pool
10, so 3 workers + 2 api = 56 of 100 with headroom for a rolling deploy. Writing it into
`docs/operations/connection-budget.md` so it is not folklore.

### 2026-08-12T10:05:00Z — nova

Fix is written and running against the staging repro. Numbers from the same `iptables -j
DROP` setup, 500 queued deliveries to a black-holed endpoint:

    before   idle in transaction peaked at 94 of 100; API /healthz failing after ~4 min
    after    idle in transaction peaked at 3;  API p99 unchanged at 11ms throughout

Delivery to the dead endpoint is exactly as slow as before — 30s per attempt, which is
correct, it is dead — and nothing else in the system notices.

Two details from the implementation worth surfacing here rather than only in the code.

`reclaim_expired` uses `locked_at < now() - $ttl` where the TTL is the send timeout plus 60s
(currently 90s), not a fixed constant, so raising `RELAY_HTTP_TIMEOUT` cannot silently start
reclaiming deliveries that are still in flight — that would produce genuine duplicates rather
than the rare crash-window ones. There is a `debug_assert` tying the two together and a test
that fails if the relationship is inverted.

The attempt row is now inserted in the second transaction, after the response, rather than
before the send. That regresses part of BUG-0001's rationale — an in-flight attempt is no
longer visible as a row while it runs — so instead the *delivery* carries `status='in_flight'`
and `locked_at`, which the dashboard already reads, and `AttemptTimeline` shows the running
attempt from those two fields. sable, this changes what your running-attempt row is built
from; the API shape is unchanged and `finished_at` stays nullable, so it should be invisible
to you, but flag it if it is not.

## Resolution

**Root cause.** `relay-worker/src/dispatcher.rs` ran the claim, the outbound HTTP request and
the release inside one transaction:

    let mut tx = pool.begin().await?;
    let batch = queue::claim_batch(&mut *tx, worker_id, 64).await?;
    for delivery in batch { let outcome = http_client.send(&delivery).await?;   // up to 30s
                            queue::release(&mut *tx, delivery.id, outcome).await?; }
    tx.commit().await?;

A Postgres connection is therefore held, `idle in transaction`, for the entire duration of a
network call to a machine we do not control. With `RELAY_WORKER_CONCURRENCY=32` and three
pods that is 96 of `max_connections=100` parked behind one black-holing endpoint; the API
could not open a connection, `/healthz` (a `SELECT 1`) failed, the liveness probe restarted
the API pods, and ingest returned 503 for nine minutes.

The transaction was there to make claim-and-release atomic across a crash. It was never
buying that: `claim_batch` already marks rows `in_flight` with `locked_by`/`locked_at`, so a
crash leaves a lease, not a lost row — and WORK-0001 shipped with "no lease expiry sweeper
yet" as its first follow-up. This incident is that follow-up presenting its bill.

**Fix**, in `relay-worker/src/dispatcher.rs` and `relay-store/src/queue.rs`:

1. The claim gets its own transaction and commits immediately; the connection is back in the
   pool in about 2ms.
2. The send holds no database connection at all.
3. The attempt row and the release are written in a second short transaction, per delivery,
   after the response or the timeout.
4. `queue::reclaim_expired(pool, ttl)` returns `in_flight` rows whose `locked_at` is older
   than `RELAY_HTTP_TIMEOUT + 60s` to `pending` without advancing the ladder, every 30s in
   every worker. Idempotent, so running it in all of them is fine — and it closes the
   crashed-worker hole WORK-0001 left open.
5. `docs/operations/connection-budget.md` writes the arithmetic down: worker pool =
   concurrency + 4, api pool = 10, so 3 workers + 2 api = 56 of 100 with room for a rolling
   deploy. Helm values now derive the pool size from the concurrency instead of setting both
   by hand, so they cannot drift apart again.
6. From patch on this thread: liveness is now a process check with no database in it,
   readiness keeps the `SELECT 1`. A pod that cannot reach Postgres should stop taking
   traffic, not be killed and rejoin the queue for connections.

**Verified.**

- The staging repro (`iptables -j DROP` on the receiver, 500 queued deliveries): `idle in
  transaction` peaked at **3** connections, against 94 before; API p99 stayed at 11ms
  throughout, where it previously crossed 30s inside four minutes. Deliveries to the dead
  endpoint remain 30s each, which is correct.
- `RELAY_WORKER_CONCURRENCY` restored from the incident mitigation of 8 to 32, and throughput
  is back to 2,900 deliveries/minute per pod from 940.
- `cargo test --workspace` — 71 passed. New: `reclaim_expired_returns_only_stale_leases`,
  `reclaim_does_not_advance_attempt_count`, and a test that fails if the reclaim TTL is ever
  set below the HTTP timeout (which would reclaim in-flight deliveries and manufacture real
  duplicates).
- Killed a worker mid-batch with `SIGKILL`: 41 deliveries left `in_flight`, all 41 reclaimed
  90 seconds later by another pod, no delivery lost and none double-sent, verified against
  the recording receiver.

**Consequence, stated plainly.** At-least-once becomes reachable through a new door: a worker
that dies after sending but before recording will have its delivery reclaimed and sent again.
That is the guarantee we document, and the alternative — recording the attempt before sending
— invents a worse failure in which a delivery is marked succeeded and never leaves the
process. Customers verify with the event id, and the signing guide says so.

**Fallout.** The attempt row is now inserted after the response instead of before it, so an
in-flight attempt is no longer a row. The dashboard's running-attempt display is rebuilt from
`deliveries.status = 'in_flight'` and `locked_at`, which the API already returns; sable
confirmed the screen is unchanged.
