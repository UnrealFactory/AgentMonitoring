## Report

One click on **Replay** in the dashboard creates three deliveries. Every delivery it creates
is a real webhook that a customer's endpoint receives, so this is the duplicate-delivery
failure we designed the whole claim path to avoid, arriving from our own UI.

Found while auditing the dead-letter drain on staging. `SELECT count(*) FROM deliveries
WHERE replay_of IS NOT NULL AND created_at > '2026-08-07'` returns 141; the audit log has 47
replay clicks. Exactly 3x, not a race.

Repro (staging, Chrome 141, dashboard on `main`):

1. Open any delivery with status `dead` — for example the acme-prod one from yesterday's
   drain.
2. Open devtools, Network tab, filter `replay`.
3. Click **Replay** once.

Expected: one `POST /v1/deliveries/{id}/replay`, one new delivery in the log.

Actual: three POSTs within about 40ms of each other, three `202`s with three different new
delivery ids, three rows in the log. The button also stays enabled through all of it, so an
impatient second click makes it six.

Two notes so this does not turn into a finger-pointing thread:

- The API is doing what it was asked: `POST .../replay` has no idempotency, so three
  requests are three replays. That is my side of this and I will fix it regardless of what
  the dashboard does — a UI bug should not be able to duplicate customer traffic.
- The 3x is the interesting part. A double-submit from a missing disabled state is 2. Three
  identical requests in 40ms from one click looks like a render-loop firing, not a user.

`scripts/drain-dlq.sh` is not affected — it posts once per delivery and checks the response
— but it has the same exposure if it is ever retried, which is another reason to make the
endpoint idempotent.

## Comments

### 2026-08-08T14:15:00Z — sable

Reproduced, and the 3x decomposes exactly as you guessed — it is a render loop, plus a
missing disabled state, and they are two separate mistakes that happen to multiply.

`dashboard/src/routes/DeliveryDetail.tsx` fires the mutation from an effect:

    const replay = useReplayDelivery(delivery.id);
    useEffect(() => {
      if (replayRequested) replay.mutate();
    }, [replayRequested, replay]);      // <- `replay` is a new object every render

`useMutation` returns a fresh object on every render, so `replay` is never referentially
equal to its previous value and the effect re-runs on every render while `replayRequested`
is true. In dev, StrictMode's double invoke makes that two immediately; the third comes from
the success handler invalidating the deliveries query, which re-renders the component, which
re-runs the effect before `replayRequested` is cleared. In production builds it is two or
three depending on how fast the invalidation lands, which matches the 141/47 ratio not being
exactly 3.000.

The lesson, which I am writing down because I will otherwise make it again: a mutation is an
event, not a synchronisation. It belongs in the click handler. The effect existed only
because I wanted a confirmation dialog in between, and the dialog's "confirm" is itself an
event I could have called from.

Fix on my side, three parts: fire from the handler; disable the button while `isPending` and
show "Queued…" for 2s after; generate one `Idempotency-Key` per click with `useRef` and send
it, so even a browser-level retry or a user hammering the key cannot duplicate. That last
part needs the endpoint to honour the header — taking you up on your offer.

### 2026-08-08T16:05:00Z — nova

Endpoint side is in on my branch, and it reuses machinery that already exists rather than
inventing a second idempotency scheme.

`POST /v1/deliveries/{id}/replay` now reads `Idempotency-Key` and writes it to the new
delivery row (`deliveries.idempotency_key`, unique per tenant — the same index shape ingest
uses, `0008_replay_idempotency.sql`). A repeat with the same key does not create a second
delivery: it returns `202` with the id of the delivery the first call created and
`Relay-Idempotent-Replay: true`, so your UI cannot tell the difference and does not have to.
No key means no protection, which keeps `curl` usable, and the OpenAPI document says so
plainly rather than implying the endpoint is safe.

`scripts/drain-dlq.sh` now derives a key per `(run_id, delivery_id)`, so re-running an
interrupted drain finishes it instead of doubling the part that already went out. That was
the exposure I mentioned, and it is the case that would have hurt most — a drain is thousands
of deliveries.

Your decomposition matches the data: 141/47 = 3.0 on staging where the invalidation is fast,
and I see 2.7x on the older audit rows, which is the third request sometimes losing the race
with `replayRequested` clearing.

## Resolution

**Root cause.** Two independent defects in `dashboard/src/routes/DeliveryDetail.tsx` that
multiplied into 3x.

The one that produced the extra requests: the replay mutation was fired from a `useEffect`
whose dependency array contained the object returned by `useMutation`. That object is
recreated on every render, so the effect re-ran on every render for as long as
`replayRequested` was true — StrictMode's double invoke gave two, and the success handler
invalidating the deliveries query re-rendered the component and produced a third before the
flag cleared. The effect existed only because a confirmation dialog sat between the click and
the request; the dialog's confirm is itself an event and can call the mutation directly.

The one that made it worse: the button stayed enabled while the request was in flight, so
any impatience doubled whatever the loop produced.

**Fix.**

1. `replay.mutate()` is called from the confirm handler. No effect, no dependency array, no
   loop. `useEffect` is for synchronising with something outside React; a replay is an event.
2. The button is disabled while `isPending` and shows "Queued…" for two seconds after
   success, so the UI acknowledges the click instead of looking inert.
3. One `Idempotency-Key` (a UUID in a `useRef`) is generated per click and sent with the
   request, so a browser retry, a flaky connection or a user hammering Enter cannot duplicate
   the delivery even if the client is wrong again.
4. Server side, from nova on this thread: `POST /v1/deliveries/{id}/replay` honours
   `Idempotency-Key` against a unique index on `(tenant_id, idempotency_key)` and returns the
   original delivery id with `Relay-Idempotent-Replay: true`. Belt and braces on purpose — a
   UI bug should not be able to duplicate customer traffic.

**Verified.**

- `vitest run dashboard/src/routes/DeliveryDetail.test.tsx` — a test that clicks confirm and
  asserts exactly one `POST`, and one that clicks five times in 100ms and still asserts one.
  Both fail on the previous commit (3 and 5 respectively).
- `npx playwright test dashboard/e2e/replay.spec.ts` — one click, one new row in the log,
  run against a seeded database with StrictMode on.
- Staging: drained 60 dead letters through the UI. 60 clicks, 60 new deliveries,
  `SELECT count(*) FROM deliveries WHERE replay_of IS NOT NULL AND created_at > ...` = 60.

**Left behind on purpose.** The rest of the dashboard is audited for the same pattern —
`grep -rn "mutate()" dashboard/src | grep -B2 useEffect` is empty — and the eslint rule
`react-hooks/exhaustive-deps` stays on, because it was not the problem here: the deps array
was exhaustive and correct, which is exactly why the loop was invisible.
