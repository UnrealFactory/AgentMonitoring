## Report

`GET /v1/deliveries` returns 500 whenever the result page contains a delivery that is being
sent right now. It is not a rare race: on staging, with the load generator running, roughly
one request in four fails, and the delivery log screen (WORK-0004) is unusable while traffic
is flowing.

Repro:

1. Point a worker at staging and start the load generator, so there is always at least one
   delivery in `in_flight`.
2. `curl -H "Authorization: Bearer $RELAY_KEY" "https://staging.relay.internal/v1/deliveries?limit=50"`
3. Repeat until it fails; with traffic it fails within a few tries.

Expected: 200 with the page, the in-flight delivery included and its current attempt shown
as still running.

Actual: `500` with

    {"type":"https://relay.dev/errors/internal","title":"Internal error",
     "status":500,"relay_request_id":"req_01J9Z8Q7"}

and this in the API log for that request id:

    ERROR relay_api::routes::deliveries: query failed
      error=error occurred while decoding column "finished_at": unexpected null;
            try decoding as an `Option`

Filtering to `?status=succeeded` never fails, which matches the theory: only rows whose
latest attempt is still open are affected.

Why nobody saw it before: `relay-store/tests/fixtures.rs` seeds attempts that have already
finished, so no test and no local dataset contains an attempt with a null `finished_at`.
Every environment with real traffic has one at all times.

Two things this blocks: the delivery log cannot be demoed on staging, and the dashboard's
error state currently shows a generic "something went wrong", so from a user's point of view
the product is randomly broken with no explanation.

## Comments

### 2026-08-01T16:50:00Z — nova

Confirmed and root-caused, and it is entirely mine.

`relay-store/src/deliveries.rs` maps the attempt join into

    struct DeliveryAttemptRow {
        attempt_no: i16,
        started_at: OffsetDateTime,
        finished_at: OffsetDateTime,   // <- not nullable
        response_status: i16,          // <- not nullable
        duration_ms: i32,              // <- not nullable
        ...
    }

but `relay-worker/src/dispatcher.rs` inserts the attempt row *before* the request goes out —
that is deliberate, it is what makes an attempt visible while it is running and what lets a
crashed worker leave evidence behind. So for the duration of every request, that row has
`finished_at`, `response_status` and `duration_ms` all null. sqlx refuses to decode null
into a non-`Option` and returns `ColumnDecode`, and `From<sqlx::Error> for ApiError` maps
everything to `Internal`, so it surfaces as a 500 with no useful detail in the body.

The `?status=succeeded` filter working is the same fact from the other side: a succeeded
delivery has no open attempt.

Fixing three columns to `Option<...>` is ten minutes. The two things worth doing alongside:
the fixtures need to be able to express an in-flight attempt (`seed_in_flight()`), otherwise
the regression test cannot exist; and `ColumnDecode` should not be indistinguishable from
"the database is down" in our own logs. Taking both.

## Resolution

**Root cause.** `relay-store/src/deliveries.rs` decoded the attempt join into a struct whose
`finished_at`, `response_status` and `duration_ms` fields were non-nullable, but the row is
inserted by `relay-worker/src/dispatcher.rs` *before* the HTTP request is sent — on purpose,
so that an attempt is visible while it runs and a worker that dies mid-send leaves evidence.
For the whole duration of every request those three columns are null. sqlx returns
`ColumnDecode` rather than silently coercing, `From<sqlx::Error> for ApiError` mapped every
sqlx error to `Internal`, and the caller got a 500 whose body said nothing.

It survived to staging because `relay-store/tests/fixtures.rs` could not express the state:
every seeded attempt was already finished, so no test and no local dataset ever contained an
open one, while every environment with traffic contains one at all times.

**Fix**, in four parts:

1. `DeliveryAttempt` now has `finished_at: Option<OffsetDateTime>`, `response_status:
   Option<i16>`, `duration_ms: Option<i32>`; `started_at` stays non-null, as sable asked, so
   the dashboard can compute elapsed time itself.
2. `docs/api/openapi.yaml` marks the three fields nullable and `api-types.gen.ts` is
   regenerated — without that the generated TypeScript would have promised a string and the
   UI would render "Invalid Date" instead of a running attempt.
3. `relay-store/tests/fixtures.rs` gains `seed_in_flight()`, and
   `relay-api/tests/deliveries_list.rs::lists_deliveries_with_an_in_flight_attempt` is the
   regression test — it fails on the previous commit with the exact `ColumnDecode` message.
4. `sqlx::Error::ColumnDecode` now maps to its own log line naming the column and stays a
   500 in the response, but is no longer indistinguishable from "the database is gone" when
   we are reading our own logs. `From<sqlx::Error>` is explicit per variant now instead of a
   catch-all.

**Verified.** `cargo test --workspace` — 52 passed, including the new regression test.
`curl` loop of 200 requests against staging with the load generator running: 200 × 200, no
500s (it failed within four requests before). sable confirmed the dashboard on the branch.

**Worth keeping in mind.** The fixture builder was the actual defect; the type signature was
just where it showed up. Any state a worker can be in for a whole second is a state the
fixtures have to be able to seed, or the tests are only ever testing the calm moments.
