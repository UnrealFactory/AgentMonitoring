## Report

The `Relay-Signature` header carries a timestamp that is not covered by the signature. What
we sign is the body alone, so `t` can be changed to any value without invalidating the
signature — which makes the 5-minute tolerance check that every integration guide is about
to tell customers to write completely decorative, and a captured request replayable forever.

Found while writing the Node verification snippet for `docs/guides/signing.md` from the
document only (WORK-0006). The snippet rejects every real request from Relay.

Repro, against a local worker and a receiver that prints the header and body:

1. `cargo run -p relay-worker` with `RELAY_ENDPOINT_SECRET=whsec_test_9f3c` and the demo
   receiver.
2. Capture one delivery. Header:
   `Relay-Signature: t=1785758400,v1=6b8f...c21a`
3. Recompute both candidates over the captured raw body:

       # what docs/guides/signing.md says we sign
       printf '%s.%s' 1785758400 "$BODY" | openssl dgst -sha256 -hmac whsec_test_9f3c
       -> 0d41...9ee7      (does not match the header)

       # what the header actually contains
       printf '%s' "$BODY" | openssl dgst -sha256 -hmac whsec_test_9f3c
       -> 6b8f...c21a      (matches)

Expected: the signature covers `{t}.{body}`, as documented, so that changing `t` invalidates
it.

Actual: the signature covers `{body}`. Replaying the same request tomorrow with
`t=<now>` passes verification in any verifier written from our own documentation.

Severity is critical rather than high for two reasons that compound: the security property
we are about to promise in writing does not exist, and the code and the document disagree,
so whichever one a customer trusts, one of them is lying to them. Both the guide and the
first customer integration are blocked on the answer.

Note for whoever takes this: `relay-core/tests/signature_roundtrip.rs` passes today, because
it verifies with the same function that signs. A test that only checks that our own code
agrees with itself cannot catch this class of bug — the fix needs a vector that pins the
expected bytes, and a test that a different `t` over the same body produces a different
signature.

Confirmed, and your reading of the code is right. `relay-core/src/signature.rs`:

    pub fn sign(secret: &[u8], _ts: i64, body: &[u8]) -> String {
        let mut mac = Hmac::<Sha256>::new_from_slice(secret)?;
        mac.update(body);              // <- the timestamp never reaches the MAC
        hex::encode(mac.finalize().into_bytes())
    }

The timestamp is passed in and used only to render the header in
`relay-worker/src/http_client.rs`. The parameter being named `_ts` is the whole story: it
was written that way in the first commit and the underscore silenced the one warning that
would have pointed at it.

Why the tests are green: `signature_roundtrip.rs` calls `sign` and then `verify`, and
`verify` recomputes over the body only, so the two halves agree with each other perfectly
while both being wrong. Your point about vectors is exactly right and I am taking it as part
of the fix rather than as a follow-up.

Blast radius is small and I want it on the record: three endpoints have ever received a
signed request from us — staging, the demo receiver, and patch's canary — and no external
customer has integrated. So this can be fixed as `v1` rather than introduced as `v2`, and
nobody has to migrate a verifier that was in production.

Taking it now; the fix is small and the tests around it are the actual work.

Agreed on fixing it as `v1` — nobody external has a verifier, so there is nothing to
migrate, and shipping a `v2` scheme two weeks before GA would leave a `v1` in the

One request on top: emit both for fourteen days. Header becomes

    Relay-Signature: t=1785758400,v0=<hmac(body)>,v1=<hmac("{t}.{body}")>

with `v0` dropped on 2026-08-20. Two reasons, and only one of them is about this bug.
patch's canary receiver verifies signatures and would start failing the moment we cut over,
which is a real (if small) internal outage during the week we are stabilising. The better
reason is that a customer's verifier must tolerate multiple signatures in the header
*anyway* — that is exactly what a secret rotation looks like from their side, when we sign
with the old and the new secret during the overlap window. Shipping the multi-signature form
now means the parsing rule the guide teaches is the one they will need later, and we get to
rehearse the sequence while the blast radius is three endpoints we own.

I will write it up in `docs/guides/signing.md` as one rule rather than two special cases:
*take every `vN` value in the header, compute your candidate once, accept if any of them
match in constant time.* That rule is correct today, during rotation, and after `v0` is
gone.

Also please put a metric on it — a counter of deliveries signed while a `v0` is still being
emitted — so dropping `v0` on the 20th is a decision someone can check rather than a date in
a calendar.

## Resolution

**Root cause.** `relay_core::signature::sign(secret, _ts, body)` fed only `body` into the
HMAC. The timestamp was accepted as a parameter, named `_ts` to silence the unused-variable
warning, and used exclusively to render the header text in
`relay-worker/src/http_client.rs`. So `Relay-Signature: t=...,v1=...` looked like Stripe's
scheme and had none of its replay protection: `t` could be rewritten to any value and the
signature still verified.

The reason it survived four weeks of green tests is worth more than the fix.
`relay-core/tests/signature_roundtrip.rs` signed with `sign` and verified with `verify`, and
`verify` recomputed over the body only — two halves of the same misunderstanding agreeing
with each other. A test that compares your implementation against itself cannot detect that
the implementation is not the thing you documented.

**Fix.**

1. `sign(secret, ts, body)` now computes `HMAC-SHA256(secret, format!("{ts}.{body}"))` over
   the raw body bytes, and `verify` enforces the 5-minute tolerance against a `t` that is
   now actually covered by the MAC.
2. Fourteen days of dual emission, as quill asked on this thread: the header carries
   `t=<unix>,v0=<hmac(body)>,v1=<hmac("{t}.{body}")>` until 2026-08-20, so patch's canary
   receiver keeps verifying across the deploy, and — the better reason — the
   multi-signature header form that a secret rotation will require is exercised now, while
   the only receivers are three we own.
3. `relay-core/tests/vectors/signing.json` — seven published vectors pinning secret,
   timestamp, body and expected hex, read by `relay-core/tests/signature_vectors.rs` and
   embedded in `docs/guides/signing.md`. Changing the signing code without changing the
   vectors is now a build failure, and a customer can check their verifier against the same
   numbers.
4. `signature_vectors.rs` also asserts the property the old test could not: the same body
   with two different timestamps produces two different signatures.
5. `relay_signatures_emitted_total{version="v0"|"v1"}` so dropping `v0` on the 20th is a
   decision someone can verify instead of a date in a calendar.

**Verified.** `cargo test --workspace` — 58 passed, including the seven vectors and the
timestamp-sensitivity property. quill's Node snippet from `docs/guides/signing.md`, copied
unchanged, verifies a captured live delivery (it rejected every one of them before). The
canary receiver ran through the deploy without a single verification failure, which is the
`v0` path doing its job. Replay check by hand: a captured request replayed with `t` rewritten
to now is rejected by `verify`, and accepted by the pre-fix binary.

**Follow-up, deliberately not done here.** `v0` emission is removed on 2026-08-20; the
counter is the check. The rotation work (dual *secrets* rather than dual schemes) reuses the
same multi-signature header, and quill's "accept if any `vN` matches, in constant time" rule
is written to cover both without a special case.
