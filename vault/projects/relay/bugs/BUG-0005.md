## Report

Every deploy of the dashboard white-screens anyone who already has it open, and they stay
broken until they discover Ctrl+Shift+R. It happened again during this morning's deploy while
two people were using the delivery log to look at a customer issue, which is exactly when the
tool has to work.

Repro:

1. Open `https://relay-dashboard.internal/deliveries` and leave the tab open.
2. Deploy any dashboard change (`.github/workflows/deploy-dashboard.yml`).
3. Navigate anywhere in the app, or reload normally.

Expected: the new build loads, or at worst the old one keeps working.

Actual: blank page. Console:

    Failed to load module script: Expected a JavaScript module script but the server
    responded with a MIME type of "text/html".
    GET /assets/index-8a3f21c9.js  404

Hard refresh fixes it permanently for that person, which is the tell: the browser is holding
an `index.html` that references asset filenames the deploy deleted.

`curl -I` on the deployed site:

    HTTP/2 200
    content-type: text/html
    cache-control: public, max-age=31536000, immutable

`index.html` is being served with the same year-long immutable caching as the hashed assets.
`deploy/nginx.conf` has a single `location /` block that adds that header to everything, and
the deploy job runs `aws s3 sync --delete`, so the old hashed files are gone the moment the
new ones land. Cached HTML plus deleted assets equals a 404 for a file the browser is certain
it should have.

The CDN has the same header, so a brand-new visitor gets the stale HTML from the edge as
well — the deploy job invalidates nothing.

Severity high: the dashboard is unusable after every deploy for everyone who does not know
the hard-refresh trick, and the people most likely to have it open are support engineers
mid-incident. Workaround exists (Ctrl+Shift+R) and is not discoverable, which is why this is
high rather than critical.

## Comments

### 2026-08-14T11:35:00Z — patch

Confirmed, and your diagnosis is right down to the `location /` block. Two mistakes of mine
that only break in combination, which is why it survived review.

`deploy/nginx.conf` has one `location /` with `add_header Cache-Control "public, max-age=
31536000, immutable"`. That header is correct for `/assets/*` — Vite puts a content hash in
every filename, so those bytes never change — and catastrophic for `index.html`, which has a
stable URL and different content on every deploy. I wrote one rule for two things with
opposite requirements.

The second is `aws s3 sync --delete` in `deploy-dashboard.yml`. Even with a sane HTML cache,
deleting the previous build's assets breaks anyone whose page is already loaded and lazily
imports a route chunk thirty seconds later. That one is subtler than the white screen and
would have kept biting after fixing the header alone.

Fix, three parts:

- `location = /index.html` gets `Cache-Control: no-cache` — revalidate every time, not
  `no-store`; a 304 costs one round trip and keeps the bytes cached. `/assets/` keeps
  `immutable`, which is the whole point of hashed filenames.
- The deploy stops using `--delete`. Old assets expire on an S3 lifecycle rule after 7 days,
  so an open tab keeps finding its chunks, and the bucket does not grow forever.
- The deploy job invalidates `/index.html` at the CDN and waits for the invalidation to
  complete before reporting success, so "deployed" means "being served".

Plus a check so this cannot come back: `scripts/check-cache-headers.sh` curls the deployed
URL and asserts `index.html` is `no-cache` and a sampled asset is `immutable`. It runs as the
last step of the deploy job and fails it.

## Resolution

**Root cause.** Two of my mistakes that are only fatal together.

`deploy/nginx.conf` had a single `location /` block adding `Cache-Control: public,
max-age=31536000, immutable` to every response. That is exactly right for `/assets/*`, whose
filenames contain a content hash and whose bytes never change, and exactly wrong for
`index.html`, which has a stable URL and different content after every deploy. One rule for
two things with opposite requirements.

`deploy-dashboard.yml` then ran `aws s3 sync --delete`, so the previous build's hashed assets
were removed the moment the new ones landed. A browser holding a year-cached `index.html`
asked for `/assets/index-8a3f21c9.js`, got the SPA fallback (HTML, 404 status), and refused
to execute it as a module — the "Expected a JavaScript module script" error in the report.
The CDN cached the same HTML with the same header, so new visitors got the stale document
from the edge too, and the deploy invalidated nothing.

**Fix.**

1. `location = /index.html` and `location = /build.json` now set `Cache-Control: no-cache`
   — revalidate every time, *not* `no-store`; the bytes stay cached and a 304 costs one
   round trip. `location /assets/` keeps `immutable`, which is what hashed filenames are for.
2. The deploy no longer passes `--delete`. Old objects expire through an S3 lifecycle rule
   after 7 days, so a tab that has been open since before the deploy still finds the route
   chunk it lazily imports — the mid-session white screen sable connected to this on the
   thread, which the header fix alone would not have solved.
3. The deploy job issues a CDN invalidation for `/index.html` and `/build.json` and waits
   for it to complete before reporting success, so "deployed" means "being served".
4. `scripts/check-cache-headers.sh` runs as the last step of the deploy: it curls the live
   URL and asserts `index.html` is `no-cache`, `build.json` is `no-cache`, and a sampled
   hashed asset is `immutable`. It fails the job. This bug class is invisible in review and
   obvious to a curl, so a curl now runs on every deploy.

**Verified.**

    $ curl -sI https://relay-dashboard.internal/ | grep -i cache-control
    cache-control: no-cache
    $ curl -sI https://relay-dashboard.internal/assets/index-4c19ab77.js | grep -i cache-control
    cache-control: public, max-age=31536000, immutable

Deployed three times in a row with a tab open on `/deliveries` throughout: no white screen,
no console error, and the old chunks still resolve. Deliberately deployed a build with a
renamed route chunk and navigated to that route on the old tab — it loads from the retained
object instead of 404ing. `scripts/check-cache-headers.sh` fails as expected when the
`location = /index.html` block is removed (checked, then put back).

**Follow-up, owned by sable:** the app fetches `/build.json` on window focus and after a
failed dynamic import and offers "A new version is available — Reload", so a long-lived tab
updates on purpose rather than by accident. `build.json` is excluded from the immutable rule
above so that check can be trusted.
