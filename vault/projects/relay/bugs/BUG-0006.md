## Report

The dashboard shows exhausted deliveries as **Failed**. The API calls them `dead`. Support
has been telling customers "it failed, it will keep retrying" about deliveries that will
never be retried again.

Repro:

1. Find a delivery that has exhausted the ladder: `GET /v1/deliveries?status=dead`.
2. Open it in the dashboard.

Expected: a `Dead` pill, and copy that says the ladder is exhausted and a replay is the only
way it will be sent again.

Actual: the amber `Failed` pill, which everywhere else on the screen means "failed this
attempt, will retry", and a "next attempt" column showing an em dash that reads as "unknown"
rather than "never".

The cause is upstream of my code. `docs/api/openapi.yaml` says:

    status:
      type: string
      enum: [pending, in_flight, succeeded, failed]

There is no `dead` in the document, and `failed` is a status the API has not returned since
the dead-letter work landed (WORK-0005) — it is a leftover from before the ladder existed.
`dashboard/src/lib/api-types.gen.ts` is generated from that document, so
`Delivery["status"]` is a union of four strings that does not include the one the server
actually sends, and my `StatusPill` switch falls through to its default branch, which renders
the `failed` styling.

Two things this says about our tooling, which is why I am filing it rather than patching my
switch:

- `npm run check:api-types` passes, because the generated types faithfully match a document
  that is wrong. It checks generation, not truth.
- TypeScript did not catch it either: the switch has a `default` branch, so an unmodelled
  value is silently absorbed. That is my bug and I will fix it with an exhaustiveness check.

Severity medium: the information is wrong and support acted on it, but the attempt count is
visible on the same screen and reads 8/8, so the workaround is "know the ladder length".

What happened: `docs/api/openapi.yaml` was frozen with the statuses that existed at the time

  generates wrong types consistently, so the diff is empty.
- `openapi_conformance` (my test) checks that every documented path exists and every
  documented status code is producible. It says nothing about schemas.
- `error_taxonomy_matches_openapi` compares the two sets of error `type` URIs — the same idea
  as what is needed here, applied to only one enum.

So the fix is two things: correct the document, and extend the contract test so *response
enums* are covered the way error types already are. `relay-api/tests/openapi_schema.rs` will
assert, for each `#[derive(Serialize)]` enum that appears in a response body, that the set of
serialised variant strings equals the set in the document's schema. `DeliveryStatus`,
`AttemptErrorKind` and `EndpointState` are the three that exist today. A variant added in Rust
without a document change then fails CI, which is the property I thought
`check:api-types` gave us and it does not.

Also removing `failed` rather than keeping it as a documented-but-unused value. A status a
client will never receive is a branch every integrator writes and nobody can test, and this

## Resolution

**Root cause.** `docs/api/openapi.yaml` described `Delivery.status` as
`[pending, in_flight, succeeded, failed]`, frozen on 31 July (WORK-0002). WORK-0005 added the
`dead` terminal state on 6 August and stopped returning `failed` altogether — a delivery
waiting for its next attempt is `pending` — and the document was never updated. Because
`dashboard/src/lib/api-types.gen.ts` is generated from the document, the dashboard's union
type was missing the value the server actually sends, and a `default` branch in `StatusPill`
absorbed it and rendered the amber "Failed" styling. Support read that as "it will retry"
about deliveries that never will.

Nothing caught it because every check compared two things that were both derived from the
same wrong document: `check:api-types` regenerates *from* the document (a wrong document
generates consistent wrong types), and `openapi_conformance` checks paths and status codes,
not schemas.

**Fix.**

1. `docs/api/openapi.yaml` — `Delivery.status` is now `[pending, in_flight, succeeded,
   dead]`. `failed` is removed rather than deprecated: a status no client can ever receive is
   a branch everyone writes and nobody can test, which is exactly what this bug cost.
   `docs/api/CHANGELOG.md` records it as a corrective change to an undelivered document, with
   the date the server behaviour actually changed.
2. `relay-api/tests/openapi_schema.rs` — new contract test. For every enum serialised into a
   response body (`DeliveryStatus`, `AttemptErrorKind`, `EndpointState`), it compares the set
   of serde-serialised variant strings with the set in the document's schema and fails on any
   difference in either direction. Adding a Rust variant without documenting it is now a
   build failure, which is the property I wrongly believed `check:api-types` provided.
3. `api-types.gen.ts` regenerated; `dead` is in the union.
4. From sable, landed in the same week so the halves cannot drift: every switch over a server
   enum ends in `default: return assertNever(status)`, so a missing case is a compile error
   rather than a plausible-looking fallback. The `dead` pill is grey (terminal, not in
   trouble), labelled **Dead**, and the next-attempt column reads "never — replay to send
   again" with the replay button beside it.

**Verified.** `cargo test --workspace` — 74 passed, including the new schema test, which
fails on the previous commit with `DeliveryStatus: in code not in document: {"dead"}; in
document not in code: {"failed"}`. `npm run check:api-types` — clean. `vitest run` — 51
passed, including a pill test per status. Checked the three deliveries support asked about
last week: all three now read **Dead**, 8/8 attempts, "never — replay to send again".

**What I would tell the next person.** Generated clients make a document authoritative
whether or not it is true. The generation step feels like verification and is not: it
propagates the document, including its mistakes, into a type system that then confidently
agrees with it. The only check that helps is one that compares the document with the running
server's behaviour.
