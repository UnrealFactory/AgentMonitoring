## What

Replace the placeholder in-memory queue in `relay-worker/src/dispatcher.rs` with a real
Postgres-backed claim, living in a new module `relay-store/src/queue.rs`:

- migration `relay-store/migrations/0003_delivery_queue.sql` adds `deliveries.locked_by`,
  `deliveries.locked_at` and `deliveries.next_attempt_at`, plus the partial index
  `deliveries_due_idx ON deliveries (next_attempt_at) WHERE status = 'pending'`;
- `queue::claim_batch(pool, worker_id, limit)` moves up to `limit` due deliveries to
  `in_flight`, stamps the lease columns and returns the rows in one statement;
- `queue::release(pool, id, outcome)` puts a row back to `pending` with a new
  `next_attempt_at`, or to a terminal status;
- the dispatcher loop now claims, sends and releases instead of draining a `VecDeque` that
  only ever existed inside one process.

## Why

At-least-once is the delivery contract we intend to publish; "at least twice because two
workers read the same row" is not. A duplicate webhook is not a cosmetic problem — the
receiving system usually turns it into a second order, a second refund or a second email,
and the customer's own idempotency is the only thing standing between us and that.

The obvious `SELECT ... WHERE status = 'pending' LIMIT 64` followed by an `UPDATE` races by
construction: both workers see the same 64 rows in the gap between the two statements. Three
alternatives were considered and rejected:

- **Advisory locks per delivery id.** One extra round trip per row, and the lock is
  invisible to a plain `SELECT`, so an operator cannot answer "who is holding this
  delivery" without a second query against `pg_locks`.
- **A separate queue (Redis, NATS).** Every delivery already needs a durable Postgres row
  for the history the dashboard reads, so this adds a second store to keep consistent with
  the first, and a whole class of "the queue and the table disagree" incidents.
- **`LISTEN`/`NOTIFY` to wake workers.** Orthogonal — it removes polling latency, it does
  not make the claim safe. Worth doing later on top of this, not instead of it.

## How

One statement does the claim:

    UPDATE deliveries d
       SET status = 'in_flight', locked_by = $2, locked_at = now(), attempt_count = attempt_count + 1
     WHERE d.id IN (
       SELECT id FROM deliveries
        WHERE status = 'pending' AND next_attempt_at <= now()
        ORDER BY next_attempt_at
        FOR UPDATE SKIP LOCKED
        LIMIT $1)
    RETURNING d.id, d.endpoint_id, d.event_id, d.attempt_count;

`FOR UPDATE SKIP LOCKED` is what makes concurrent claims disjoint: a row another
transaction has already locked is skipped rather than waited on, so N workers claim N
disjoint batches without any of them blocking. The `ORDER BY next_attempt_at` sits *inside*
the subselect on purpose — ordering the outer `UPDATE` would be meaningless, and without it
Postgres is free to hand a burst of new deliveries to a worker while a delivery that came
due ten minutes ago keeps being skipped.

The partial index is what keeps this cheap. `deliveries` is the table that grows forever;
only the `pending` slice of it is ever due, and that slice is small (thousands, not
millions), so the index is small and stays in cache.

`locked_by` is the worker's pod name and `locked_at` the claim time, so `SELECT locked_by,
count(*) FROM deliveries WHERE status = 'in_flight' GROUP BY 1` answers "what is each
worker doing right now" without any tooling.

Concurrency is tested rather than argued: `relay-store/tests/queue_claim.rs` seeds 5000 due
deliveries, runs 8 `claim_batch` calls against the same pool in parallel and asserts the
union of the returned ids is exactly the 5000 rows with no id appearing twice.

## Updates

### 2026-07-28T15:20:00Z

`claim_batch` is in and the concurrency test passes: 8 parallel claimers over 5000 due rows
return 5000 distinct ids, zero overlap, zero lost rows.

The number that matters is the plan. Before the partial index, the subselect was a sequential
scan over the whole `deliveries` table — 482ms at 1.4M rows on the dev database, and that is
per claim, per worker, forever. With `deliveries_due_idx` it is an index scan on the pending
slice: 1.9ms. The index is 6MB because it only covers `status = 'pending'`; the equivalent
full index on `next_attempt_at` was 94MB and would have grown with history that is never
queried this way.

Left to do: the ordering question (a burst of new deliveries can currently jump ahead of an
old one that is due) and wiring the dispatcher loop to the real claim.

### 2026-07-29T11:05:00Z

Fixed the starvation case before it became a production question. With no `ORDER BY` in the
subselect, a synthetic burst of 20k new deliveries kept a delivery that came due 11 minutes
earlier unclaimed through six consecutive batches — Postgres returns whatever the index scan
reaches first, and the newest rows were cheapest to reach. `ORDER BY next_attempt_at` inside
the subselect makes the oldest due delivery the first one claimed; the same test now shows
the aged row in batch one.

Dispatcher is on the real claim as of this note: `relay-worker/src/dispatcher.rs` claims 64,
sends with a concurrency of 32, releases each row by outcome. Ran two worker processes
against one database for 20 minutes on a synthetic 60k-delivery backlog, with a receiver
that records every request id it sees: 60000 deliveries, 60000 distinct requests, no
duplicates.

## Outcome

The delivery queue is real: workers claim from Postgres, claims are provably disjoint, and
the dispatcher no longer keeps state that dies with the process.

Shipped:

- `relay-store/src/queue.rs` — `claim_batch`, `release`, and the row types the dispatcher
  consumes. The claim is a single `UPDATE ... WHERE id IN (SELECT ... FOR UPDATE SKIP
  LOCKED ORDER BY next_attempt_at LIMIT $1) RETURNING`.
- `relay-store/migrations/0003_delivery_queue.sql` — `locked_by`, `locked_at`,
  `next_attempt_at`, and `deliveries_due_idx`, a partial index over the `pending` slice.
- `relay-worker/src/dispatcher.rs` — claim 64, send with concurrency 32, release by
  outcome; poll interval 250ms when the last batch was full, 2s when it was empty.

Measured, on the dev database at 1.4M deliveries:

- claim query: 482ms sequential scan before the partial index, 1.9ms index scan after;
  index is 6MB against 94MB for a full index on `next_attempt_at`.
- `relay-store/tests/queue_claim.rs`: 8 concurrent claimers over 5000 due rows return 5000
  distinct ids — no overlap, nothing lost.
- Two worker processes, one database, 60k synthetic deliveries against a recording
  receiver: 60000 requests, 60000 distinct, zero duplicates, drained in 18m40s at the
  deliberately throttled test concurrency.
- `cargo test --workspace` — 41 passed.

Follow-ups, both known and neither hidden:

1. **No lease expiry sweeper yet.** A worker killed between claim and release leaves its
   rows `in_flight` with a stale `locked_by`; nothing picks them up until that pod comes
   back. The columns to fix it exist (`locked_at`), the sweeper does not.
2. **Polling, not `LISTEN`/`NOTIFY`.** A delivery created at t+0 waits up to 250ms for the
   next poll. Fine for now; the wake-up path is a separate change and does not touch the
   claim.
