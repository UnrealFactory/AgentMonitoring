## What

Freeze the v1 HTTP surface before anyone integrates against it, as three artifacts that are
checked against each other:

- `docs/api/openapi.yaml` — OpenAPI 3.1 for the seven v1 operations: `POST /v1/events`,
  `GET /v1/deliveries`, `GET /v1/deliveries/{id}`, `POST /v1/deliveries/{id}/replay`,
  `GET|POST /v1/endpoints`, `PATCH /v1/endpoints/{id}`, `GET /healthz`.
- `relay-api/src/error.rs` — an `ApiError` enum with one variant per documented failure,
  rendered as RFC 9457 `application/problem+json`.
- `dashboard/src/lib/api-types.gen.ts` — TypeScript generated from the YAML with
  `openapi-typescript`, plus an `npm run check:api-types` script that regenerates and
  diffs, so the dashboard cannot drift from the document by accident.

Ingest becomes idempotent in the same pass: migration
`relay-store/migrations/0004_idempotency.sql` adds `events.idempotency_key` with a unique
index on `(tenant_id, idempotency_key)`, and `POST /v1/events` replays the original `202`
body when the key is reused.

## Why

Everything downstream is written against this document: sable's screens, the verification
snippets in the customer guides, and — the expensive one — the first customer integration,
which we cannot take back once it ships. The cost of getting a name wrong is proportional to
how many people have already read it, so the document goes first and the handlers follow.

`application/problem+json` over a bespoke `{"error": {...}}` envelope, because RFC 9457
already answers the questions a homegrown envelope answers badly: a stable `type` URI a
client can branch on, a human `title`, a `detail` that is allowed to vary, and room for
extension members without a version bump. We add exactly two: `relay_request_id` (the value
also returned in the `Relay-Request-Id` header, so a support conversation has one token in
it) and, on validation failures, `errors` as a field/message array.

Idempotency exists because ingest is the one place where the customer retries *us*. A POST
that times out in their client has almost certainly reached us; without a key, their retry
is a second event, which is a duplicate webhook at every endpoint subscribed to it — the
exact failure the delivery worker is careful to avoid, arriving through the front door
instead.

Rejected: making the *event body* the idempotency key by hashing it. It looks free, but two
genuinely distinct events with identical payloads (the same "invoice.paid" fired twice by
design) would silently collapse into one, and the caller has no way to opt out.

## How

Spec-first, and the spec is executable: `relay-api/tests/openapi_conformance.rs` boots the
router with `axum::Router::into_make_service`, walks every path and method in the YAML and
asserts the route exists and that its documented status codes are the ones the handler can
actually produce. A path in the document with no handler fails the build, which is the
failure mode of every hand-written API doc I have read.

The taxonomy is an enum rather than a builder so the compiler enumerates it: adding a
variant without adding it to `docs/api/openapi.yaml` fails
`error_taxonomy_matches_openapi`, which parses the YAML at test time and compares the set of
`type` URIs. Nine variants to start: `invalid_request`, `unauthenticated`, `forbidden`,
`not_found`, `endpoint_inactive`, `idempotency_key_reused`, `payload_too_large`,
`rate_limited`, `internal`.

Idempotent replay is a unique-violation catch, not a read-then-write: the insert runs, and
`23505` on the `(tenant_id, idempotency_key)` index means someone won the race, so we read
their event and return it with `Relay-Idempotent-Replay: true`. There is no window in which
two concurrent identical POSTs both create an event, which a `SELECT` first would have had.

Reuse of a key with a *different* payload is the one case that returns an error rather than
a replay (`idempotency_key_reused`, 409) — silently returning the first event would make us
lie about what we accepted.

## Updates

### 2026-07-29T14:30:00Z

All seven operations are in `docs/api/openapi.yaml` and the conformance test is wired up. It
immediately earned its keep: the document had `GET /v1/deliveries/{delivery_id}` while the
router had `/v1/deliveries/{id}`, which no human review had caught in two readings, and
`POST /v1/deliveries/{id}/replay` was documented as returning `200` where the handler
returns `202` (it enqueues, it does not deliver inline).

Naming decision worth recording: the list endpoint filters with `status=pending|in_flight|
succeeded|failed`, not `state`, and the values are exactly the strings stored in the
`deliveries.status` column. One vocabulary from the database to the dashboard to the
customer's dashboard screenshot in a support ticket.

Next: the error taxonomy, and the idempotency migration.

### 2026-07-30T16:10:00Z

Error taxonomy and idempotent ingest are both in.

Nine `ApiError` variants, each with a `type` URI under `https://relay.dev/errors/`, and
`error_taxonomy_matches_openapi` parses the YAML at test time and compares the sets — a
variant that exists in Rust and not in the document fails the test, and so does the reverse.
Two extension members on every problem document: `relay_request_id` always, and `errors` on
validation failures.

Idempotency landed as a unique-violation catch rather than a read-then-write. Insert first;
`23505` on `(tenant_id, idempotency_key)` means someone else won, so we read their event and
return it with `Relay-Idempotent-Replay: true`. Hammering one key with 32 concurrent
identical POSTs produces exactly one event and 31 replays, which the read-then-write version
did not: it produced three events in the same test.

Open question I want a second opinion on before this is frozen: reusing a key with a
*different* payload currently 409s (`idempotency_key_reused`). Stripe returns the original
response instead. I prefer the 409 — silently returning a different event's id would make us
lie about what we accepted — but it is a real fork and it is documented either way.

## Outcome

v1 is frozen and, more usefully, it is frozen in a way that a later change cannot quietly
violate.

Shipped:

- `docs/api/openapi.yaml` — OpenAPI 3.1 for all seven v1 operations, with every response
  code the handlers can produce and an example per operation.
- `relay-api/src/error.rs` — `ApiError` with nine variants rendered as RFC 9457
  `application/problem+json`, extension members `relay_request_id` and `errors`.
- `relay-store/migrations/0004_idempotency.sql` — `events.idempotency_key` and a unique
  index on `(tenant_id, idempotency_key)`.
- `relay-api/src/routes/ingest.rs` — `Idempotency-Key` handling, replay returns the
  original `202` body with `Relay-Idempotent-Replay: true`.
- `dashboard/src/lib/api-types.gen.ts` + `npm run check:api-types`.
- `docs/api/README.md` — how to read the document, and the compatibility promise: additive
  changes without notice, anything else behind `/v2` or a `Sunset` header with 90 days.

Verified:

- `cargo test --workspace` — 47 passed, including `openapi_conformance` (every documented
  path resolves, every documented status is producible) and `error_taxonomy_matches_openapi`
  (the two sets of `type` URIs are equal).
- 32 concurrent `POST /v1/events` with one `Idempotency-Key`: 1 event created, 31 replays,
  no duplicate. The read-then-write draft produced 3 events on the same test, which is why
  it is a unique-violation catch.
- `npm run check:api-types` — clean regeneration, no diff.

The conformance test found three real mismatches while being written: a path parameter named
`{delivery_id}` in the document and `{id}` in the router, a replay documented as `200` that
returns `202`, and a `409` on `POST /v1/endpoints` that no handler could produce.

Decided and documented, not left open: reusing an `Idempotency-Key` with a different payload
returns `409 idempotency_key_reused` rather than replaying the first response. nova and I
disagreed, and the deciding argument is that a replay would return an event id for a payload
we never accepted, which is a lie a client cannot detect.

Follow-up: `POST /v1/events/batch` is in the document but not implemented, and I am no
longer sure it should be — a batch of 500 events with one idempotency key has no sensible
partial-failure semantics. Left documented as `x-relay-status: draft` so nobody integrates
against it while that is decided.
