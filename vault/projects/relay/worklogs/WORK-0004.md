## What

The screen support will live in: a delivery log that can be filtered down to one endpoint's
last hour, and a detail view that shows every attempt Relay made and what came back.

- `dashboard/src/routes/DeliveryLog.tsx` — cursor-paginated table (event type, endpoint,
  status, attempt count, next attempt, age), filtered by endpoint, status and time window.
- `dashboard/src/routes/DeliveryDetail.tsx` — one delivery: the request we sent, the
  attempt history, and the replay action.
- `dashboard/src/components/AttemptTimeline.tsx` — one row per attempt: number, when it
  started, how long it took, the response status, and the first 512 bytes the endpoint
  returned.
- `dashboard/src/components/StatusPill.tsx`, `FilterBar.tsx`, `PayloadViewer.tsx`.
- `dashboard/src/lib/api.ts` — TanStack Query hooks over the v1 API, typed from
  `api-types.gen.ts`, so a field the OpenAPI document does not promise does not compile.

## Why

The workflow this replaces is a support engineer with `psql` open and a Slack thread with a
customer in it. The questions are always the same three, in the same order: did it get
there, if not what did the endpoint say, and can you send it again. A screen that answers
those three without a query is worth more than any chart on an overview page, so the log is
the first screen built and the overview is not.

Attempt history is the part people underestimate. "Failed" on its own starts an argument;
"attempt 3 of 8, 502 from your load balancer, body `upstream connect error`, 12ms" ends one
— it is the customer's infrastructure and now they can see it. So the response snippet is
first-class, not hidden behind an expander.

Rejected: an infinite-scroll feed. Support engineers read this while typing into a ticket
and need a stable thing to point at ("page 2, the 14:07 one"). Cursor pages with a visible
"older" control keep a position; infinite scroll loses it the moment the tab is switched.

## How

Pagination is cursor-based against `GET /v1/deliveries?cursor=`, not offset. Offset
pagination over a table this write-heavy shows duplicates and gaps as new rows arrive; the
cursor is `(created_at, id)`, so a page is stable no matter what lands while you read it.

The timeline is a list, not a chart. There are at most 8 attempts on the ladder, and support
reads them one at a time — a duration bar chart looked good in the mock and answered nothing
you could not read from the numbers.

Response snippets are rendered as text, never as HTML. Endpoints return whatever they like,
including HTML error pages with scripts in them, so `PayloadViewer` sets `textContent` and
the JSON pretty-printer is a small recursive React renderer over `JSON.parse`, not
`dangerouslySetInnerHTML`.

Keyboard: `j`/`k` move the selection, `Enter` opens, `/` focuses the filter, `Escape`
clears. Support engineers are one-handed while typing to a customer, and every one of them
tried `j` unprompted in the first session.

No virtualisation. Page size is 50 rows, which paints in 4ms; adding a virtualiser would
have added a dependency and broken `Ctrl+F`, which is how people actually search a page.

Filter state lives in the URL query string (`?endpoint=&status=&since=`), so a filtered log
can be pasted into a ticket and reopened as the same view.

## Updates

### 2026-07-31T17:15:00Z

Table and filters are up against the real API. Cursor pagination works and the URL carries
the filter state, so `/deliveries?endpoint=ep_7f2a&status=dead&since=1h` is a link you can
paste into a ticket.

Two findings from using it rather than building it. Endpoint names are long enough
(`acme-prod-orders-webhook`) that the column pushed status off-screen on a 1280px laptop, so
the endpoint column now truncates from the middle and keeps the tail, which is the
distinguishing part in every name we have seen. And "next attempt in 42m" reads better than
an absolute time for pending rows, while terminal rows want the absolute time — the column
now switches on status instead of picking one format for both.

`AttemptTimeline` renders the response snippet and it is already the most useful thing on
the screen: the staging endpoint's 502s carry an nginx body that says exactly which upstream
refused.

### 2026-08-03T10:40:00Z

In-flight attempts render properly now that BUG-0001 is fixed and `finished_at` is nullable
in the contract: attempt 3, "started 4s ago", duration column counting up once a second
instead of a dash. It reads as alive, which is the whole point of the screen.

Also filled in the states that get skipped in a demo and hurt in production: an empty log
with the filter that produced it named ("no deliveries for acme-prod in the last hour"), a
loading skeleton the shape of the table rather than a spinner, and an error state that shows
the `relay_request_id` from the problem+json body with a copy button — support can paste
that straight into a ticket, which is exactly how BUG-0001 got diagnosed in one hop.

Ran the axe checks: contrast on the `dead` pill was 3.1:1 on the raised surface, now 4.8:1.
Status is never colour alone; each pill has a label.

## Outcome

The delivery log and the delivery detail screen are done and are already the way we answer
"did it get there" — three support questions on staging this week were answered from the
screen instead of from `psql`.

Shipped:

- `dashboard/src/routes/DeliveryLog.tsx` — cursor-paginated table, filters for endpoint,
  status and time window, all of it in the URL (`?endpoint=&status=&since=`) so a filtered
  view is a link.
- `dashboard/src/routes/DeliveryDetail.tsx` — request we sent, attempt history, replay.
- `dashboard/src/components/AttemptTimeline.tsx` — per attempt: number, start, duration,
  response status and the first 512 bytes of the response body. In-flight attempts show a
  live elapsed counter.
- `dashboard/src/components/StatusPill.tsx`, `FilterBar.tsx`, `PayloadViewer.tsx`.
- `dashboard/src/lib/api.ts` — TanStack Query hooks typed from `api-types.gen.ts`.

Decisions a reviewer would otherwise have to reconstruct:

- Cursor pages, not offset: `deliveries` takes writes constantly, and offset pagination
  shows duplicates and gaps while you read. The cursor is `(created_at, id)`.
- No virtualisation: 50 rows paint in 4ms and `Ctrl+F` keeps working, which is how people
  actually search a table they are reading out loud to a customer.
- Response snippets are rendered as text through `textContent`, never as HTML. Endpoints
  return arbitrary bodies, including HTML error pages.
- The "next attempt" column switches format on status: relative for pending ("in 42m"),
  absolute for terminal rows.

Verified: `vitest run` — 38 tests, including the pagination cursor round-trip and the
`StatusPill` mapping for all five statuses. `npx playwright test dashboard/e2e/delivery-log.spec.ts`
— 6 scenarios against a seeded database (filter, paginate, open, replay, empty state, error
state). `npm run build` — tsc clean, 214kB JS. axe: no violations; the `dead` pill went from
3.1:1 to 4.8:1 contrast, and no status is signalled by colour alone.

Found and filed on the way: BUG-0001 (`GET /v1/deliveries` 500s on an in-flight attempt),
fixed by nova; the timeline's running state is a direct consequence of that fix.

Follow-ups: the log has no live updating yet — it polls every 5 seconds, which is visible as
a stutter when a row changes status mid-read, and is the next piece of work. Timestamps
render in the browser's locale, which is wrong for a support workflow that thinks in UTC.
