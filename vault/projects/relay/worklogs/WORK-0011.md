## What

Convert `delivery_attempts` to a range-partitioned table, one partition per month, and make
retention a `DROP TABLE` instead of a `DELETE`:

- `relay-store/migrations/0010_partition_attempts.sql` — a partitioned parent
  (`PARTITION BY RANGE (started_at)`), monthly partitions from 2026-04 forward, the existing
  table copied in batches and attached as the historical partitions, and a rename swap at the
  end.
- `relay-worker/src/retention.rs` — a daily tick that creates next month's partition seven
  days ahead of time and detaches-then-drops any partition entirely older than
  `RELAY_ATTEMPT_RETENTION_DAYS` (90), plus a `relay_oldest_attempt_partition_days` gauge so
  the job's failure is visible before it becomes a disk alert.
- `relay-store/src/deliveries.rs` — every attempt query gains a `started_at` bound so the
  planner can prune partitions.
- `docs/operations/retention.md` — what is kept, for how long, and what a compliance export
  of older data would involve now that it is not a `SELECT`.

## Why

`delivery_attempts` is 214GB of a 341GB database and grows about 2.1GB a day: up to eight
attempt rows per failed delivery, kept forever. The consequences are no longer theoretical —
nightly backup takes 3h10m, last month's restore drill took 6h04m, and the planner's
statistics on a table this size are stale often enough to matter.

The obvious `DELETE FROM delivery_attempts WHERE started_at < now() - interval '90 days'`
removes about 190M rows and gives back no space: the pages stay in the table as bloat,
autovacuum on a 214GB table runs for days at a visible latency cost, and `pg_repack` wants as
much free disk as the table is large, which we do not have. Deleting is how a table this size
gets *worse*.

Partitioning makes the same retention decision a metadata operation: `DROP TABLE
delivery_attempts_2026_04` returns in milliseconds, gives the space back immediately, and
touches nothing else.

Rejected: **tiering old attempts to object storage as Parquet.** It sounds better than
deleting and is worse in practice — support gets a two-tier store that nobody remembers how
to query, and "attempts are online for 90 days and then gone" is a promise a customer and a
support engineer can both hold in their head. Rejected: **partitioning by `hash(delivery_id)`**,
which spreads writes nicely and makes retention a `DELETE` again, i.e. it solves the problem
we do not have and keeps the one we do.

## How

The copy is the risky part, so it is done in pieces that can each be abandoned: `INSERT INTO
delivery_attempts_p SELECT * FROM delivery_attempts WHERE started_at >= $1 AND started_at <
$2` in 5M-row batches, ordered oldest first, throttled to keep replica lag under 10s. If the
process dies, the completed months are already there and the loop resumes.

Attaching a partition normally takes an `ACCESS EXCLUSIVE` lock while Postgres scans the
table to prove every row belongs in the range — minutes of a completely locked table for a
big partition. The trick that avoids it: add the range as a `CHECK` constraint `NOT VALID`
first, `VALIDATE CONSTRAINT` (which takes only `SHARE UPDATE EXCLUSIVE`, so reads and writes
continue), and *then* attach — Postgres sees the validated constraint, skips the scan, and
the lock window is milliseconds.

The final swap renames both tables inside one transaction that starts with `SET
lock_timeout = '3s'`. Without that, the swap queues behind any long-running read and, while
queued, blocks every new query on the table — a swap that cannot get its lock must fail
immediately and be retried at a quieter moment, not wait.

Partition pruning only works when the query bounds the partition key, and today's per-delivery
attempt lookup is keyed on `delivery_id` alone. Every attempt of a delivery falls inside
`deliveries.created_at` to `created_at + 32h` (the ladder spans about 31 hours and a replay
creates its own delivery row rather than extending this one), so the query gains that bound
and the planner touches at most two partitions instead of all of them.

## Updates

### 2026-08-17T19:40:00Z

Parent table, monthly partitions and the batched copy all work on a dev restore of the
production database (214GB, 1.9B attempt rows).

    copy, oldest month first     3h50m total
    5M-row batch                 ~90s, replica lag peaked at 4.1s (cap is 10s)
    attach with NOT VALID + VALIDATE + ATTACH   lock held 11ms per partition
    attach without that trick (measured once, on 2026-05)   4m38s of ACCESS EXCLUSIVE

That 11ms against 4m38s is the whole reason this can be done on a live database. The
`VALIDATE CONSTRAINT` step still takes minutes, but it holds `SHARE UPDATE EXCLUSIVE`, so
reads and writes continue while it runs.

The swap script (`scripts/swap-attempts-partitioned.sh`) sets `lock_timeout = '3s'` and does
both renames in one transaction. Rehearsed it with a deliberate long-running `SELECT` open on
the table: the swap failed after 3 seconds and changed nothing, which is exactly the desired
behaviour — a swap that waits for its lock blocks every new query behind it.

Next: prove partition pruning actually happens on the queries the API runs. Writing the
`started_at` bound into `relay-store/src/deliveries.rs` tomorrow.

### 2026-08-18T07:50:00Z

Partition pruning does not happen for free, and the query that matters was the one that broke.

`EXPLAIN (ANALYZE)` on the API's per-delivery attempt lookup against the partitioned dev
table:

    Append  (actual time=0.019..48.412 rows=6 loops=1)
      ->  Index Scan on delivery_attempts_2026_04 ...      (38 partitions scanned)

Keying on `delivery_id` alone gives the planner nothing to prune with, so it scans every
partition — 48ms for six rows, against 0.9ms on the unpartitioned table. Partitioning would
have made the dashboard's most-used query fifty times slower.

Fixed by bounding the partition key from data we already have: every attempt of a delivery
falls inside `deliveries.created_at` to `created_at + 32h` (the ladder spans ~31h, and a
replay creates its own delivery row rather than extending this one), so
`relay-store/src/deliveries.rs` now passes that range and the plan becomes

    Append  (actual time=0.021..0.104 rows=6 loops=1)
      ->  Index Scan on delivery_attempts_2026_08 ...      (2 partitions scanned)

0.9ms → 0.104ms, because the partitions are individually small. The 32h constant is defined
once in `relay-core` next to the ladder and there is a test asserting it exceeds the ladder's
total span, so extending the ladder without extending the window fails the build rather than
quietly hiding attempts from the UI.

This is the failure mode of partitioning generally: it is invisible in `SELECT` results and
only shows up in the plan, so every query against the table needs its `EXPLAIN` read once.
Doing that for the other four now.
