## What

Give each worker pod an exclusive slice of the queue instead of having every pod compete for
every row:

- `deploy/k8s/worker-statefulset.yaml` — the delivery worker becomes a StatefulSet, so pod
  names are stable and `relay-worker-2` is always shard 2; `RELAY_WORKER_SHARDS` carries the
  total.
- `relay-store/src/queue.rs` — `claim_batch_sharded()`, which adds
  `AND hashtext(endpoint_id::text) % $shards = $shard` to the claim, plus the expression
  index to keep it off a sequential scan.
- `relay-store/migrations/0006_shard_leases.sql` — a `shard_leases(shard, holder,
  expires_at)` table so a pod that is restarting cannot overlap with its own replacement.
- `relay-worker/src/shard.rs` — acquire the lease on boot, renew every 5s, release on
  SIGTERM.

## Why

Two premises, both of which look solid from where I am standing today.

The first is that `FOR UPDATE SKIP LOCKED` will stop scaling before we want it to. Every
worker walks the same hot index pages on `deliveries_due_idx`, and the usual reported
ceiling for this pattern is somewhere between four and eight concurrent claimers before the
claim latency curve bends. We are at three worker pods and the backlog after an endpoint
outage already takes 18 minutes to drain; if the ceiling is real, adding pods stops helping
right about where we need it to start.

The second is ordering. "Deliver events for one endpoint in the order they happened" is a
request every webhook product eventually gets, and it is impossible while any worker can
pick up any delivery. Sharding by `endpoint_id` makes it merely difficult: one owner per
endpoint at a time is the precondition.

Rejected: table partitioning by shard (the partition count becomes a schema migration, and
we would be rewriting a 40M row table to add a pod), and an external queue (a second durable
store to reconcile with the Postgres rows the dashboard already reads).

## How

The pod ordinal is the shard id, which is the only thing a StatefulSet gives that a
Deployment does not, and the reason for the whole shape. `shard.rs` parses `HOSTNAME`,
takes the lease, and refuses to start delivering if the lease is held by someone else — a
pod that is being replaced holds its lease until SIGTERM, and the replacement waits rather
than double-owning the slice for the length of a graceful shutdown.

`hashtext()` rather than a hash computed in Rust, so the modulus is evaluated database-side
and the expression index can serve it. That means an index per shard count:
`CREATE INDEX ... ON deliveries ((hashtext(endpoint_id::text) % 4)) WHERE status =
'pending'`, which is the part I am least happy about and will be watching.

Lease TTL is 15s with a 5s renewal, so a pod killed without SIGTERM (OOM, node loss) has its
shard picked up within 15 seconds, and the 3x margin means a GC pause or a slow database
does not cause a pod to lose a shard it is actively working.

## Updates

### 2026-08-07T16:20:00Z

StatefulSet is up with four shards and the sharded claim works: each pod sees roughly a
quarter of the due rows, leases are acquired and renewed, and a `kubectl delete pod
relay-worker-2` has its shard picked up 11 seconds later by the replacement.

The problem is the one I flagged as the part I was least happy about, and it is worse than I
thought. The expression index has the shard count baked into it
(`(hashtext(endpoint_id::text) % 4)`), so changing `RELAY_WORKER_SHARDS` from 4 to 6 needs a
new index *and* a window during which some pods use the old modulus and some the new one.
During that window two pods can both consider themselves the owner of the same endpoint,
which is precisely the property the whole design exists to provide.

The only safe sequence I can write down is: scale the StatefulSet to zero, build the new
index, change the count, scale back up. That is a full stop of delivery — minutes of it —
every time we want more workers. Scaling that requires an outage is not scaling, and it
would land us in exactly the incident we would be scaling to avoid.

Parking the rescale question and going to measure the premise instead: if SKIP LOCKED does
not actually bend at 4-8 claimers, none of this is needed.

### 2026-08-10T11:30:00Z

Measured the premise this whole design rests on, and it is false.

Benchmark: `relay-store/benches/claim_contention.rs`, 1.2M pending deliveries on a database
sized like production, N processes calling `claim_batch(64)` in a loop for 60 seconds.

    workers   claim p50   claim p99   claimed/s
      1        0.7ms       1.4ms        8,900
      4        0.8ms       2.0ms       34,600
      8        0.9ms       3.1ms       67,100
     12        1.1ms       4.4ms       98,300

Throughput is linear to 12 workers, which is three times what I expected the ceiling to be
and four times what we would deploy. There is no contention wall to design around: SKIP
LOCKED skips, so the workers are not blocking each other, they are just reading a small
index that fits in cache. The "four to eight claimers" number I built this on came from
descriptions of `SELECT FOR UPDATE` *without* SKIP LOCKED, where workers genuinely queue
behind each other. Different mechanism, and I did not check.

The second premise — per-endpoint ordering — I went and asked about instead of assuming.
Nobody has requested it: not in the design notes, not from the two integration partners.
Ordering also does not survive the retry ladder anyway (event 2 succeeds on attempt 1 while
event 1 is on its 15-minute step), so shard ownership would give a guarantee only until the
first failure.

So the remaining scaling problem is not "which pod owns which endpoint", it is "how many
pods should exist right now", and that is a question for an autoscaler reading queue depth,
not for a StatefulSet with shard leases and an unscalable index. Writing that up before
deciding what happens to this branch.

### 2026-08-12T09:30:00Z

**Abandoned.** Abandoned because the premise is measurably false and the design has a defect I cannot fix
inside it.

The premise was that `FOR UPDATE SKIP LOCKED` stops scaling somewhere between four and eight
concurrent claimers, so we would need endpoint-sharded ownership to add workers. The
benchmark in the second note (`relay-store/benches/claim_contention.rs`) shows throughput
linear to 12 workers at 98,300 claims/second with p99 claim latency of 4.4ms — no wall, three
times past where I predicted one, and four times past what we would ever deploy. The number I
built on describes `SELECT FOR UPDATE` *without* SKIP LOCKED, which is a different mechanism
with a different failure mode; I did not check it before designing around it.

The second premise, per-endpoint ordering, is not a requirement anyone has asked for, and it
would not survive the retry ladder anyway: once event 1 is on its 15-minute step and event 2
succeeds first, ordering is gone regardless of who owns the shard.

The defect: the sharded claim needs an expression index with the shard count baked in
(`(hashtext(endpoint_id::text) % 4)`), so changing the number of workers requires a new index
and a window in which pods disagree about the modulus — during which two pods can own the
same endpoint, which is the one property the design exists to guarantee. The only safe
rescale is to drain to zero, reindex, and scale back up: an outage per scaling event, in a
system we would be scaling to avoid an outage.

What to read instead: **WORK-0010**, which scales replicas on queue depth and
oldest-pending age with a plain Deployment and KEDA — the same goal (add capacity when the
backlog grows) without ownership, leases, or an index that hard-codes the replica count.
**BUG-0004** covers the crash-safety half that shard leases were also going to provide:
`queue::reclaim_expired` sweeps abandoned in-flight rows, which is what WORK-0001's first
follow-up asked for.

Nothing from this branch ships. `deploy/k8s/worker-statefulset.yaml` is deleted rather than
left dormant — a manifest nobody applies is a trap for the next person — and its resource
limits, `terminationGracePeriodSeconds: 45` and the preStop drain hook, which were the only
good parts, are carried into `deploy/k8s/worker-deployment.yaml` in WORK-0010. Migration
`0006_shard_leases.sql` was never applied outside my dev database and is reverted in the
branch, not on `main`. The benchmark stays: it is the evidence, and the next person to
propose sharding should have to beat it.
