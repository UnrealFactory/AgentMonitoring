## What

`docs/guides/signing.md` and the material that keeps it true:

- what Relay signs, byte for byte, and what the `Relay-Signature` header looks like;
- verification snippets in Node, Python, Ruby and Go under `docs/guides/examples/`, each
  one a complete file a reader can run, not a fragment;
- `relay-core/tests/vectors/signing.json` — published test vectors (secret, timestamp, body,
  expected signature) that both the guide and `relay-core/tests/signature_vectors.rs` read,
  so a change to the signing code that does not update the vectors fails the build and a
  reader can check their implementation against the same numbers we do;
- the rotation section: what a customer sees during a secret rotation, and why they must
  accept a header carrying more than one signature.

## Why

Signature verification is the only part of Relay that every integrator writes themselves,
in their language, from our prose. It is also the part where being wrong is not a bug report
but a security incident on their side: a verifier that accepts anything is
indistinguishable, in normal operation, from one that works.

The failure I want to make impossible is the documentation drift. Prose describing a hash
computation goes stale silently — nothing breaks in our CI when the code changes and the
document does not, and the reader with the broken integration has no way to tell which of us
is wrong. Published test vectors turn that into a build failure on our side and a two-minute
check on theirs.

Writing the snippets from the document only — not from `relay-core` — is a deliberate
constraint. If the document is sufficient to write a verifier, a customer can. If it is not,
I find out in an afternoon rather than in a support thread six weeks after GA.

## How

Four languages, chosen for coverage of the mistakes rather than popularity: Node (where the
temptation is `==` on strings instead of `timingSafeEqual`), Python (`hmac.compare_digest`,
plus the encoding trap of `str` versus `bytes`), Ruby (`Rack::Utils.secure_compare`), Go
(`hmac.Equal`). Each snippet does all four steps a real verifier needs: parse the header,
reject a timestamp outside the tolerance, recompute over exactly the raw body, compare in
constant time.

The raw-body point gets its own section with framework-specific notes, because it is the
single most common integration failure in every webhook product I have read the support
forum for: Express with `express.json()` has already parsed and discarded the bytes we
signed, and re-serialising the parsed object produces different bytes whenever key order or
unicode escaping differs. The guide shows `express.raw({type: 'application/json'})` and the
Rails and Flask equivalents.

Tolerance is documented as 5 minutes with the reasoning attached — long enough for clock
skew on a machine with a lazy NTP client, short enough that a captured request is not
replayable for an afternoon — and the guide tells the reader to check it, because a
signature check without a timestamp check is a replay away from useless.

## Updates

### 2026-08-06T11:50:00Z

Writing the Node snippet from the document alone worked exactly as intended, and it found a
critical bug in the first hour: the header's timestamp is not covered by the signature at
all. Filed as BUG-0002 with the openssl commands that show both candidate digests. The guide
is blocked on that answer, because there is no honest way to document a replay-protection
step that the signature does not enforce.

The Node and Python snippets are otherwise done and the raw-body section is written, which I
now think is the most valuable page in the guide. `express.json()` has already parsed and
discarded the exact bytes we signed by the time a handler runs, and re-serialising the
object produces different bytes whenever key order or unicode escaping differs — so the
integration works in testing with ASCII payloads and fails the first time a customer name
has an umlaut in it. The guide shows `express.raw({type: 'application/json'})` first, before
any HMAC code, with the Flask (`request.get_data()`) and Rails (`request.raw_post`)
equivalents beside it.

### 2026-08-07T09:35:00Z

BUG-0002 is fixed, so the guide can say what it needs to say. All four snippets now verify a
captured live delivery unchanged from the page.

The header rule is written once, as a rule rather than as two special cases: *split the
header on commas, take every `vN` value, compute your candidate signature once, accept if any
of them matches in constant time.* That sentence is correct today with `v0` and `v1` in
flight, correct during a secret rotation when both signatures are `v1` under different
secrets, and correct after 2026-08-20 when there is only one. A reader who follows it never
has to come back and change their verifier because we changed ours.

Test vectors are in `relay-core/tests/vectors/signing.json` and the same seven rows are
tabulated in the guide, so a reader debugging at 2am can compare their hex against ours
without running our code.

Go and Ruby snippets are done. Each of the four does the four steps in the same order and
names the constant-time comparison for that language explicitly, because `==` on a signature
string is the mistake that looks like it works.

## Outcome

`docs/guides/signing.md` is published and, more importantly, it is the kind of document that
cannot quietly become false.

Shipped:

- `docs/guides/signing.md` — the header format, exactly what bytes are signed, the
  tolerance and why it is five minutes, the multi-signature acceptance rule, the raw-body
  section, and the rotation walkthrough.
- `docs/guides/examples/verify.{js,py,rb,go}` — four complete, runnable verifiers, each
  doing the same four steps in the same order, each naming its language's constant-time
  comparison (`timingSafeEqual`, `compare_digest`, `secure_compare`, `hmac.Equal`).
- `relay-core/tests/vectors/signing.json` — seven vectors, read by
  `relay-core/tests/signature_vectors.rs` and tabulated in the guide.
- `docs/guides/README.md` — index and reading order for the guides.

Verified: all four snippets, copied from the rendered page rather than from the source
tree, verify a captured live delivery from staging; `cargo test --workspace` — 58 passed,
the vector test among them; `npm run docs:lint` — no broken internal links, no code block
without a language tag.

The method is the result here. Writing the verifier from the document instead of from
`relay-core` found BUG-0002 in the first hour — the signature did not cover the timestamp,
so the replay protection the guide was about to describe did not exist. A guide written by
reading the implementation would have described the implementation, correctly and
uselessly.

Two things I changed my mind about while writing:

- The multi-signature rule started as a rotation-only footnote and is now the primary rule,
  because there is no version of a customer's verifier that should special-case "exactly one
  signature". It is correct during the `v0`/`v1` window, during a secret rotation, and after.
- The raw-body section moved to the top, above any HMAC code. Every "signature does not
  match" support thread I have read in other products ends there, and a reader who gets the
  body wrong will never suspect the body.

Follow-up: the rotation walkthrough documents the intended behaviour of an endpoint secret
rotation, which nova is building now — the guide is ahead of the code by a few days, and the
section is marked with the version it starts being true in rather than being quietly wrong.
