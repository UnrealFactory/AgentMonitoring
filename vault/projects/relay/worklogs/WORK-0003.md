## What

`.github/workflows/ci.yml`, four jobs, everything a merge needs:

- **check** — `cargo fmt --check`, `cargo clippy --workspace --all-targets -D warnings`, and
  `cargo sqlx prepare --check --workspace`, all with `SQLX_OFFLINE=true` so this job needs no
  database.
- **test** — a `postgres:16` service container with a health check, `sqlx migrate run`
  against it, then `cargo test --workspace`.
- **dashboard** — `npm ci`, `tsc --noEmit`, `vitest run`, and quill's `npm run
  check:api-types` so a change to `docs/api/openapi.yaml` that nobody regenerated fails here.
- **images** — `deploy/Dockerfile.api` and `deploy/Dockerfile.worker` built with buildx,
  cargo-chef for dependency layers, GHA cache, pushed to GHCR on `main` only.

Supporting bits: `.sqlx/` offline metadata committed, `scripts/dev-db.sh` (one command to
get the same Postgres locally), and `deploy/docker-compose.yml` for running api + worker +
db together.

## Why

The alternative that keeps getting proposed for CI is a mocked store. It cannot work here:
`sqlx::query!` type-checks SQL against a real schema at compile time, so mocking the store
means either giving up compile-time checking or shipping a second, hand-maintained idea of
the schema. Both end with a query that Postgres rejects passing CI. The service container
costs about 40 seconds of startup and buys the guarantee that every merged query has been
run by an actual Postgres.

Committing `.sqlx/` is what keeps that honest without making a database a prerequisite for
`cargo check`: the metadata is generated from the real schema, and `--check` in CI fails if
the committed metadata no longer matches the queries in the tree. So a contributor with no
Docker still gets compile-time SQL checking, and stale metadata is a build failure rather
than a runtime surprise.

The images job exists now rather than at deploy time because the build is where Rust CI goes
wrong: a naive `COPY . . && cargo build --release` recompiles every dependency on every
source change. Discovering that during an incident, when you want a hotfix image in three
minutes, is the wrong time.

## How

cargo-chef splits the build into a `recipe.json` of dependencies and the source build, so
the dependency layer is only invalidated by `Cargo.lock`. Combined with
`type=gha,mode=max` buildx cache, a source-only change reuses the whole dependency layer.
Runtime images are `debian:bookworm-slim` with just the binary and CA certificates.

Job graph is deliberately not a chain: `check`, `test` and `dashboard` run in parallel from
the start, `images` waits only for `check`. The slowest path is `test`, so making anything
else faster would not help.

Concurrency group `${{ github.workflow }}-${{ github.ref }}` with
`cancel-in-progress: true`, so pushing twice to a branch does not pay for the first run.

The one non-obvious part is the postgres service and `sqlx migrate`: the container reports
healthy before it is actually accepting connections on the mapped port, so the step waits on
`pg_isready` in a loop with a 30s cap rather than trusting the health check alone. Without
it roughly one run in fifteen failed on connection refused, which is exactly the kind of
flake that teaches a team to re-run CI without reading it.

## Updates

### 2026-07-30T10:45:00Z

Pipeline is green end to end, and the numbers are already better than the target: 13m50s
cold, 5m20s warm on a source-only change. The dependency layer is 4m10s of that and is now
only rebuilt when `Cargo.lock` moves.

Two things fought back. First, the `postgres:16` service container reports healthy before it
accepts connections on the mapped port — roughly one run in fifteen died on "connection
refused" in the migrate step. The fix is a `pg_isready` loop capped at 30s before
`sqlx migrate run`, not a longer sleep. Second, buildx `type=gha` cache was silently missing
on every run until `mode=max` was set; with `mode=min` only the final layer is exported, so
the chef layer was rebuilt every time while the log cheerfully said "cached".

Images: 1.14GB down to 84MB for the API, 81MB for the worker, both on
`debian:bookworm-slim` with just the binary and `ca-certificates`.

### 2026-07-31T09:25:00Z

Added the `dashboard` job and `cargo sqlx prepare --check` to `check`, which found stale
`.sqlx/` metadata on `main` from the `0004_idempotency.sql` migration — the queries compiled
locally against a migrated database and would have failed the first build on a clean
machine.

`scripts/dev-db.sh` brings up the same `postgres:16`, runs the migrations and prints the
`DATABASE_URL` to export. It reuses `deploy/docker-compose.yml` rather than defining a
second Postgres, because two definitions of the dev database drift within a week.

Concurrency group is on with `cancel-in-progress`, which cut the queue during today's
push-twice-in-a-minute afternoon from six runs to three.

## Outcome

CI runs on every push, tests against a real Postgres, and produces deployable images. Merge
to `main` now has one meaning.

Shipped:

- `.github/workflows/ci.yml` — `check` (fmt, clippy `-D warnings`, `cargo sqlx prepare
  --check`), `test` (postgres:16 service, migrations, `cargo test --workspace`),
  `dashboard` (npm ci, `tsc --noEmit`, vitest, `check:api-types`), `images` (buildx +
  cargo-chef, GHCR on `main`).
- `deploy/Dockerfile.api`, `deploy/Dockerfile.worker` — cargo-chef dependency layer,
  `debian:bookworm-slim` runtime.
- `deploy/docker-compose.yml`, `scripts/dev-db.sh` — one Postgres definition shared by
  local dev and compose.
- `.sqlx/` offline metadata committed, so `cargo check` needs no database.

Measured:

- 13m50s cold, **5m20s** warm on a source-only change (target was six minutes). Dependency
  layer 4m10s of the cold run, rebuilt only when `Cargo.lock` changes.
- Images 1.14GB to 84MB (api) and 81MB (worker).
- Flake rate over the last 40 runs: 0, down from roughly 1 in 15 before the `pg_isready`
  wait.

Two traps worth writing down for whoever touches this next:

1. buildx `type=gha` cache with `mode=min` exports only the final layer, so the cargo-chef
   layer was rebuilt on every run while the log said "cached". `mode=max` is not optional
   here.
2. The `postgres:16` service container is reported healthy before it accepts connections on
   the mapped port. The fix is a `pg_isready` loop, not a longer sleep — a sleep tuned on a
   fast runner just moves the flake.

`cargo sqlx prepare --check` earned itself on day one: `main` already had stale `.sqlx/`
metadata from the idempotency migration, which compiled locally and would have failed the
first clean build.

Follow-up: the `images` job pushes to GHCR but nothing deploys them yet — no environments,
no rollback path. That is the next piece of infrastructure work, and it is deliberately not
in this log.
